Practice design: an investment-research assistant

Interview prompt to rehearse: “Help a research analyst compare approved internal research with a new company filing, with citations, while preventing unauthorized disclosure or autonomous trade actions.” This is a practice scenario, not a claim about Acadian’s systems.

Define the decision and boundary

Identify the analyst’s task, permitted source documents, freshness requirement, and what a useful, cited answer looks like. Keep investment decisions and orders with authorized humans.

Design retrieval and tools

Ingest with source version, effective date, tenant and entitlement metadata. Retrieve only documents the caller can access; show citations to exact passages. Treat document text as data, never instructions.

Choose a narrow agent loop

Use deterministic retrieval and comparison first. Add bounded tool calls only where they improve the task; set budgets, timeouts, trace IDs, and a clear stop condition. Define human approval for any write or outward action.

Evaluate before release

Build a versioned set of real analyst questions: correct citations, answer support, abstention, access-control negatives, stale-source handling, latency, and cost. Review difficult cases with research and Risk; gate rollout on agreed thresholds.

Operate and improve

Log source and model versions without leaking sensitive content. Monitor quality, cost, latency, denied access, and human overrides. Roll out by cohort, preserve rollback, and assign an owner for incidents and data lifecycle.

Likely interview questions

Answer aloud before opening the prompts. These are inferred from the job description, not a known interview script.

How would you turn a successful agent prototype into a production service?

Start with the workflow and measurable outcome. Name the owner and API contract; constrain tool permissions; make side effects idempotent; add traces, evals, incident response, rollback, and a staged rollout. Explain which autonomy you would postpone until evidence supports it.

How do you know a RAG or agent system is good enough?

Split the scorecard: retrieval recall and entitlement, grounded answer quality, abstention, tool correctness, human task success, latency, and cost. Version the dataset and judge criteria; compare to a simple baseline; inspect regressions by slice before a release.

Where do governance and security controls live?

At the data, tool, and action boundaries: caller identity, document entitlements, scoped credentials, approval on consequential actions, audit logs, retention, and red-team cases for prompt injection. A model instruction alone is not an enforcement boundary.

How would you handle disagreement between research, Risk, and platform engineering?

Write down the shared outcome and constraints, compare two or three concrete options with cost and failure modes, then run a small test with an agreed decision date. Make the chosen standard and exception path visible; revisit it with adoption and incident data.

Would you use Bedrock, a hosted model API, or a self-hosted model?

Ask first about data classification, required regions, existing contracts, model quality, latency, volume, and team capacity. Compare total operating cost and control needs against a benchmark workload. The posting prefers Bedrock; it does not say every workload must use it.

How would you improve inference cost without losing quality?

Measure token mix and bottlenecks first. Consider prompt and context trimming, retrieval quality, caching where entitlements permit it, smaller models for narrow tasks, batching, and fallback rules. Re-run the same quality and safety evals before claiming savings.

After the screen: the client’s bar

Prepare now

Rob’s screen gets you submitted. What follows is Anthropic’s own step, usually a conversation with someone on the evaluation side and often a work sample: review a model-written PR, rate what you find, and write the rationale yourself. The material below is the vocabulary that step is graded in. Rehearse it aloud before the client call, not after.

The severity ledger

SeverityWhat it meansWhat it looks like in a model PRHow you prove it
Blocking Wrong behaviour on a realistic input, data loss, a security hole, or the task not actually done. The description claims a fix; the diff changes the test instead. An exception path that returns None into a caller that iterates. Expected values hard-coded to make the test pass. A reproduction: the input, the command, the observed output. Cite the line. Quote the claim it contradicts.
Major Works on the happy path; breaks on an edge the task named or a real user hits. Empty input, unicode, concurrency, timeouts, a migration without a rollback, config added but never read. Name the edge, show it is in scope (the task text or the existing tests), show the diff does not cover it.
Minor Correct but wrong for the codebase: duplicates an existing helper, ignores a convention, leaves the design harder to change. A second retry helper beside the one in utils. A broad try/except around new code. Dead parameters left from an abandoned approach. Point at the existing pattern the change should have used. One line of why it matters later.
Nit Style, naming, a comment that lies. Worth noting, never worth the lead paragraph. A docstring describing the old behaviour. Inconsistent naming against neighbours. State it in one clause and move on. Nits that crowd out a Blocking finding are a reviewer failure.

The tell they are hiring for. A plausible PR passes its own tests, reads cleanly, and describes itself accurately in every place except the one that matters. Start from the claim, not the code.

Reading a session log: the four columns

The JD lists these four verbs. Use them as literal column headings when you take notes on a transcript.

Investigated

What did it open before it edited?

  • Did it find the callers of what it changed?
  • Did it read the existing tests and CI config?
  • Did it look for a helper that already did this?

Verified

What did it actually run, and did it read the result?

  • Tests run, and which ones, after the last edit?
  • Reproduced the bug before fixing it?
  • Checked output, or only the exit code?

Assumed

Premises it never checked.

  • Input shape, environment, library behaviour.
  • “The tests cover this.”
  • Any “should work” in the transcript.

Skipped

The part of the task that quietly went missing.

  • Edge cases named in the task, absent from the diff.
  • Error paths, migrations, docs, config.
  • Scope narrowed without saying so.

What a rationale looks like

They want why it fails, not how to fix it. Lead with the failure, cite the location, show the input that triggers it, then the severity and its reason. An illustrative diff and the finding it would earn: 

+ def fetch(url, tries=3):+     for attempt in range(tries):+         try:+             return client.get(url, timeout=5)+         except Timeout:+             log.warning("timeout %d/%d", attempt + 1, tries)  # falls through after the last timeout and returns None
Blocking

Retries swallow the final failure

fetch() returns None after the third timeout instead of raising. Its only caller, sync_orders(), iterates the return value, so three slow responses in a row turn a retryable failure into a TypeError inside the sync job. The added test covers two timeouts followed by success and never reaches the exhausted path. Reproduced by patching the client to raise Timeout three times. The PR description says the change “adds resilient retries”; the transcript shows the model never opened the caller.

Write it by hand. That paragraph is the length and shape they are asking for. Practise producing one against a real PR, timed, without assistance, before the client conversation.

If they ask about building a benchmark

  • Hermetic. Pinned base image, pinned dependencies, no network at test time. A benchmark that passes on Tuesday and fails on Friday measures the weather.
  • Deterministic tests, split visible from hidden. The model sees enough to understand the task; the graded tests it cannot see, so it cannot pattern-match them.
  • Requires reading the codebase. A good task cannot be solved from the prompt alone; the answer depends on callers, conventions and constraints that live in the repo.
  • Guarded against shortcuts. Hard-coded outputs, edited tests, and skipped assertions must fail the grade, not pass it. Write the rubric before the model runs.
  • Passable by a human. Solve it yourself inside the container first and record how long it took. A task nobody can pass measures nothing.

Is this a way into Anthropic?

What the research found

Not in any documented way. Searches across Blind, Hacker News, Reddit and Glassdoor turned up no account of a vendor evaluator converting to a full-time Anthropic role. Anthropic sources this kind of work through vendors at scale — Mercor alone reports tens of thousands of contractors — and its full-time engineering loop is a separate, referral-heavy, highly selective process that a contract does not shortcut.

The fair valuation: six months of well-paid work on frontier-model evaluation that sharpens exactly the judgement this whole prep set is about, and a resume line that travels. A referral from a researcher you work with would be a genuine bonus. Plan on the work, not the bonus.

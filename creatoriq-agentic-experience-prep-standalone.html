01 · Read the actual mandate

This is a platform role with an AI product surface.

Interpretation of the supplied posting: they need someone who can take an agent beyond a demo—into authenticated enterprise workflows, operational controls, and a usable full-stack experience. Prepare to explain the boundary between the model's suggestions and the system's authority.

The business context

The supplied description places CreatorIQ at the center of creator relationships, campaign performance, governance, and commerce. It reports more than 1,300 organizations, more than 15 million creators, and more than 250 million social posts processed daily. These are figures from the supplied posting, not a fresh scale audit.

The public homepage also emphasizes intelligence, brand safety, enterprise integration, and governance. That supports leading with trustworthy workflows, not a generic chatbot pitch. [1]

Translate scale into judgment

Do not propose an LLM call for every post simply because the posting names a large ingestion volume. First separate ingestion, indexing, deterministic filtering, ranking, and task-specific agent reasoning. Ask what already exists and reuse it.

Creator discovery and agent discovery are different: the former finds people for campaigns; the latter helps a user choose an automation that is capable, permitted, and safe for the task.

The sentence to keep returning to

“I want users to get useful work done, with permissions, evidence, and recovery built into the workflow—not bolted onto the answer afterward.”

04 · A plausible design exercise, not a known interview question

Design a governed creator-shortlisting assistant.

Practice prompt

A brand manager gives a campaign brief. The assistant proposes relevant creators, explains the evidence and data freshness, saves a draft shortlist, and optionally drafts outreach. It must not reveal another client's data or contact creators without the required approval.

Clarify before drawing: Who can act for which brand? Are agencies managing several brands? Which datasets and APIs are available? What counts as success? Is outreach in scope? Which actions are irreversible? What are the run-time, cost, freshness, language, and approval requirements? Don't assume CreatorIQ's internal implementation.

  1. React / TypeScript: select the workflow and scope

    Show the active brand, task, allowed data sources, requested actions, and expected review steps. Submit a run request to the backend. The browser never receives connector secrets and is not the policy authority.

  2. Node.js API: authenticate, authorize, and create durable state

    Resolve actor and tenant from trusted identity, validate the brief and resource scope, pin the agent version, and create a run record. Use an idempotency key for run creation. Enqueue through a transaction/outbox arrangement so the accepted run is not lost between database commit and queue publish.

  3. Durable orchestration: retrieve, reason, verify

    Run bounded steps in a worker; Python is useful if the ranking/ML stack needs it, not mandatory for every step. Persist checkpoints, deadlines, and usage. Let deterministic services perform filters and calculations; use the model for interpretation and evidence-grounded synthesis.

  4. MCP / API adapters: enforce the business boundary

    Expose narrow operations such as search_creators, get_campaign_metrics, and save_shortlist_draft. These names are illustrative. Derive tenant context server-side; enforce per-resource access and input/output contracts. Treat returned bios and posts as untrusted content.

  5. Review UI: show a proposal, not an unexplained verdict

    Return creator IDs, reasons, supporting records, timestamps, missing data, and suitability flags for human review. Show draft versus executed state clearly. Outreach approval names exact recipients and message content; changes invalidate the approval.

  6. Execution worker: reauthorize and perform one identified action

    Recheck policy, approver authority, expiry, resource version, and cancellation just before the side effect. Use a stable action ID with downstream idempotency where available. Record the external receipt. If the result is uncertain, reconcile before retrying.

  7. Observability: evidence from request to outcome

    Publish durable run events to the UI over SSE or another supported streaming channel, with reconnect from an event cursor. Keep audit access tenant-scoped. Track task outcome, tool failures, review burden, latency, and cost; route incidents into regression tests.

State model you can write on a whiteboard

queued → running → awaiting_approval → executing → succeeded

Also allow explicit failed, cancelled, partial, and unknown_outcome states. A policy denial is a reasoned outcome, not a generic transport error. A retry is a transition with a budget, not a new invisible run.

Store the run separately from its actions. A run can contain one successful read and one uncertain send.

Choose boring infrastructure deliberately

Start with a relational store for tenants, agent versions, runs, actions, approvals, and audit references; object storage for large artifacts; a durable queue for background work; and a search/retrieval index when needed. Treat caches and embeddings as derived data, not the authorization authority.

Pick AWS or GCP based on their existing environment. Use scoped service identities, managed secrets, bounded workers, backup/restore checks, and tenant-aware admission. Multi-cloud is not automatically a requirement.

The follow-up that reveals distributed-systems experience

“The outreach API timed out. Do you retry?” Not blindly. The send may have completed. Query a receipt or status using the stable action ID; reuse a provider-supported idempotency key. If the provider cannot disambiguate, show an unknown outcome and reconcile through an operator. “Exactly once” is not a property you get by adding a queue.

06 · Do not miss this requirement

Agent discovery is a governed product experience.

Proposed catalog: a user searches by job to be done—campaign research, performance summary, shortlist drafting—then sees only eligible agents. Filter on tenant entitlement, data access, connector availability, approved version, and risk policy before ranking by task fit.

What an agent card should explain

  • Purpose, owner, supported tasks, and known limitations
  • Inputs, outputs, data freshness, and required connectors
  • Read/write permissions and the actions that need approval
  • Evaluation scope and date—not a context-free quality score
  • Expected latency/cost range from representative measurements
  • Version, availability, suspension status, and safe trial option

How to evaluate and choose

Offer a sandbox or draft-only sample with the user's permitted data. Let users compare evidence quality, review effort, connector support, and task success. Explain why an agent is unavailable and what permission or configuration is missing.

A reviewed release moves from draft to pilot to approved; retirement and suspension remove it from new runs. Existing runs pin their version, but not an irrevocable right to continue after security revocation.

Success metric: time from task intent to a correctly completed, policy-compliant workflow. A catalog click or agent install is only an intermediate signal.

07 · Active recall

Sixteen questions to rehearse aloud.

Try each answer before opening it. These are original practice prompts inferred from the role—not leaked questions or a confirmed interview plan. Aim for 60–90 seconds, then let the interviewer choose the depth.

01 · Architecture

What makes an agent production-ready rather than a demo?

Reveal answer spine and follow-up

Start with the useful task and permitted actions. Then cover trusted identity, durable run state, typed tools, resource-level authorization, bounded execution, approval for important side effects, observability, and a tested recovery path. Ship a small workflow with measured outcomes before generalizing to arbitrary autonomy.

Follow-up: “How do you know it worked?” Cite the action receipt and task-specific evidence. A fluent final message, HTTP 200, or queued job is not proof of successful execution.

02 · MCP in production

How would you expose CreatorIQ functionality through a custom MCP server?

Reveal answer spine and follow-up

Put a narrow adapter over existing domain APIs and reuse their permission rules. Define clear tool names, validated schemas, bounded results, typed errors, and resource checks. For a remote server, select a supported transport and compatible authorization implementation; plan for connection lifecycle, timeouts, rate limits, credential rotation, and contract tests. MCP standardizes interaction, not your entire security model. [2]

Follow-up: “Does a session ID authenticate the caller?” No. Keep transport/session continuity separate from authenticated identity and authorization. Recheck the latter on protected operations.

03 · Tool design

What would a good campaign-analysis tool contract look like?

Reveal answer spine and follow-up

Prefer a domain operation to unrestricted SQL or an arbitrary URL fetcher. Accept a campaign identifier and a bounded date range; resolve brand access from the caller. Return structured metrics with units, period, attribution caveats, source timestamps, and pagination/truncation markers. Keep “no records,” “forbidden,” “stale data,” and “upstream unavailable” distinct.

Follow-up: “Can the model choose the tenant ID?” It may request a scope, but the server validates it against the caller's authority. A model-supplied ID must never become authority on its own.

04 · Agent discovery

How would you help customers choose the right agent?

Reveal answer spine and follow-up

Start with task intent and filter for eligibility before relevance. Show a versioned agent card with capability, permission, connector, review, and evaluation information. Let the user try a representative safe workflow and inspect the output. Measure completed workflow quality and time to value, not just selection frequency.

Follow-up: “What if the most relevant agent isn't allowed?” Explain the missing prerequisite without leaking restricted metadata. Offer an eligible alternative or a legitimate access-request path; ranking cannot override policy.

05 · Guardrails

Where do prompts stop being the right safety mechanism?

Reveal answer spine and follow-up

Use Papercusp's concrete boundary: a typed dispatcher can authorize an action before its handler; a file lock serializes a conflicting write; managed shell and PTY tools give arbitrary execution an accountable route. But a generic shell still needs OS and credential restrictions, and native execution remains available in the inspected Codex session. Do not claim universal enforcement. The source-checked Bash/tool breakdown explains what exists, which substitutions are not equivalent, and what a complete cutover must prove.

For CreatorIQ, that translates to a narrow campaign or outreach operation whose backend checks actor, brand, resource, and approval—not a general-purpose shell with campaign credentials. Keep build/debug capabilities separate from customer-agent capabilities.

Follow-up: “Is removing a tool from the menu enough?” No. A manually constructed call still needs server authorization; an alternative runtime with the same unrestricted credentials can still defeat a high-level tool restriction.

06 · Prompt injection

A retrieved creator post asks the agent to export client data. What happens?

Reveal answer spine and follow-up

Treat the post as task data, never as a permission grant or a trusted instruction. Constrain the data passed into reasoning and keep external content out of privileged instructions. Restrict tool capabilities and egress, validate requested actions, and log the denied attempt if one is made. Test whether a forbidden side effect occurred, not whether the final answer sounded safe. [4]

Follow-up: “Can you eliminate the risk?” No single filter or prompt proves that. Use multiple controls and disclose the residual risk.

07 · Distributed systems

How do you handle a tool timeout after a write may have succeeded?

Reveal answer spine and follow-up

Keep a stable action identity and separate submission from confirmation. Query downstream state or a receipt, use supported idempotency, and reconcile before retrying. Distinguish a transient connection problem from invalid input or a policy denial. A failed response is not a negative acknowledgment from the business system.

Follow-up: “What if the API has neither idempotency nor a status lookup?” Preserve an unknown outcome, stop automatic retries for risky writes, and provide a human reconciliation path. State that limitation before launch.

08 · React / TypeScript

How would you build the frontend for a long-running agent?

Reveal answer spine and follow-up

Use server-owned run state represented by a typed state machine. Show progress, evidence, pending approvals, partial results, and actionable errors. Subscribe to events, deduplicate by event ID, and reconnect with a cursor or fetch a fresh snapshot when the cursor is too old. Cancel goes to the backend. A tab refresh must not lose the job or imply it restarted.

Follow-up: “What about generated content?” Render it as untrusted text or sanitized markup, validate links, and never execute generated HTML. Support keyboard navigation, focus management, and non-noisy status announcements.

09 · Backend boundaries

Where would you use Node.js and where would you use Python?

Reveal answer spine and follow-up

Choose based on the existing team and workload. Node/TypeScript can own the API, frontend-adjacent types, streaming, and connector adapters. Python can own ranking, ML evaluation, or orchestration when its libraries justify it. Do not split a simple workflow into services just to use both languages. Across a real boundary, use versioned schemas, run IDs, timeouts, and explicit errors.

Follow-up: “How do you keep the API and worker in sync?” Contract tests and backward-compatible event/schema changes; deploy consumers that tolerate the transition before producers depend on new fields.

10 · Cloud and scale

How would you scale this across global enterprise customers?

Reveal answer spine and follow-up

Separate interactive APIs, durable orchestration, inference, and connector workers. Bound concurrency at provider and tenant boundaries; use fair queues so one brand cannot monopolize capacity. Autoscale against actionable queue and latency signals with downstream limits in mind. Plan scoped service identities, secrets, telemetry, region requirements, restore tests, and failure drills.

Follow-up: “AWS or GCP?” Start with the platform they already operate. Explain one concrete design you understand; do not assume the posting's mention of both means a multi-cloud mandate.

11 · Databases

What belongs in a relational database versus a vector index?

Reveal answer spine and follow-up

Use a relational store for authoritative identities, permissions, run transitions, approvals, and action records. Use search/vector retrieval for candidate discovery and supporting evidence, with scope filtering and freshness metadata. Store large artifacts separately. Indexes and caches need invalidation and deletion propagation; their stale copy must not decide that access is allowed.

Follow-up: “Can an embedding be treated as harmless?” No. Apply the source data's access and retention requirements to derived representations too.

12 · Evaluation and creator relevance

How would you know the shortlist is good?

Reveal answer spine and follow-up

Agree a task rubric with domain experts: relevance to the brief, evidence correctness, freshness, suitability concerns, useful coverage, and review effort. Compare against a baseline on representative campaigns, languages, and creator sizes. Keep hard permission tests separate from subjective recommendation quality. Then examine user acceptance, edits, completion time, and downstream outcomes with appropriate caveats.

Follow-up: “Does higher engagement prove the agent drove sales?” No. Metric definitions and attribution matter; do not turn correlation, estimated reach, or missing conversion data into a causal ROI claim.

13 · Framework judgment

Would you use LangGraph, an agent SDK, or custom orchestration?

Reveal answer spine and follow-up

Choose on requirements: durable state, human review, branching, replay behavior, tracing, language, and operational support. LangGraph supports interrupt-and-resume workflows; the OpenAI Agents SDK runs tool loops and supports agent handoffs and review patterns. Frameworks do not own your business authorization, tenancy model, or external side-effect guarantees. [5] [6]

Follow-up: “What subtle behavior would you check?” Whether resuming repeats code before a pause. LangGraph's interrupted node restarts from its beginning, so repeated side effects require careful placement and idempotency. Be precise about the version you've actually used.

14 · Client engagement

A customer says the agent's recommendations are wrong. What do you do?

Reveal answer spine and follow-up

Ask for the business expectation and a concrete example, with permission to inspect the relevant trace. Reconstruct the brief, data freshness, agent version, tool results, and review outcome. Classify whether the issue is retrieval, permissions, metric meaning, reasoning, or unclear UX. Agree a testable improvement with the customer and turn the example into a privacy-safe regression case.

Follow-up: “Would you show the entire trace?” Only what that customer is allowed to see, with secrets and unrelated data removed. Explain the evidence and decision path without exposing hidden model reasoning.

15 · Product trade-off

A PM wants autonomous outreach immediately. How do you respond?

Reveal answer spine and follow-up

Clarify the desired outcome and the actual risk: wrong recipients, duplicate messages, incorrect claims, or policy violations. Offer a useful first release—drafting plus a bounded, explicit approval flow—then define what evidence would justify more autonomy. Put metrics and stop conditions on the pilot. Challenge the mechanism while preserving the business goal.

Follow-up: “Does that slow innovation?” It creates a credible path to learn with limited consequences. Avoid both unrestricted automation and approval fatigue.

16 · Honest production evidence

Tell me about an agent or MCP system you personally deployed.

Reveal answer spine and follow-up

Name the environment and users, your precise contribution, one end-to-end request, one failure you handled, and the test or operational evidence that supports the outcome. Use Papercusp where that is accurate, but distinguish internal dogfooding, alpha deployments, and external customer use. State what you would need to add for a global multi-tenant enterprise.

Follow-up: “What was the scale and impact?” Use a dated measurement you can explain, with units and a denominator. Do not substitute repository size, number of agents launched, or a marketing-style estimate for production reliability.

09 · A proposal, not a promise

Learn the boundary, ship a slice, then widen it.

  1. Days 1–30: understand the existing platform

    Map identity, tenant/brand access, APIs, MCP implementations, deployment, and incident history. Sit with a customer-facing partner and a real workflow. Agree the first use case, risk model, baseline, and measurable acceptance criteria.

  2. Days 31–60: deliver one governed vertical slice

    Ship a limited draft-first experience with a typed connector, durable runs, permission tests, evidence display, and approvals where needed. Pilot with an agreed audience; measure quality, latency, cost, and review burden.

  3. Days 61–90: make the pattern reusable

    Use pilot results to improve the agent card, evaluation suite, connector contracts, audit view, and operational runbook. Broaden scope only where the evidence supports it. Assign ownership for each version and its ongoing support.

01 · Context persistence and memory management

Persist by purpose, not by dumping the whole conversation.

A1

“How would you decide what an agent keeps in context or memory?”

“I separate three things: working context, durable state, and optional memory. Working context is what the current step needs right now — the task, the latest tool results, constraints, and the evidence supporting the next decision. I would summarize it when it approaches a measured token or latency budget, but the summary has to preserve open decisions, identifiers, deadlines, and unresolved uncertainty. I would never silently summarize away a pending side effect.

Durable state is different: run status, checkpoints, approvals, tool receipts, and user-owned artifacts belong in a durable store with explicit schemas. Memory is selective and policy-controlled. I would write a fact only when it is useful beyond this run, safe to retain, attributable to a source, and likely to remain valid. Every memory needs an owner, scope, timestamp or version, and a way to correct or retract it.

On resume, I would rebuild context from the durable run record and the relevant memories rather than trusting a stale transcript. Retrieval should be scoped to the actor, tenant, task, and time horizon. The acceptance test is not ‘the model remembers’; it is that a resumed run makes the same safe decision, cites the right evidence, and does not repeat a completed side effect.”

Follow-up: “What gets summarized first?” Compress redundant tool output and conversational filler first. Preserve state transitions, exact IDs, policy decisions, approvals, failures, and anything needed to reconcile an external effect.

02 · Idempotency and job persistence

A retry is safe only when the system can identify the same action.

A2

“How would you make idempotency keys and background jobs survive restarts?”

“I would create the idempotency record before doing work, backed by a unique constraint on the actor, operation, and client-provided key — or a server-generated key returned to the client. The record stores the normalized request, the target resource, the current state, and the result or external receipt. A duplicate request returns the existing outcome instead of starting a second action; a conflicting payload under the same key is rejected.

For a background job, the database is the source of truth. I would persist the job and its attempt state in one transaction with the event or outbox entry that wakes the worker. Workers claim with a lease, renew it while running, and make each step restartable. If a worker dies, the lease expires and the job can be retried. If an external call times out, I do not assume failure: I query the provider by the same idempotency key or reconcile by receipt. If the provider cannot disambiguate, the job becomes unknown_outcome and needs an operator or reconciliation path.

I would not clear the idempotency store as a cleanup shortcut. Retention can be bounded only after the downstream system's duplicate window and late retries are understood. The tests I want are restart after claim, duplicate delivery, timeout after provider acceptance, and a malformed reuse of an existing key.”

Follow-up: “Can a queue guarantee exactly once?” No. It can deliver at least once or at most once depending on the design, but exactly-once business effects require a durable identity, downstream cooperation, and reconciliation.

03 · Experiment design

Define the decision before collecting a prettier number.

A3

“How would you design a rigorous A/B test for an AI feature?”

“I start with a falsifiable hypothesis and the decision it will change: for example, ‘the new retrieval policy improves successful task completion without increasing harmful or abandoned actions.’ The primary metric must represent that outcome, not just model preference or click-through. I pre-register the guardrails too — error rate, latency, cost, complaint rate, and any safety or policy-violation measure.

The randomization unit depends on interference. If users share state or teams coordinate, randomize at the workspace or account level; if not, user-level randomization may give more power. I keep assignment sticky, verify balance, exclude only pre-declared invalid traffic, and log exposure so I can distinguish assignment from actual treatment. The control and treatment must use comparable data, model budgets, and evaluation windows.

Before launch I estimate the minimum detectable effect, baseline variance, sample size, and expected runtime. I use confidence intervals and a pre-declared stopping rule rather than repeatedly peeking until something is significant. I would also inspect heterogeneous effects by task type and user segment, while treating those as secondary unless powered in advance. A result is actionable only when the primary metric improves, guardrails hold, the effect is practically meaningful, and the experiment was not contaminated by rollout or logging differences.”

Follow-up: “What if labels arrive late?” Use an operational proxy only as an explicitly temporary signal, keep the final outcome metric separate, and do not declare a winner until the delayed-label window has matured.

04 · Deployment strategy

Separate artifact validation from exposure and rollback.

A4

“Explain blue/green and canary deployment for an AI service.”

“I build an immutable candidate once, then promote that exact artifact. In blue/green, blue is the current environment and green is a separately provisioned environment with the new service, model, configuration, and dependencies. I validate green with smoke tests, contract tests, representative offline evaluation, health checks, and a reversible data-migration plan before shifting traffic. The switch is a routing decision, not a rebuild.

Canary is more gradual: send a small, controlled slice of traffic to the candidate, keep the assignment observable, and compare it with the baseline on both technical and task metrics. For an AI system I would watch not only 5xx responses, but successful task completion, groundedness or policy violations where measurable, latency, token cost, queue age, and human escalation. The thresholds must be tied to a baseline and a time window, not a single noisy sample.

Rollback means routing away from the candidate and stopping new work on it. Before a rollout I verify backward-compatible schemas or use expand-and-contract migrations, because reverting application code cannot revert an incompatible database change. I also pin in-flight runs to their version and record which version produced each result. A rollout is complete only after the canary window passes and the rollback path has been exercised or otherwise verified.”

Follow-up: “Would you roll back on one bad answer?” Not automatically. Classify severity, check whether the issue is isolated or systemic, halt expansion when the guardrail is threatened, and use the smallest safe rollback that protects users while preserving evidence.

05 · Observability

Every metric should answer what action it changes.

A5

“What metrics, thresholds, and trace spans would you use?”

“I use three layers. First are operational signals: request rate, error rate, cancellation rate, queue age, saturation, and p50/p95/p99 latency. Second are AI-specific signals: task completion, tool success, retry rate, token and dollar cost, retrieval hit or empty-result rate, human correction, and policy denials. Third are delayed outcome signals such as user acceptance, incident rate, or model quality once the labels exist. I keep these definitions explicit because a 200 response or a queued job is not proof that the task succeeded.

For thresholds, I would start from the service SLO and a measured baseline rather than invent universal numbers. As an example, a sustained p95 latency breach for five minutes could page for a synchronous user path; a smaller increase could open a ticket. A sudden error-rate jump, queue age above the maximum useful wait, or any confirmed cross-tenant or unsafe side effect would be a release stop regardless of average latency. Cost and token budgets should have per-run limits as well as aggregate alerts.

A trace should make one run explainable without exposing secrets: request and identity scope, run creation, retrieval, model call, each tool call, policy decision, approval, external receipt, and final outcome. I would attach stable run and action IDs, version and dataset identifiers, durations, retry counts, and redacted error categories. High-cardinality values belong in trace attributes or sampled event records, not unbounded metric labels. The detector itself needs tests: a deliberately failed tool call should create the expected span and alert signal, and a successful run should leave a complete positive-control trace.”

Follow-up: “What is the first dashboard?” Start with the user journey: accepted runs, completed runs, failed or unknown outcomes, p95 latency, queue age, cost, and the top failure categories. Add model-quality panels only when their label and denominator are trustworthy.

SLOstask outcometrace spanscardinalitypositive control

Senior Software Engineer · start here

The questions you remember, answered plainly.

Likely checklist, based on the feedback

Normal behavior, boundary inputs, concurrent calls, failures and retries, side effects, and performance. The exact interview wording is unknown.

Q1

“How would you check that a function is behaving well?”

“First I would define what the function promises: which inputs it accepts, what it returns, what errors it raises, and whether it changes any state. Then I would test a normal case and the inputs where its behavior changes, such as empty input or a value at the allowed limit. For each case I would assert the exact result or error, not just that the function did not crash.

If the function touches shared state, I would test overlapping calls and retries. I would check its side effects as well as its return value. Finally, I would try very large or difficult inputs and measure whether the amount of work grows unexpectedly.”

What makes the test pass? The expected output or error, the expected final state, and the expected number of side effects—for example, one charge rather than two.

contractnormal caseboundaryside effectsperformance
Q2

“What is a boundary?”

“A boundary is a point where a function's behavior changes, often the edge of what it accepts. If it accepts ages 18 and up, I would test 17, 18, and 19: just below, exactly at, and just above the boundary. For a list, empty versus one item is another boundary. If a string may have at most 100 characters, I would test 99, 100, and 101. Bugs often hide at these edges.”

Easy phrase to remember: “Just below, exactly at, and just above the limit.”

17 · 18 · 19empty · one item99 · 100 · 101
Q3

“How would you test concurrency?”

“Concurrency means two calls are in progress at the same time. I would test two calls using the same shared data. I would pause both after they read it, then let them continue together. I would check the final value and any side effects. If both calls increment a counter, the final value should increase by two, not one. If both submit the same payment key, there should be one charge and both should get the same result.

In JavaScript, calls can overlap across await points even though one event-loop thread runs their JavaScript code one piece at a time. A controlled pause makes the overlap repeatable; simply using Promise.all might miss the bug. If the function is purely synchronous and has no shared state, I would test for unwanted mutation instead, and test concurrency at the stateful part of the system.”

What makes the test pass? No lost update, no duplicate action, and the same stable result for duplicate requests.

overlap deliberatelyfinal stateside-effect countawait interleaving
Q4

“What is database chunking, and how would you process a large table?”

“Database chunking means handling a large set of rows in smaller batches. If I needed to process a million rows, I would not load them all into memory or hold one long transaction. I might read 1,000 at a time in order of an indexed, stable ID, process that batch, commit its changes, save the last processed ID, and continue with IDs after it. That bounds memory use and transaction time, and the saved position lets the job resume after a crash.

I would make processing each row safe to retry, because a crash can happen after a batch commits but before its position is saved. I would choose the batch size from measured database time and lock impact. For a changing table, I would define which rows belong to the run—perhaps by recording the highest ID at the start—so new inserts do not make the job run forever. I would use a stable cursor rather than a large OFFSET, which can get slower and can skip rows as data changes.”

Clarify the term: This answer is about processing rows in batches. Sharding means splitting data across databases; document chunking means splitting text into passages, often for search or AI.

small batchesstable cursorcheckpointsafe retry

06 · Senior Software Engineer · JavaScript concurrency

Explain where work overlaps and where it truly runs in parallel.

SWE1

“Does JavaScript run requests in parallel?”

“I would separate concurrency from parallel execution. In a typical Node.js process, JavaScript callbacks on one event-loop thread run one at a time. An await lets other work progress while an I/O operation is pending; Promise.all can overlap those operations, but it does not give CPU-heavy JavaScript more cores. Node also has a thread pool for selected operations, and worker threads or separate processes can run JavaScript in parallel.

That distinction matters in a review. Two request handlers can interleave across await points, and multiple processes or service replicas can touch the same database row at once. I would identify the shared resource and enforce the invariant there, usually with a unique constraint, an atomic update, or a transaction. I would not rely on the fact that one callback runs at a time to prevent duplicate charges.”

Follow-up: “What if the work is CPU-bound?” Measure event-loop delay and throughput, then move the heavy computation to worker threads, a separate service, or a bounded job pool; simply adding Promise.all will not parallelize it.

event loopI/O overlapworker threadsdatabase boundary
SWE2

“What concurrency bug would you look for in a payment code review?”

“A classic bug is read, await, then write: two handlers both observe ‘unpaid,’ both call the provider, and both mark the order paid. I would ask what identifies one logical payment attempt and where that identity is enforced. I would reserve the attempt under a unique key in durable storage, commit the request and work intent, and send the same key to a provider that supports idempotency. A conditional state transition prevents stale workers from overwriting a newer result.

I would also check fan-out. An unbounded Promise.all can overload the provider or database even if each request is logically correct. I would cap concurrency, honor rate limits, and test two simultaneous requests plus a retry after a process restart. The expected result is one logical charge and one stable result for the same key.”

Follow-up: “Would a mutex in the Node process fix it?” It can coordinate that one process, but it does not cover other replicas or restarts. The durable constraint remains the authority.

interleaving at awaitunique keyconditional transitionbounded fan-out

07 · Senior Software Engineer · test design

Name the exact observation that makes a test pass.

SWE3

“How do you choose a test oracle for a payment workflow?”

“I start from the contract, not from the implementation. For an accepted payment, the oracle is an allowed state transition, one provider charge or receipt for the idempotency key, and a durable result the client can retrieve. A declined payment has a terminal failure state and no successful charge. A timeout is different: it may produce unknown_outcome until reconciliation confirms what the provider did.

I use deterministic fixtures for request, provider response, clock, and retry schedule, then assert the state and external-call count at each boundary. If an output is meant to be stable, I can compare a canonicalized result or stable hash, excluding timestamps and generated IDs. If the output is intentionally variable, I assert invariants and relationships instead of a brittle snapshot. That gives the test a clear reason to fail.”

Follow-up: “Why not assert HTTP 200?” It proves only that the API answered. The test also needs the business outcome and its durable evidence.

state transitionexternal receiptdeterministic fixturestable hash
SWE4

“How would you test idempotency across crashes and replays?”

“I would inject failures at the important boundaries: before the attempt is committed, after it is committed but before the provider call, after provider acceptance but before our response is stored, and after completion but before the client receives it. Then I restart the worker or replay the queue message. For the same key and payload, the eventual result should be the same, with no second business effect. Reusing a key with a different payload should be rejected.

The hardest case is a provider timeout after acceptance. My fixture should record that the provider charged once while our process saw a timeout. The expected local state is unknown until a status lookup or reconciliation resolves it; a blind second charge fails the test. I would also verify that duplicate messages and concurrent callers converge on the same attempt record.”

Follow-up: “What does the queue guarantee?” Assume at-least-once delivery and make the business effect safe under replay; queue delivery alone cannot prove exactly-once charging.

failure injectionrestartduplicate deliveryunknown outcome
SWE5

“How do you make performance tests useful without making them flaky?”

“I separate algorithmic tests from environment-sensitive benchmarks. First I use deliberately difficult inputs—large arrays, high-cardinality keys, skewed distributions, and cases that trigger worst-case sorting or repeated scans. I assert work directly where possible: query count, comparison count, allocation size, queue depth, or event-loop delay. Those checks expose an accidental quadratic path without depending on a noisy wall clock.

For end-to-end latency, I use a controlled environment, warm-up, repeated runs, fixed data and concurrency, and a distribution such as p95 rather than one timing. I compare against a measured baseline and a meaningful regression budget, then investigate noisy results before declaring failure. The test report should show the input size and the observed scaling, so we can tell a code regression from host variance.”

Follow-up: “What would run in CI?” Keep deterministic complexity and instrumentation checks in regular CI; run noisier load benchmarks in a stable performance environment.

worst-case inputsoperation countscontrolled benchmarkp95 + baseline

08 · Senior Software Engineer · architecture

Connect a clear API contract to durable work and visible outcomes.

SWE6

“Sketch a payment flow that survives worker or queue failures.”

“The API validates the request and idempotency key, then records a payment attempt and an outbox event in one database transaction. A publisher moves the event to a durable queue; workers may receive it more than once, so they claim the attempt and check its current state before calling the provider. The provider call carries the same idempotency key. The worker stores the provider receipt and transitions the attempt to a final state, while the API exposes a status endpoint for clients that did not receive the first response.

The outbox closes the gap between committing the attempt and publishing work. I would monitor unpublished outbox age and queue age, retry with backoff, and send exhausted or malformed work to an operator-visible dead-letter path. A replay must reuse the same attempt identity. This design makes a lost response or duplicate queue delivery recoverable without creating a second charge.”

Follow-up: “Why not write to the database and then publish to the queue?” A crash between those two separate writes can leave an accepted payment with no queued work.

transactional outboxdurable queuereplaystatus endpoint
SWE7

“How do you handle provider timeouts and rate limits?”

“A timeout does not tell me whether the provider accepted the charge. I record the attempt as unknown_outcome, keep its original key, and reconcile using the provider's status API or receipt before deciding to retry or finish. If the provider cannot answer, I expose the pending status and escalate after a bounded reconciliation window instead of inventing success or failure.

I put rate limits at the provider boundary, with a bounded worker pool and a per-provider or per-merchant budget where required. On a documented 429, I honor Retry-After or exponential backoff with jitter; the queue absorbs the delay while age and backlog remain visible. I would avoid unbounded retries and set a deadline after which an attempt needs explicit review. The client sees a stable attempt ID and status throughout.”

Follow-up: “When is a retry safe?” When the same operation identity is preserved and the provider guarantees or reconciliation confirms that repeating it cannot create another charge.

reconciliationbounded workersRetry-Afterbackpressure
SWE8

“What telemetry would help you debug one delayed or double-charge report?”

“I would correlate the API request, payment attempt, outbox event, queue message, worker attempt, and provider receipt with stable IDs carried in structured logs and trace spans. A trace shows where time was spent—request validation, database commit, outbox publish, queue wait, provider call, and reconciliation. Logs capture state changes and redacted error categories; they must not expose card data or secrets.

Metrics answer whether this is isolated: unknown-outcome count, duplicate-key conflicts, outbox and queue age, provider 429 and timeout rates, retries, and time from acceptance to final status. I would alert on a sustained breach tied to a service objective, and treat any confirmed duplicate charge as an immediate incident. For an individual report, the durable attempt and provider receipt are the source of truth; a missing trace must not erase the outcome.”

Follow-up: “Where do the IDs go?” Put low-cardinality categories in metrics; keep individual attempt and correlation IDs in traces and structured logs.

trace correlationstructured logsqueue ageprovider receipt

09 · Senior Software Engineer · technical writing

Make the state machine and ownership boundaries easy to verify.

SWE9

“How would you document the payment state machine?”

“I would start with an explicit list of states and allowed transitions. The example below has created, queued, processing, retry_wait, unknown_outcome, succeeded, and failed_terminal. A transition records who makes it, what evidence is required, and whether it can be retried. Terminal states cannot silently reopen. Every accepted attempt must remain queryable by its stable ID.”

  • created → queued: API transaction commits the attempt and outbox event.
  • queued → processing: worker claims the attempt; duplicate deliveries observe the same record.
  • processing → succeeded or failed_terminal: provider receipt proves the final outcome.
  • processing → retry_wait → queued: a known retryable failure is delayed and retried under the same key.
  • processing → unknown_outcome → succeeded/failed_terminal: a timeout is resolved by provider lookup or reconciliation evidence.

Follow-up: “What guards these arrows?” A conditional database update checks the expected prior state and attempt version; the transition and its evidence are stored together.

explicit statesallowed transitionsevidence per transitionterminal states
SWE10

“How would you structure the design document so responsibilities and invariants are clear?”

“I would open with the contract: inputs, idempotency-key scope, status response, and what a client should do after a timeout. Then I would list the core payment invariants separately: one logical attempt per key and payload, no second charge on replay, every final state backed by evidence, and unknown outcomes reconciled rather than guessed. Next comes the state table above, with allowed transitions and the owner of each transition.

The API owns validation and attempt creation; the database owns durable identity and transitions; the outbox publisher owns reliable dispatch; the worker owns execution and retry scheduling; the provider adapter owns provider-specific idempotency and status lookup; reconciliation owns unresolved outcomes. I would give authorization its own section—who may create, view, or refund a payment—because it is a distinct policy with separate checks and tests. Finally I would document failure scenarios, telemetry, and the exact acceptance tests for each invariant.”

Follow-up: “How do you keep the document from becoming stale?” Put executable contracts and transition tests in the repository, link them from the design, and update both when the behavior changes.

contract firstcore invariantscomponent ownerauthorization section

Delivery checklist

Sound senior without overclaiming.

A senior answer is not a pile of impressive nouns. It makes the system's promises explicit, shows where those promises are enforced, and explains what evidence would change the next decision.

What “the invariant I would protect” means

An invariant is a condition that must remain true before, during, and after a change. In a rollout, I might say: “Every accepted run is tied to exactly one version, and every external side effect is authorized and recorded before we call it successful.”

That sentence gives the interviewer something concrete to test. It tells them what state must be durable, which boundary owns the rule, and what must happen if the deployment is interrupted. Other useful rollout invariants are: “a rollback must not lose accepted work,” “a canary cannot expand without comparable telemetry,” and “an approved action cannot silently change its recipients or parameters.”

S1

A reusable senior-level answer shape

1. Name the invariant. What must stay true for users and the business?

2. Name the control. Where is it enforced: routing, the API, the worker, the database, or the provider boundary?

3. Name the evidence. Which logs, metrics, traces, receipts, or tests prove the control worked?

4. Name the decision rule. What threshold pauses, rolls back, retries, or asks for review?

5. State your boundary. Separate what you personally built from what you would design or verify in a new environment.

Plain-English translation: “Here is what must not break, here is where I stop it from breaking, here is how I know, and here is what I do when the evidence turns red.”

S2

Example: a stronger rollout answer

“The invariant I would protect is that every accepted run has a durable owner and a pinned version, so a deploy cannot make an in-flight task ambiguous. I would build one immutable candidate, validate it in a separate environment, and expose it to a small canary before expanding traffic.

During the canary I would compare the candidate with the current version on p95 latency, error rate, successful task completion, cost, and any safety or policy failures. Logs explain individual failures, metrics show whether the population is drifting, and traces connect one run from retrieval through model call, policy check, tool call, and final receipt.

I would define the action before rollout: for example, stop expansion on a sustained latency or error breach, and roll back immediately for a confirmed unsafe side effect. If the provider timed out after accepting an action, I would reconcile by the stable action ID rather than blindly retry. I would not claim this was production experience unless I had actually operated it; I would describe the design and then connect it to the closest system I personally built.”

invariantcontrol boundaryevidencedecision rulehonest boundary

Say this

  • Invariant: “The condition I need to remain true is…”
  • Control: “I enforce that at the API/worker/database boundary by…”
  • Evidence: “The durable record and metric I would inspect are…”
  • Failure: “The failure case I would test is…”
  • Ownership: “In my experience, I personally built…”
  • Uncertainty: “For the rest, I would validate the assumption by…”

Avoid this

  • Vague: “We make it reliable” without naming the failure.
  • Absolute: “Exactly once” without a reconciliation story.
  • Unmeasured: “The canary is healthy” based only on HTTP 200.
  • Unscoped: “The metric improved” without denominator, window, or guardrails.
  • Overclaimed: presenting a proposed architecture as a shipped feature.

Personalize before the interview

Replace the generic example with one real story: context (what was changing), your action (which boundary you owned), invariant (what had to remain true), failure (what went wrong or could have gone wrong), evidence (how you measured it), and lesson (what you would do differently). The goal is not to sound like a textbook. It is to make your systems thinking easy to verify.

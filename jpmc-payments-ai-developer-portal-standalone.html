Q3 · Safe execution for an external agent The core design question ~2:00

A client's AI agent wants to call our payments APIs through the portal. How do you make that safe?

Resist listing controls. Give a model — every action is typed, bounded, attributable, and reversible-or-confirmed — then hang the controls on it.

“I'd separate four properties and make each one enforceable in code, not in a prompt.

Typed. Every action is a schema with a declared effect class — read, write, money-moving — and the agent can only reach what the schema exposes. Discovery returns schemas, never raw endpoints.

Bounded. Per-call result caps so an agent can't exfiltrate a ledger by accident; rate and cost budgets per credential; idempotency keys required on anything that moves money, so a retry is safe by construction.

Attributable. Every invocation is a ledger row with the client, the credential, the agent, and the inputs — and provenance on the instruction that caused it, so ‘the client's agent did it’ and ‘the client did it’ are distinguishable after the fact.

Reversible or confirmed. Anything irreversible defaults to a dry run that returns exactly what would happen; execution requires an explicit confirm, and past a threshold, a human in the client's own approval flow. Forced or overridden actions are audited with a reason.

That's the model I run today for agents editing a shared codebase — the same four properties, with file locks, a sandbox, and a secrets guard as the controls. For payments the controls change; the properties don't.”

If they push

“Prompt injection — a client's own data tells the agent to move money.”
The boundary has to be stronger than the model: instructions from data are never authority; authority comes from the credential and the typed schema. Say it that way, then point at the turn-provenance stamps as the mechanism you built for exactly that ambiguity.
“Who's accountable when the agent is wrong?”
The credential holder — which is why attribution has to be complete and why the confirm step exists. You can only be accountable for what you could have inspected.

Q5 · Evaluation and release gating for AI Responsibility 5, verbatim ~1:30

How do you decide an AI feature is safe to release? What does your evaluation practice look like?

“Three layers, and the important property is that none of them trusts a claim.

First, completion requires evidence: what was run, what the result was, how it was verified, which files changed. A bare ‘done’ is reopened automatically.

Second, every plan closes through two independent evidence families — a code-truth audit where only citations to real source or test files count and the paths have to resolve, and then a graded acceptance rubric where the grader is structurally prevented from being the author or anyone in the author's spawn lineage.

Third, the guards are themselves tested: a mutation probe deliberately breaks the thing a guard protects and confirms the guard fails — because a guard that has never failed is a guard you have not tested.

Release is a green-only branch behind a periodic gate; when it goes red, the first real red freezes as the candidate and fixes land on top of it by path, so you converge instead of re-cutting at a moving tip. For an AI feature specifically I'd add what I don't have today — a held-out scenario suite with a human-graded baseline, re-run on every model or prompt change.”

If they push

“How do you stop the evaluation from being gamed by the thing being evaluated?”
Grader independence is enforced in code, not by convention: the eligibility check resolves the rubric's author and refuses any session in that lineage. Then say the residual: an independent grader can still be lazy, which is why cards need concrete evidence per criterion.

Q10 · Onboarding & credential journeys Responsibility 4 ~1:00

What does a good secure onboarding journey look like for a client integrating with our APIs?

“Sandbox first, and the sandbox has to be the same contract as production — a different behaviour in sandbox is a bug you ship to the client. Part 5 · if they whiteboard

An agent-ready developer portal in five moves

If Steven asks about architecture outside the coding exercise, talk in this order; each move maps to something you have built, so every claim survives a follow-up.

1. A capability registry, not a doc site. Every API operation is registered once as a typed action — schema, effect class, auth scope, idempotency requirement, examples — and the OpenAPI spec, the human docs, the SDKs and the agent tool definitions are all generated from it. One source; nothing can disagree. (Papercusp: the tool catalog + OpenAPI from the route registry + the derived-truth rule.)

2. Discovery by intent. An agent asks for “refund a partially settled payment” and gets the two or three actions that fit, with guidance on when each applies — hybrid lexical + semantic search over the registry, fused by rank. (tools:find.)

3. Context assembly. Before an agent acts, one call assembles what it needs: the client's workspace state, integration progress, open incidents, recent calls — bounded, with the agent able to project only the fields it wants. (coord:orient + projection + state cells.)

4. Safe execution. The four properties from Q3 — typed, bounded, attributable, reversible-or-confirmed — enforced in the execution path, with dry-run as the default for anything irreversible and a client-side approval hook past a threshold. (hooks, sandbox, confirm/force with audit.)

5. Evaluation and gating as infrastructure. A scenario suite per action, rubric-graded with an independent grader; a green-only release gate; a ledger of every invocation so any failure replays. (rubrics/scorecards, green-checkpoint, tool_invocations.)

Then the sentence that shows judgement: “The order matters — the registry is the leverage, because everything else is generated from it. If I could only build one thing in the first quarter, it's that.”

04 · Whiteboard this

From a product request to a reviewed change.

  1. 1. Clarify outcome
  2. 2. Define contract
  3. 3. Split bounded tasks
  4. 4. Execute + inspect
  5. 5. Integrate + verify
  6. 6. Release + observe

Proposed practice: agree on acceptance criteria and API/data contracts first. Parallelize independent modules after the contract is stable. Give each task a named owner, a narrow write scope, explicit dependencies, and a verifiable stopping condition. Keep integration ownership with one engineer.

Task: Add the invoice-review API for a single property.
Read first: existing authorization, API errors, and audit conventions.
Allowed changes: invoice API/service and their tests.
Dependencies: approved request/response contract and schema.
Acceptance:
- Authorized reviewers can view invoices for their assigned property.
- Cross-property access is rejected by the server.
- Stale review updates fail without overwriting a newer decision.
- Retrying the same review request creates one effective transition.
Verify: unit + database-backed API tests; report commands and results.
Stop and escalate: a shared contract or unrelated schema must change.

Keep task-specific facts in the task, stable conventions in the repository guidance, and enforceable restrictions in permissions and tooling. Review the diff and test results yourself. A second agent can help find defects; human ownership and independent checks still matter.

How to measure the improvement

Establish a baseline for comparable work. Measure time from ready-to-start to accepted delivery, reviewer effort, rework, escaped defects, and operating cost. Report sample size and task mix. More agents or generated lines do not establish faster delivery.

05 · Hypothetical interview exercise

Design an invoice-review workflow for multiple hotels.

Prompt: A hotel controller needs staff to review imported invoices without duplicates, conflicting decisions, or access to another property’s financial data. Explain the feature design, then how you would use coding agents to implement it. This is a practice scenario, not a claim about M3’s internals.

  1. Clarify the accounting workflow.

    Who imports, reviews, approves, and posts? Can a user act across properties? Which system owns the invoice? What happens when an accounting period closes? Ask the domain owner to define correction and approval rules before implementation.

  2. Model explicit states and authorization.

    Consider received → needs review → approved/rejected → posted, subject to business rules. Store tenant/property, source identifier, version, and audit history. Authorize every operation on the server using the authenticated user’s property access.

  3. Handle retries and conflicting updates.

    Use a unique source key for import deduplication. Bind request idempotency to tenant, operation, and payload. Use a transaction for related database changes and a concurrency token for stale updates. Resolve a conflict explicitly instead of silently overwriting someone’s decision.

  4. Make downstream posting recoverable.

    If posting crosses a system boundary, commit a durable work item with the local decision. A worker retries delivery; a receiver with idempotency support avoids duplicate effects. If the receiver cannot deduplicate, reconcile ambiguous outcomes before retrying. Show pending and failed states to the operator.

  5. Split implementation by ownership.

    After agreeing on the API contract: one agent handles the API/service, another the Angular review screen, and another independently develops adversarial tests. Give schema changes one owner. An engineer resolves integration conflicts and reviews the combined behavior.

  6. Verify business effects.

    Exercise duplicate imports, simultaneous reviewers, forbidden property access, timeout after a downstream commit, rounding boundaries, and closed-period behavior. Release to a small agreed cohort and monitor duplicates, reconciliation exceptions, error rate, and review completion time.

Stack detail: EF Core supports optimistic concurrency tokens and surfaces stale updates for the application to handle. A unique-key conflict on insertion is a separate case. Microsoft: concurrency conflicts.

06 · Answer aloud before opening

Twelve questions to rehearse.

These are practice questions inferred from the role. They are not a reported M3 interview script. Use the answer beats to organize your own evidence.

Q01Match autonomy to task clarity.

How do you decide whether to use an agent?

Reveal answer beats

I look for a clear contract, useful context, bounded permissions, and a checkable result. A contained refactor or regression test can fit well. An unresolved product decision, a sensitive migration, or a change I cannot meaningfully review needs more human work first. I also compare setup and review effort with the cost of doing the task directly.

Your evidenceGive one real example where using an agent would have added overhead.

Q02Dependencies before concurrency.

How do you coordinate parallel agents?

Reveal answer beats

I separate independent work from shared decisions, agree on interfaces, assign ownership, and cap concurrency at our ability to review and integrate. Isolated branches/worktrees can contain edits; shared-tree work needs explicit coordination. Neither approach resolves incompatible assumptions by itself. Shared schema changes and integration have named owners.

Your evidenceUse the edit-collision example from Q4; distinguish your actual setup from a proposed M3 workflow.

Q03A compact implementation contract.

What makes a good prompt or agent-ready task?

Reveal answer beats

It gives the goal, relevant files, constraints, examples, acceptance criteria, verification commands, and escalation conditions. I ask for observable results and a concise change report. If the agent repeatedly guesses the same missing detail, I repair the task or interface rather than continually correcting the final answer.

Your evidenceShow a task before and after one real failure.

Q04Trace behavior through the diff.

How do you review AI-generated code?

Reveal answer beats

I start with the requirement and changed trust boundaries, then inspect correctness, authorization, data integrity, error paths, performance, dependencies, and maintainability. I run tests that could fail for the bug we care about and inspect what actually executed. I do not accept the author’s test summary as independent proof.

Your evidenceExplain the test that would catch a plausible but incorrect implementation.

Q05Challenge their shared assumptions.

What if the agent writes both the implementation and the tests?

Reveal answer beats

Both can agree on the same mistake. I derive acceptance checks from the requirement, preserve existing regression coverage, and include negative and boundary cases. I verify that tests execute and detect a known bad behavior. Another agent may propose adversarial cases, but the acceptance rule should remain independent of the generated solution.

Your evidenceUse Q2’s positive-control story if it matches your contribution.

Q06The instrument can be wrong.

Tell me about a difficult debugging problem.

Reveal answer beats

Use the liveness-check incident: explain the reported symptom, how you discovered the check itself was invalid, and the independent observation that established reality. Finish with the detector or contract change and its validation. Keep the actual incident separate from other examples of the same failure pattern.

Your evidenceOpen Answer Bank Q3 and rehearse it in 90 seconds.

Q07Define the invariant with the business.

How would you protect financial correctness?

Reveal answer beats

I ask the domain owner what must remain true: permitted property access, approval authority, valid accounting periods, balanced entries where applicable, and a traceable correction process. I represent those rules explicitly and test transaction boundaries, concurrency, retries, and amount precision. Generated code receives the same review as any other change.

Your evidenceExplain which checks run in the UI, API, and database, and why the server is authoritative.

Q08Constrain the action path.

What would you do if an agent exposed a secret or followed malicious text?

Reveal answer beats

I would stop the affected execution, determine what was accessed or transmitted, and follow the incident process, including credential rotation when needed. Preventive controls include scoped credentials, approved data use, restricted tools, and treating retrieved documents as untrusted input. Instructions are useful guidance; enforcement must survive a bad instruction.

Your evidenceDescribe an actual boundary from your bank without claiming controls you have not validated.

Q09One useful workflow, then teach it.

How would you introduce these practices to an existing team?

Reveal answer beats

I would pair with engineers on a small real task, show the full loop from specification to review, and create a short reusable example. We would discuss both a success and a failure. I would track review effort and rework, invite feedback, and expand only after the workflow helps people deliver reliably.

Your evidenceSupply a real human mentoring story; keep a proposed rollout in future tense.

Q10Measure accepted work and its cost.

How would you prove agents improve delivery speed?

Reveal answer beats

I would compare similar tasks using a baseline and include specification, execution, review, integration, and rework time. I would track defects and change failures alongside lead time. With a small sample, I would describe the limits instead of claiming a universal multiplier. The gain needs to survive real review and operation.

Your evidencePrepare a measured result if you have one; otherwise show the measurement plan.

Q11Name the cost and the follow-up.

How do you balance speed with technical debt?

Reveal answer beats

I distinguish a deliberate temporary shortcut from an unclear design. I can accept a bounded compromise when its effect is visible, it does not violate a critical invariant, and we have an owner and a trigger for revisiting it. Agent-generated abstractions and extra dependencies still need to justify their maintenance cost.

Your evidenceGive an example of something you chose not to generalize.

Q12Diagnose the candidate and contain impact.

What happens when a release fails?

Reveal answer beats

I identify the actual release candidate and failing check, preserve useful evidence, and decide whether to fix forward or roll back. Schema compatibility and external effects shape that decision. I re-run the necessary checks on the candidate being shipped and verify the user-visible behavior afterward. Then I improve the detector or process that missed the problem.

Your evidenceUse Q1 or N9, with an exact before/after and a truthful outcome.

08 · A proposed starting plan

Learn, ship, then make the practice repeatable.

  1. Days 1–30: understand the system and deliver one change.

    Meet engineering and product partners, trace a real user workflow, learn the existing .NET/Angular patterns and approved AI tools, baseline delivery friction, and ship a bounded change with tests and review.

  2. Days 31–60: pilot a repeatable agent workflow.

    Choose a recurring task, define the task template and evidence requirements, pair with a few engineers, and measure total effort and defects. Fix the biggest context or review bottleneck.

  3. Days 61–90: expand what the evidence supports.

    Document useful prompt patterns, examples, and review expectations. Add parallelism where dependencies permit it. Share results and limitations with the team and decide together what to adopt next.

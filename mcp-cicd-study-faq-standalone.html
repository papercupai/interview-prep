Part 1 · from the papercusp deep-dive

MCP details

D1What MCP is

MCP (Model Context Protocol) is a JSON-RPC protocol between an LLM client/host (Claude Code, Claude Desktop, Cursor, codex, omp…) and any number of servers. A server exposes three primitives:

  1. Tools — advertised via tools/list (name + description + JSON-Schema args); the model invokes via tools/call.
  2. Resources — addressable read-only content (resources/list / resources/read).
  3. Prompts — server-defined templates (prompts/list / prompts/get) that clients surface in their UI.

That's the whole job: standardize discovery, invocation, and transport so a capability is written once and any MCP-speaking client can use it. It adds no intelligence — it turns "a function on some server" into "a tool the model can see and call," with the schema traveling alongside.

The spec also defines client-side primitives the server can invoke: sampling (server asks the client's model for a completion), roots (client tells the server which dirs are in scope), elicitation (server asks the user for input mid-operation).

How deep does the spec go? Three layers with a normativity gradient.

LayerNormativity
Wire: JSON-RPC framing, lifecycle, transports, OAuth, cancellation, progress, pagination, notificationsFully normative
Primitive shapes + control model (who initiates each)Shapes normative; behavior guidance SHOULD-level
Host behavior: UI, rendering, when the model runs, context managementExplicitly out of scope — "servers provide, hosts decide"
D2The three primitives and who controls them

The primitives can carry the same data; what distinguishes them is who initiates:

  • Tools — model-controlled. The model decides mid-turn to call one. Verbs.
  • Resources — application-controlled. The host app (or user through it) attaches content. Documents.
  • Prompts — user-controlled. The user explicitly invokes a template. Commands.

This control model is the deepest the spec reaches into app behavior — and it only says who should initiate, never how it looks.

D3Resources vs just reading a file

For a same-box agent with a Read tool: almost no difference — that's honest. Resources exist for where "point the model at a file" fails:

  1. No shared filesystem. A resource works over the wire — Claude Desktop/Cursor has no path to your box and no PG connection. papercusp://docs/index is an address that travels.
  2. Most aren't files. audit:recent is a live SQL query rendered at read time. The file alternative = materializing projections to disk.
  3. Access control travels with it. bearer → Principal → capability check → workspace-bound transaction, same trust boundary as tools.
  4. User-attachable without a model turn — pickers, @-mentions, zero tokens on discovery/retrieval.

"But a tool could return the same data!"

True. The difference is control + affordances, not capability:

  1. No model in the loop. Tool retrieval requires a model turn that decides to call it (tokens + nondeterminism). A resource is fetched by the app before the model ever runs.
  2. Tool definitions cost context on every turn (they ride tools/list into the prompt). Resources are enumerated by the host UI and cost nothing until attached.
  3. The read-only/addressable/subscribable contract is what hosts build UX on. A host may freely re-fetch a resource; it can NEVER safely re-invoke a tool on its own (might send an email). The primitive split tells the host "this one you may fetch whenever."
  4. The user chooses the context, not the model.

Analogy — HTTP GET vs RPC

Everything GET does could be a POST, but GET-with-a-URL is what makes links, caches, bookmarks, and browsers possible. Resources are MCP's GET; tools are its RPC.

Concrete app example ("Papercusp for Cursor"): IDE connects → resources/list (incl. templated per-harness URIs) → renders an @-mention picker in its own chrome → user picks "sheets — open issues" → IDE resources/reads and attaches the JSON like a pasted file → model runs ONCE with context already present. Live variant: a sidebar panel subscribes and refreshes on updated — a pure-UI feature, no model involved.

D4resources/subscribe

Design keystone: the update notification carries no content — it's an invalidation ping.

  1. Negotiated up front: server must declare resources: { subscribe: true } at initialize. (Separate from listChanged = the catalog changed vs updated = one URI's content changed.)
  2. → resources/subscribe {uri} … ← {} — server now remembers who watches what (protocol session state).
  3. Change detected (fs watcher, DB trigger, poll — server's business, spec silent) → ← notifications/resources/updated {uri} (no id, fire-and-forget, no payload).
  4. Client re-reads when it cares: resources/read {uri} (re-applies capability check). resources/unsubscribe stops it.

Why notify-then-fetch: content may be big, client may not want it now, rapid changes coalesce into cheap pings, authz enforced on every fetch.

Real-world example: attached file staying fresh in a chat client — attach file:///repo/TODO.md, client subscribes, you edit it in vim, server's watcher fires updated, client silently re-reads and swaps the attachment. Without it the model reasons over a stale copy and nobody knows.

Papercusp parallel: notifySyncInvalidate → SSE ping → useSyncQuery re-fetch is the same pattern, richer (typed queries, targeted invalidation). MCP's version is the interop edition; our MCP server doesn't implement subscribe (no consumers).

D5Prompts and slash commands

Spec-defined half

  1. initialize handshake; server declares prompts capability.
  2. prompts/list → entries: name, description, declared arguments (name/description/required — strings only, no JSON Schema, unlike tools).
  3. prompts/get {name, arguments} → server renders at that moment and returns {description, messages: [{role, content}]} (content can be text/image/embedded resource).

Client-defined half (Claude Code's choices, not spec)

  • Minting /mcp__<server>__<name> slash commands from the list; the autocomplete UI; positional argument parsing.
  • Inserting the returned messages as the user's turn and triggering a model turn. The spec defines how to fetch the template, not what fetching is for. (Spec docs mention slash commands only as an example surfacing.)

Papercusp examples: prompts/agent/role.ts (agent:role — takes a role arg, returns the canonical persona md as a message; exports papercusp's personas to external clients), dispatch/framing.ts, operator/scanner.ts. Note: papercusp's user-saved prompts (saved_prompts in PG) become slash commands via file projection (.claude/commands/<name>.md, $CODEX_HOME/prompts/) — not MCP prompts — because two file formats cover all three CLIs.

D6JSON-RPC

A tiny, transport-agnostic RPC message format (spec 2.0 fits on ~2 pages). Exactly three shapes:

// Request — method + params + caller-chosen id
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "work_items:claim", "arguments": { "id": "WI-1234" } } }

// Response — same id back; result XOR error
{ "jsonrpc": "2.0", "id": 7, "result": { "content": [ { "type": "text", "text": "…" } ] } }
{ "jsonrpc": "2.0", "id": 7, "error": { "code": -32602, "message": "invalid params" } }

// Notification — NO id ⇒ no reply expected, none allowed
{ "jsonrpc": "2.0", "method": "notifications/tools/list_changed" }

Three properties do all the work:

  1. id correlation — replies match by id, not order ⇒ many in-flight requests, out-of-order answers, both directions multiplexed on one pipe. This is what makes MCP bidirectional.
  2. Notifications — fire-and-forget; the mechanism behind every MCP push (list_changed, resources/updated, progress, cancellation).
  3. Transport-agnostic — message shapes only; something else carries the bytes (stdio lines, HTTP bodies, WebSocket frames).

vs REST: REST = resources + URLs + HTTP verbs + status codes; JSON-RPC = named procedures, address in the params, errors in-band (-32601 method not found, -32602 invalid params, + app codes).

Layering for papercusp: JSON-RPC envelope grammar → MCP method vocabulary → papercusp's ~550 tools behind tools/call. server.ts is handlers registered per JSON-RPC method (server.setRequestHandler(CallToolRequestSchema, …)).

D7Typing JSON Schema on top

JSON-RPC itself has NO type system — no IDL, no way to declare what a method accepts/returns (contrast gRPC/protobuf, REST/OpenAPI; OpenRPC exists but is niche and unused by MCP).

MCP fills the gap one layer up: every tools/list entry carries an inputSchema (full JSON Schema) — that's what lets a model construct calls. Prompts don't get this (string args only) — one reason tools are the richer primitive.

Papercusp's pipeline — zod plays two roles

  1. Declaration: tool args = a zod schema (Standard Schema V1; adapter defaults to zod 4's native z.toJSONSchema).
  2. Wire advertisement: at tools/list, toArgsJsonSchema (define-tool.ts) → strip $schema → advertisedArgsSchema → sanitizeToolSchema → the inputSchema you see on every mcp__papercusp-su__* tool. (HTTP projection also runs flattenForOpenAi; computeOutputEligibility derives an output schema.)
  3. Enforcement: JSON Schema is advisory for the model; incoming tools/call args are validated against zod at dispatch (standardValidate, + fuzzy-enum matching, structured invalid-args).

Earned scar

A trailing .transform() in an args schema is fatal to the whole catalog — JSON Schema can't represent it, the conversion runs at module import AND in the tools/list handler, so one bad schema breaks tool discovery for every client, as an anonymous un-greppable error. Rule: refinements fine; do transforms in the handler, or terminate with .pipe(<schema>).

D8Transports and how client and server agree

The dissolving insight

Tools are not individually callable things. One connection per server; ONE fixed method (tools/call) invokes every tool on it. A tool has no URL/transport of its own — it's a menu row. Restaurant analogy: the menu has no directions to each dish; you tell the same waiter "number 7" over the table you're already at.

Agreement happens at three layers.

Layer 1 — transport: chosen by CONFIG, not negotiated.

The client is told how to reach each server, out-of-band. Config entry = command (spawn → stdio) or url (→ streamable HTTP). Settled before the first message. Both transports are normatively specified in the spec's Transports section; custom transports permitted (anything carrying bidirectional JSON-RPC). Papercusp uses three: stdio (StdioServerTransport), HTTP (_mcp-handler.ts; psu → :9071 proxy), and the degenerate case — in-process dispatch(): same handlers, zero wire.

  • stdio (specified): client spawns server as subprocess; newline-delimited JSON-RPC, client→stdin / server→stdout; no embedded newlines; stderr for logs; stdout for nothing else. Clients SHOULD support stdio — the baseline.
  • Streamable HTTP (specified): ONE endpoint URL; each client message = HTTP POST with the JSON-RPC body; client MUST send Accept: application/json, text/event-stream (⇒ the 406 papercusp's proxy returns without it); server may reply with plain JSON or an SSE stream; server may mint Mcp-Session-Id at initialize, client echoes it thereafter; optional GET opens a standalone SSE stream. (Deprecated predecessor: "HTTP+SSE", 2024-11-05.)

Layer 2 — version + capabilities: the initialize handshake (in-band).

  1. Client sends protocol version (date-based, e.g. 2025-06-18) + its capabilities (sampling? roots? elicitation?) + identity.
  2. Server replies with the version it will speak + its capabilities (tools{listChanged}, resources{subscribe,listChanged}, prompts, logging).
  3. Client acks notifications/initialized. Both sides use only declared features (e.g. tools:find fires list_changed only "on a listChanged-capable transport").

Layer 3 — per-method contracts: discovered, not negotiated.

tools/list → names + inputSchemas; prompts/list → arg declarations; resources/list → URIs + mime types. Self-describing at runtime (no shared .proto) — exactly what a model-driven caller needs. Full exchange, all on one pipe:

→ initialize                      → tools/list
← capabilities                    ← [{name, description, inputSchema}, …]
→ notifications/initialized       → tools/call {name, arguments}
                                  ← result content

How does the client RECEIVE a server notification?

Per transport, in the spec:

  • stdio: free — the pipe is full-duplex; the server writes one more stdout line; client sorts arriving lines by shape (id ⇒ response; no id ⇒ notification).
  • HTTP: built from held-open responses parsed as SSE (data: <one JSON-RPC message>), in two places: (1) a POST's own response may be an event stream (progress… then the response); (2) the standalone GET stream carries unsolicited pushes like resources/updated. Optional both sides (405 if unsupported). Dropped-stream recovery: SSE event id:s + reconnect with Last-Event-ID for replay.
D9The stateful claim

"MCP is stateful, unlike HTTP" = session state, not data storage. Classic "HTTP is stateless": each request self-contained, server remembers nothing between requests. MCP defines a long-lived session both sides carry memory of:

  • Negotiated session — initialize fixes version + capabilities once; everything after is interpreted against it.
  • Server push — notifications mid-session (impossible in plain HTTP).
  • Subscriptions — server remembers who watches what.
  • In-flight request tracking — progress tokens, cancellation by id.
  • Server-initiated requests — sampling/elicitation need a standing two-way channel.

The tell: MCP-over-HTTP must fake a session on top of stateless HTTP (Mcp-Session-Id + SSE) — a stateful protocol tunneled over a stateless one. What it does NOT mean: MCP persists nothing; papercusp's actual state is in Postgres, protocol-irrelevant. Live papercusp example: the trimmed tool surface — tools:find activates tools mid-session via list_changed; which tools your session sees is evolving session state.

D10The full layer stack and TOON
carrier:     stdio | HTTP+SSE                      ← spec (moves bytes)
envelope:    JSON-RPC                              ← spec (call/response/notification grammar)
vocabulary:  MCP methods + result shapes           ← spec (initialize, tools/*, resources/*, …)
contracts:   JSON Schema per tool                  ← MCP's typing layer (zod-generated in papercusp)
payload:     TOON / CSV / MD inside content[0].text ← papercusp's own, invisible to layers below

TOON (Token-Oriented Object Notation) never touches JSON-RPC — it lives inside the one opaque string MCP gives you:

{ "jsonrpc": "2.0", "id": 9, "result": {
    "content": [ { "type": "text",
        "text": "format: toon\nrowCount: 8\nrows[8]{tool_name,n,last_used}:\n  locks_acquire_resource,\"49\",…" } ],
    "_meta": { } } }
  • Why: JSON repeats every key per row; TOON renders uniform arrays as CSV-style rows under one header while staying JSON-lossless (types/nulls/nesting). csv/tsv ~6% denser but lossy; md display-only.
  • Machinery: serializeToolResponse (libs/generic/tooldef/src/serialize-result.ts) — the SINGLE place format logic lives; every transport calls it so the contract can't drift.
  • Contract: compact payloads self-identify (format: <fmt> prefix; JSON unmarked); envelope fields (nextCursor, degraded) go to _meta, never the tabular body; lossless guarantee = silent fallback to JSON labeled _meta.formatFallback; format is client-negotiable ('compact' = server picks).
  • Same move as gzip in an HTTP body: the protocol defines the container, never inspects the bytes.

C1CI vs Delivery vs Deployment
TermOne-sentence definitionThe tell
Continuous IntegrationEvery change merges to the shared mainline frequently (≥ daily) with an automated build + test verifying each one.About merging often with automated verification — not owning a Jenkins server.

The point of all three: shrinking batch size. Small frequent changes are easier to test, review, diagnose, and roll back — almost every practice downstream of that one idea.

Why CI at all? It solves integration risk compounding over time — week-old branches make merging an event. CI inverts it: each merge trivial, each failure points at a small recent change. Green main = the real deliverable (anyone can branch/deploy/debug from known-good). Tradeoff: demands fast tests + small PRs — a 45-min pipeline quietly kills CI (people batch changes to avoid the wait).

Trunk-based vs GitFlow: default trunk-based (small merges to main, features behind flags) — you can't continuously integrate 3-week branches. GitFlow fits when maintaining multiple released versions in parallel (on-prem, mobile release trains). Tradeoff: trunk shifts the burden to flags + test discipline; flags become debt to retire.

C2The reference pipeline

For a containerized web service — commit this shape to memory and route every answer through it:

Trigger        → Lint + Build   → Test            → [PACKAGE]        → Staging        → [PRODUCTION]    → Observe
push/PR main     fail fast,       unit ∥ integ,     build image ONCE   deploy +         canary            metrics gate,
                 cache deps       parallel shards   tag by commit SHA  smoke/e2e        5% → 100%         auto-rollback

The two bracketed stages are what interviewers listen for: one immutable artifact promoted through environments, and a guarded, reversible path into production.

What makes a pipeline good (priority order)

  • Fast (<~10 min or people bypass it)
  • Deterministic (same commit same result; flakes destroy the signal)
  • The only path to production (no side-door deploys or the guarantees mean nothing)
  • Reproducible + versioned (definition in the repo, reviewed like code)

Speed vs thoroughness resolves by staging the checks — fast unit gate on PR, deeper e2e post-merge/pre-deploy.

GitHub Actions sketch (concepts, not syntax to memorize): test job (checkout, setup w/ dep cache, npm ci && lint && test) → package needs test, main only, docker build -t app:${{github.sha}} (immutable tag, never :latest) → deploy-staging needs package, environment: staging (scoped secrets), deploy + smoke → deploy-prod needs staging, environment: production (manual approval = Continuous Delivery), deploy --canary.

C3The four principles

  1. Build once, deploy many

    Artifact built exactly once, tagged immutably (commit SHA), promoted through staging to prod. Rebuilding per environment = you never tested what you shipped.

  2. Fail fast, cheap checks first

    Lint/compile in seconds before minutes of tests — a cost-sorted funnel.

  3. Config from the environment, not the artifact

    Same image everywhere; env vars / config service / secrets manager supply differences. This is what makes promotion possible.

  4. Deploys reversible by default

    Canary/blue-green, health-checked; rollback = "point back at previous known-good artifact," not "revert and rebuild under pressure."

C4The three-beat answer formula

Candidates fail on abstraction, not knowledge — reciting definitions proves nothing; CI/CD is operational and the interviewer probes whether you've lived it. Fix is mechanical: memorize one reference pipeline, then:

  1. Define it in one sentence. Crisp; proves vocabulary, buys a beat.
  2. Ground it in a concrete pipeline. "In practice, on a service I worked on…" — walk the relevant slice.
  3. Name one tradeoff or failure mode, unprompted. "The catch is…" — the strongest senior signal there is.
Flat (canary)

"Release to a small % of users first."

Strong (canary)

"Route ~5% of real traffic to the new version watching error rate + latency vs old; promote 5→25→100 with auto-rollback on regression. Catch: needs real observability and traffic volume — on a low-traffic internal service a canary tells you nothing, so there I'd prefer blue-green with a good smoke test."

All three require tolerating two versions at once — really a statement about backward-compatible APIs and schemas, usually the harder problem than traffic mechanics.

C6Zero downtime checklist

A checklist, not one trick:

  • Rolling/blue-green/canary so healthy capacity always serves;
  • Health checks — readiness, not just liveness, so the balancer routes only to ready instances;
  • Graceful shutdown — drain in-flight requests on SIGTERM;
  • Backward-compatible changes — API + schema work for both versions during overlap.

The last is the one teams miss: platform solves the mechanics; compatibility is per-change discipline no tool enforces.

C7Rollback

A bad change reached production — ordered by preference:

  1. Flag off — seconds, no deploy (if it shipped behind a flag).
  2. Redeploy previous artifact — point prod at the last known-good image tag. This is why immutable SHA-tagged artifacts matter: rollback is a pointer move, not a rebuild.
  3. Fix forward — only when rollback is impossible (irreversible migration ran, data written in the new shape).

Worth saying: the rollback path is a product requirement, not emergency improvisation — tested, and the canary gate does it automatically on metric regression. What breaks "just roll back" is DB migrations → expand/contract.

C8DB migrations — expand, migrate, contract

Rule: schema changes must be backward compatible with currently running code (two versions run during any deploy; rollback must stay possible). Renaming a column becomes:

  1. Expand: add the new column; deploy code that writes both, reads old.
  2. Migrate: backfill old → new; deploy code that reads new.
  3. Contract: once nothing references the old column, drop it — a separate, later change.

Migrations run as a versioned pipeline step (Flyway/Liquibase/framework-native) — never by hand. Tradeoff: one logical change = three deploys, and the contract step gets forgotten → zombie columns; track contraction as explicit follow-up work.

C9Feature flags

Flags decouple deploy from release — code ships dark; turning it on is a runtime decision, reversible in seconds, targetable to 1% of users. They make trunk-based development safe (half-done work merges but stays off) and are the fastest rollback mechanism that exists.

Tradeoff: every flag doubles the state space; dead flags rot into "which of these 200 is load-bearing?" Flags need owners and expiry dates — scaffolding, not architecture.

C10Speeding up a slow pipeline

First measure — stage timings; usually one or two dominant stages. Then, typical payoff order:

  1. Cache dependencies (npm/pip/Maven; Docker layer cache with deps before source) — minutes for near-zero effort;
  2. Parallelize — lint ∥ unit ∥ integration; shard the big suite across runners;
  3. Run only what changed — monorepo affected-target detection (Nx, Bazel, Turborepo);
  4. Tier the suite — fast gate on PR, deep e2e post-merge/nightly;
  5. Fix the tests — e2e that sleep, rebuild fixtures, or hit real networks are usually the true whale.

Tradeoff: "run less" trades confidence for speed — post-merge e2e occasionally catches a break after it lands, fine only if revert is cheap and fast.

Papercusp adds a sixth

See P2: when the pipeline is red, freeze the candidate so recovery cost doesn't scale with the outage. Nobody expects that one.

C11Flaky tests

Treat flakiness as a sev-2 against the pipeline itself — it erodes the only thing a pipeline produces: trust in the green.

  • Detect: track pass/fail per test across runs; fails-then-passes on retry of the same commit = flaky by definition.
  • Quarantine: non-blocking lane immediately, but with a ticket + owner — quarantine without follow-up is deleting tests slowly.
  • Fix the class, not the instance: flakes cluster — time/timezones, test-order dependence, real network calls, race-prone async waits, port collisions.

Tradeoff: blanket auto-retry ("3×, pass if any pass") hides real intermittent production bugs. Retry is a detection mechanism, not a fix.

C12Secrets and supply chain

Secrets

Never in the repo, never in the artifact, never in logs. Injected at deploy/runtime from a secrets manager (Vault, AWS SM, CI encrypted store), scoped per environment (staging job physically can't read prod). Modern answer interviewers like: no long-lived secrets at all — OIDC federation exchanges the CI job's identity token for short-lived cloud creds (GH Actions → AWS is canonical). Residual risk: the pipeline itself — anyone who can edit a secret-holding workflow can exfiltrate; workflow changes need review, third-party actions pinned.

Supply chain

  • Scan continuously: SAST on source, dependency audit on lockfiles, image scan on the container — as gated stages with severity thresholds;
  • Pin everything: lockfiles, digest/SHA-pinned base images and CI actions (a moving latest is an unaudited change vector);
  • Least-privilege runners: build jobs read-only tokens; only deploy jobs get deploy creds, per environment;
  • Provenance: sign artifacts + SBOM so prod can verify "this image came from this pipeline at this commit."

Tradeoff: blocking on every low-severity CVE gets bypassed within a month — block critical/high with an expiring-exception process; report the rest.

C13GitOps

Desired state lives declaratively in git; an in-cluster agent (Argo CD, Flux) continuously pulls and reconciles reality to match — instead of the pipeline pushing deploy commands. Concretely: CI builds + pushes the image, then commits the new tag to a config repo; the agent notices and rolls out. Wins: audit-by-git-log, rollback-by-revert, drift detection, cluster creds never leave the cluster.

Tradeoff: deploys become eventually consistent — pipeline green no longer means "it's live"; close the loop by watching the agent's sync/health. And it mostly presumes Kubernetes.

C14Testing the pipeline itself

Three layers:

  1. Pipeline definition is code in the repo — changed via PR, reviewed, exercised by the very PR that changes it;
  2. Staging is a rehearsal of production — same deploy mechanism, so every staging deploy tests the deploy tooling, not just the app;
  3. Post-deploy verification is a pipeline stage — smoke tests + metric checks so "deployed" = "verified serving correctly," not "script exited 0."

Also rehearse the failure path: a rollback that has never been run is a rollback that doesn't work. Same for restores from backup.

C15DORA metrics

Four metrics, two balancing pairs —

  • Throughput: deployment frequency (how often you ship) · lead time for changes (commit → running in prod).
  • Stability: change failure rate (% of deploys causing incident/rollback) · mean time to restore.

The finding worth citing

Elite teams are better on all four at once — speed and stability aren't a tradeoff, because small frequent changes are individually safer and easier to reverse. That's the thesis of the whole topic in one sentence.

P2The frozen-candidate story

This is the one to go three questions deep on

(C16 beat 3.) It lands under C10 speeding up a slow pipeline, C11 flaky/trust, and C14 testing the pipeline itself.

The failure — a feedback loop, not a slow test. The affected-test selector derives its diff base from main. main only fast-forwards when the gate is green. So the moment the gate went red, the diff base froze: every subsequent run read more files as affected → runs got longer → more likely to time out or be preempted before rendering a verdict → main stayed red. Recovery cost was coupled to the age of the outage, which is why it never self-healed.

Measured at worst: 4,572 changed paths against a base 3,868 commits behind — 75 workspaces, 105 test tasks. The same tree scoped honestly to the three files that had changed: 5 workspaces, 23 tasks.

The diagnosis — two facts had been conflated: "tests are certified through this commit" and "main fast-forwarded to this commit." They come apart constantly; the outage that motivated the work was failing on typecheck, a non-test leg, so the tests were never what broke and we re-ran the whole inflated radius anyway. The selector wasn't imprecise — it was being asked the wrong question.

The fix, two halves

  1. A test-certified watermark

    A git ref that advances only when the affected-test leg passes in full at that sha; the selector diffs against that instead of main. A ref rather than a DB row or state file: git's own primitive for a commit pointer, atomic, no extra dependency inside the gate's isolated checkout, and it cannot drift from the objects it names.

  2. Freeze-and-converge

    On the first real red, that exact commit is pinned as the candidate and one repair queue opens against it; fixes land on top. Each repair run re-runs only the tests still failing, plus the tests whose related files changed since the freeze — anything that passed at freeze time and hasn't been touched is inherited, not re-executed. Green = that delta is green ∧ the broken list is empty.

    The alternative — re-cutting at the current tip after each fix — is a treadmill: every new cut re-admits the whole sweep and imports breakage faster than fixes land.

Beat 3, the tradeoffs — volunteer these

  • Promotion never narrows; only selection does. Each verdict is rendered against its predecessor's anchor, so coverage composes back to the last green pin. It's inheritance, not omission — that's what keeps "the whole candidate is certified" true.
  • It fails safe in exactly one direction. Any branch that can't positively verify its anchor falls back to the full run. A silently narrowed run would hand you a false green, and that is the one outcome that must be impossible.
  • You are testing a slightly stale anchor. The frozen thing is the verdict anchor, not the work — the head being repaired converges forward onto the live branch when it's safe — but it is a real cost and naming it first is the senior move.
  • This is a sixth item for C10's list. The book's list is cache → parallelize → run-only-what-changed → tier → fix the tests. Ours adds: when the pipeline is red, freeze the candidate so recovery cost doesn't scale with the outage.

R1What the word means — and the trap in it

“Guardrail” is an umbrella covering at least three mechanisms that work completely differently. Noticing that is most of the signal.

The vocabulary trap When a vendor or an interviewer says “guardrails,” the default mental image is often the narrow one — input/output content filtering — because that is what the products carrying the name do: AWS Bedrock Guardrails (content filters, denied topics, PII, contextual grounding), NVIDIA NeMo Guardrails (programmable topical and safety rails), Guardrails AI (output schema validation), OpenAI's Agents SDK (input/output guardrails whose tripwires halt a run).

So ask, then widen: “Do you mean content-level guardrails, or the whole boundary including what the agent is authorized to execute? I think of it as a stack, because the content layer can't hold on its own.” That single move reframes the conversation onto ground where you have real examples.

Three adjacent words people conflate

Guardrails are runtime — they act during execution. Evals are pre-deployment measurement — they tell you how often something happens, they don't stop it. Alignment is training-time disposition. A candidate who uses them interchangeably signals they have only read about this.

The one sentence to have ready

“Does this guardrail change what the model is likely to do, or what it is able to do?” Most guardrail discussions get muddy because someone is treating a system prompt as a security control. Naming that distinction before you are asked reads as experience rather than reading.

The corollary — they are depth, not substitutes. You want the probabilistic layers because they catch things early and cheaply, and the deterministic ones because the probabilistic layers will eventually be wrong. “We handle that in the prompt” is one layer. “The prompt reduces attempts, authorization makes success impossible, and the audit trail bounds the damage if I'm wrong about the second one” is three, and it's the answer that ends the line of questioning.

R5The strongest pattern — correct by construction

Take one deep dive here if offered. The design idea generalizes well beyond this system.

The problem. The capability envelope deliberately exempts superuser callers — the stated reasoning is that the policy is a safety net precisely where there is no human, and a supervised session should keep native ergonomics. Defensible. But it was keyed to the wrong predicate for one population: some autonomous agents need superuser identity for unrelated reasons (the coordination channel is identity-gated), so they inherited an exemption meant for supervised humans.

Two attempted fixes did not hold, and both failures are instructive. A client-side tool ban is advertisement, not enforcement — a denied tool stays reachable through the generic dispatch route. And the envelope's grain is the capability, not the tool: the verb that needed blocking shares its capability with dozens of others, including ones the agent needs to record its own progress. Revoking that capability would have blocked the target and stranded the work.

The fix — a differently shaped gate rather than a hole in the existing one. A launch-declared confinement that runs before the exemption, with two structural guarantees:

  1. It cannot be bypassed by privilege, because it never receives privilege

    The decision function takes no context, no role, no superuser flag. There is no privilege check to get wrong, and no later edit can quietly add one — a guard test pins the module's imports.

  2. It cannot widen, because it has no allow dimension

    The structure carries a deny list and nothing else. The worst a malformed or hostile confinement can do is deny more.

Status — say this unprompted

Implemented, tested and wired into the dispatch seat — and never used. Zero confinements have ever been declared; the store holds one empty per-workspace container. The directed pair is the case this was built for, not a case we run. Offer it as a design pattern and a worked analysis of why three simpler approaches failed — never as a deployment. Presenting a motivating design case as an operating one is the precise overclaim R6 is about, and it is an easy one to make about your own system.

The transferable idea

Remove the dangerous vocabulary rather than policing its use. Most guardrails are correct if configured correctly; this one is correct because the incorrect state is unrepresentable. That is a meaningfully higher bar, and the same move was reached independently elsewhere in the codebase for runtime-created tools — which is decent evidence it's a real pattern and not a one-off.

One more detail worth carrying: the matcher folds both spellings of a tool name onto one key, because clients mangle the canonical form. A denial that caught only one spelling would be bypassable by typing the other — the same class of hole as the client-side ban it replaced.

R6How do you know a guardrail actually works?

This is the follow-up most candidates have no answer to, and it maps to the Answer Bank's G6. A guardrail that has never failed is a guardrail you have not tested.

Our answer is a mutation probe. Deliberately break the thing the guard protects, assert the guard catches it, restore. Three details make it more than a slogan:

  • A no-op mutation is refused outright. If the mutation changed nothing, every guard looks weak — a false verdict from a probe that never ran. So “did I actually mutate anything” is checked before the verdict is trusted.
  • Positive controls are mandatory. Before believing “the guard caught it,” run the same instrument against something known to be present. If the control also comes back empty, the instrument is broken, not the subject.
  • Destructive subjects run against shims that log what would have been deleted rather than deleting it — you assert on intent, with real execution gated behind an explicit sandbox flag.

The generalizable point, and it is a good one

Across this system the recurring bug class is an instrument that measured nothing but reported a clean result — a test filter matching zero tests, a search truncated before the real hit, a query against a column whose values can never match, a typecheck that compiled zero files. Every one produces output identical to genuine success. So the guardrail on your guardrails is: never accept a negative result from an instrument you haven't positively controlled.

Part 5 · Fundamentals asked cold

Design and Python fundamentals

F1"What is the difference between cohesion and coupling?"

The 20-second answer

Cohesion is how strongly the things inside one module belong together, i.e. whether it has one clear job. Coupling is how much one module depends on others, i.e. how far a change in one forces changes elsewhere. You want high cohesion and low coupling, because together they mean a change lands in one place instead of rippling across the codebase. The two pull in the same direction: grouping the things that change together raises cohesion, and that is usually what cuts the dependencies between groups.

CohesionCoupling
DirectionInward — within one moduleOutward — between modules
You want itHighLow (loose)

Smell when it's wrongA utils.py junk drawer; a class whose methods share no fieldsReaching into another module's internals; two services sharing one database schema; shotgun surgery (one change, ten files)
Classic ladder, worst → bestcoincidental → logical → temporal → procedural → communicational → sequential → functionalcontent → common (global) → external → control → stamp → data

The one-line test

Pick a plausible requirement change and count how many modules it touches. Many modules touched means low cohesion, high coupling, or both. The terms come from Larry Constantine's structured-design work (Yourdon & Constantine, Structured Design, 1979). Keep the ladders in reserve for when the interviewer probes; don't lead with them.

The senior add-on: implicit coupling is the dangerous kind

An import is coupling you can see: tooling knows about it, and a compiler or test will complain. The coupling that causes incidents is implicit: two pieces of code that must change together with nothing enforcing it. A real example from this site: the nav list in sitenav.js and the build list in build-standalone.sh both enumerate every page. Adding a page to only the first silently broke a link on all 36 standalone pages. The standard fixes apply: derive one list from the other, which removes the coupling, or add a check that fails when they disagree, which makes it explicit. If they want more depth, Page-Jones' connascence gives finer-grained vocabulary for the same idea.

In a system-design round

The idea scales up unchanged. Microservices pay off only with high cohesion inside each service and loose coupling between them. A shared database, synchronous call chains (temporal coupling), and shared mutable config each quietly reintroduce coupling across service boundaries.

F2"What is Python's hashing algorithm?"

The 20-second answer

It depends on the type. For str and bytes, hash() uses SipHash, a keyed 64-bit hash. PEP 456 adopted SipHash-2-4 in Python 3.4, and 3.11 switched to the faster SipHash-1-3. The key is random per process, so the same string hashes differently on every run. That is deliberate: it stops an attacker from crafting keys that all collide in one dict (hash-flooding DoS). Numbers hash by modular arithmetic, and tuples, frozensets, and plain objects each have their own scheme.

TypeHow it hashesConsequence worth saying out loud
str, bytesSipHash-1-3, keyed by a 128-bit random seed chosen at startup. A str caches its hash after the first call.Not stable across runs. Setting PYTHONHASHSEED=0 (or any fixed value) makes it stable, for example to reproduce an ordering bug.
int, float, Fraction, DecimalThe value reduced mod P = 261−1, a Mersenne prime, on 64-bit builds. A fraction m/n hashes as m·n−1 mod P.hash(1) == hash(1.0) == hash(Fraction(1)) == hash(Decimal(1)), so d[1] and d[1.0] are the same key.
-1Mapped to -2−1 means "error" in the C API, so nothing may hash to it.
inf, nanhash(inf) == 314159; NaN hashes by identity (since 3.10)Two different NaN objects are two different dict keys.
tupleCombines the element hashes with an xxHash-derived mix (since 3.8)Hashable only if every element is.
frozensetAn order-independent combination of the element hashesEqual sets hash equal, whatever the insertion order.
Plain objectsDerived from the object's address (id), bit-rotated by 4 because allocations are 16-byte alignedIdentity semantics until you define __eq__/__hash__.

How a dict uses it

CPython dicts and sets use open addressing, not chaining. The low bits of the hash pick a slot. On a collision, the probe sequence is j = (5*j + 1 + perturb) mod 2i, with perturb shifted right by 5 bits each step. That feeds the hash's high bits in gradually, so every slot is eventually reachable. Since 3.6 a dict is a compact index array plus a dense entries array, which is why dicts keep insertion order.

The contract, and the classic gotchas

  • a == b must imply hash(a) == hash(b). The reverse need not hold, because collisions are allowed.
  • Defining __eq__ without __hash__ sets __hash__ = None, which makes instances unhashable. That is deliberate: the inherited identity hash would now break the contract.
  • Mutable built-ins (list, dict, set) are unhashable. If a key's hash changed after insertion, the dict would look in the wrong slot and "lose" it.
  • For a custom class, return hash((self.x, self.y)) over the same fields that __eq__ compares, or use @dataclass(frozen=True).

Don't confuse it with hashlib

hash() is a fast, non-cryptographic function built for hash tables. hashlib (SHA-256, BLAKE2, …) is for integrity and content addressing: stable across runs and machines, deliberately slower, and collision-resistant. Never persist hash() output or use it as a cache key across processes.

Verified, not remembered

Checked on Python 3.14.7 on 22 Sep 2026: sys.hash_info.algorithm == 'siphash13', modulus == 2**61 - 1, inf == 314159, hash(-1) == -2, the numeric-equality identity above, and identity-based NaN. Two runs of hash('boom') gave different values until PYTHONHASHSEED=0 made them match. Running python -c "import sys; print(sys.hash_info)" is the fastest way to show an interviewer you know where the ground truth lives.

60-second answer

“I would pause when the next step needs authority the agent does not have, or a product or risk decision only a person can make. AO6 · Recovery“How can you tell an agent is busy but making no progress?”

60-second answer

“I would examine the sequence of attempts and results. If the agent keeps making the same failing call, I want to know whether it learned anything, changed its approach, or eventually succeeded. A corrected request followed by success is useful recovery. Repeated failures with no later success are a signal to inspect the task, arguments, and dependency health.

Papercusp has a detector for that pattern. It groups calls by agent and tool, keeps successful calls as well as failures, and looks for failure episodes that remain unresolved. Its delivery code notifies the agent first and can escalate a repeated finding to its leader. I would use the alert to ask why progress stopped, then turn the confirmed cause into a test or a tool improvement.”

Concrete implementation: the detector uses at least three failures within ten minutes, excludes episodes followed by success, and gives a recent failure episode time to settle before reporting it. It also reports changed arguments and fallback tools as evidence.

failure → failure → success is recovered. failure → failure → failure → no recovery can merit investigation after the settling interval.

Do not overclaim: this is a narrow behavior detector. An outage or confusing tool contract can produce the same symptom as poor agent judgment. The source also detects typed goal changes within a declared intent; it does not infer semantic drift from arbitrary prose. Current production alert rates were not measured here.

AO7 · Evaluation“How do you evaluate the agent's behavior before expanding its use?”

60-second answer

“I would use representative tasks with explicit success criteria and a few deliberate difficulties: ambiguous instructions, a failed tool, stale context, or a denied action. Evaluation versus monitoring: scoring representative runs helps judge a proposed change. Observing actual runs tells you whether the same behavior holds in use. Capturing a trace does not automatically grade it, and an LLM judge's explanation can be wrong. Mark missing or unexercised evidence explicitly and check outcomes independently.

Another behavior record: the governed-action decision ledger records action, policy posture, outcome, and policy reason where available. Its emitter excludes superuser calls and reads and writes best-effort. That record explains the policy applied to an action; it is not a transcript of the agent's reasoning or a complete record of every run.

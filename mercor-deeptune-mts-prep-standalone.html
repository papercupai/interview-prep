01 · What they are actually hiring for

Environment engineering, not model theater

Build

High-fidelity applications

Reproduce the behavior and workflows of professional software: realistic state, permissions, data, latency, errors, and task surfaces.

Expose

Agent-operable interfaces

Give an agent a bounded tool API, MCP server, or computer-use surface with clear schemas, observable side effects, and useful failures.

Measure

Rollouts and task calibration

Separate model failure, task-design failure, and environment failure. Tune difficulty from evidence instead of turning every bad rollout into a model verdict.

Own

Production infrastructure

Carry a system from incomplete specification through implementation, tests, deployment, debugging, and delivery without hiding uncertainty.

One sentence to remember

“I build the environment, the interface the agent uses, and the measurement loop that tells us whether a failure belongs to the agent, the task, or the environment.”

02 · Round 1 · 60 minutes

Tell one system deeply, with Papercusp as the case study

Deep-dive narrative problem → architecture → decisions → evidence aim for 12–15 minutes, then discuss

Choose the part of Papercusp where your personal contribution is clearest: reliable multi-agent software work in a shared repository.

  1. Problem. Agents can make useful changes, but they crash, lose context, race on files, misread empty results, and declare completion without enough evidence.
  2. Architecture. A local operator backbone stores plans, work items, locks, events, memory, tests, and release state; agent sessions connect through MCP; the UI observes the same durable state.
  3. Key decisions. Pull-based claims instead of hand assignment; locks at the write boundary; checkpoints outside the model context; evidence-gated completion; green-only promotion.
  4. Failure. Tell one concrete incident where a check, monitor, or agent believed the wrong object, then show how you measured the root cause.
  5. Testing. Explain the recurrence guard: positive controls, mutation probes, zero-match refusals, liveness checks, or a release test that would fail if the class returned.
  6. Redesign. Name what you would simplify or change today, and the cost or risk that made the original choice reasonable.

“The system I want to walk through is Papercusp, an operator control plane for reliable agent work. The constraint was not launching one agent; it was coordinating many ordinary agent sessions against one shared codebase while preserving ownership, context, and evidence. I’ll show the planes, trace one work item, then explain a failure and the guard that prevents it from returning.”

Do not lead with

“It has hundreds of tools,” “it is autonomous,” or a list of frameworks. The interview signal is your reasoning about boundaries, failure modes, and guarantees.

What to say while drawing
BoxInterview explanation
Agent sessionAn ordinary worker. It can be restarted, lose context, or make a wrong claim; the platform cannot rely on its memory or honesty.
Operator planeThe durable control surface: work is claimed, tools are bounded, events wake the right session, and the UI reads canonical state.
EnvironmentThe thing being operated or trained against: application state, data, APIs, permissions, and observable side effects.

04 · Papercusp demo

Demo the reliability loop, not the dashboard

1 · Start

Give it a small goal

“Add a feature to this repository and prove it works.” Show how the goal becomes a plan and a work item rather than remaining a chat request.

2 · Claim

Show ownership

Let an agent pull the next eligible item. Explain why atomic claims and leases matter when workers can overlap or disappear.

3 · Operate

Show the agent boundary

Open the MCP/tool surface. Point to bounded inputs, useful errors, explicit truncation, and the distinction between a tool call being accepted and its effect being verified.

4 · Recover

Show context outside the model

Use a checkpoint or wake. Explain that a restarted session can recover the goal, current state, next action, and evidence without trusting the old context window.

5 · Verify

Show a test that could fail

Run the focused test and, if available, a positive-control or mutation check. Emphasize that a command which matched nothing or measured the wrong object is not evidence.

6 · Finish

Show evidence-gated completion

Close with files changed, tests run, result, and verification method. Then distinguish implementation from release promotion and rollback.

“The demo is intentionally small. I want to show the control loop: an agent receives durable work, acts through an accountable interface, survives interruption, and cannot call the work complete without evidence. That is the same reliability problem Deeptune has around an environment and its rollouts.”

06 · Likely Round 1 questions

Rehearse answers that expose technical depth

Q1 · Architecturedraw, then trace

Why is Papercusp more than an agent launcher?

Because launching is the easy edge. The durable system owns work identity, scheduling, locks, context recovery, verification, and release state. An agent is a replaceable worker; the operator plane is the system of record.

Q2 · Reliabilityname one failure

Tell me about a time a monitor or test gave a confident but wrong answer.

Use the wrong-object pattern: an empty result or green exit can mean absence, a blind instrument, or a check that never ran. Explain the measurement that distinguished the hypotheses and the guard you added afterward.

Q3 · Agent interfaceshow the contract

What makes a tool or MCP server good for agents?

Typed inputs, bounded output, explicit errors, clear side effects, idempotency where possible, and evidence that names the object actually changed. The contract must help an agent recover from partial failure rather than merely expose an endpoint.

Q4 · Evaluationmodel vs task vs environment

How would you tell whether a failed rollout was the model's fault?

First validate the task contract and fixture. Then verify the environment's state transitions and observability with a control or replay. Only after those are sound should the residual failure be attributed to the policy/model. The judge must be independent enough not to certify its own blind spot.

Q5 · Scopepractical judgment

What would you build first for a new environment?

A narrow vertical slice: one realistic task, one agent interface, one seeded dataset, one observable success condition, one failure fixture, and one replayable evaluator. Expand only after that slice is reliable; otherwise you scale ambiguity and debugging cost.

Q6 · Ownershipbe specific

What did you personally build?

Separate your own design and implementation from platform capabilities, team contributions, and model-assisted work. Name the files, interfaces, tests, and decisions you can defend. If you do not know a detail, say what you would inspect rather than filling the gap with confidence.

07 · Round 2 · maximum 8 hours

Hackathon operating plan

The constraint

You are being evaluated on functionality, technical decisions, code quality, testing, reliability, scope management, and understanding—not on how much surface area you can produce. Treat the eight hours as a budget with a stop condition.

Suggested time budget
TimeWorkExit condition
0:00–0:30Read the brief twice. Extract actors, state, inputs, outputs, success criteria, and explicit non-goals.You can state the smallest useful vertical slice.
0:30–1:00Write a short design note: architecture, data model, API/tool boundary, risks, and test strategy.One diagram and one decision log exist.
1:00–4:45Build the vertical slice end to end. Keep the happy path working while adding one meaningful failure path.A reviewer can run the core workflow.
4:45–6:15Add tests for the contract, boundary cases, failure recovery, and the most likely regression.Tests fail for a deliberate broken behavior, then pass after the fix.
6:15–7:00Harden: validation, error messages, idempotency, timeouts, seeded data, and a clean setup path.Fresh setup and rerun are plausible.
7:00–7:30Review the diff and remove unrelated complexity. Record tradeoffs and known limitations.No unexplained files or accidental secrets remain.
7:30–8:00Write the README and final walkthrough. Run the exact commands a reviewer will use.The submission explains what works, how to test it, and what you would do next.

Build first

One complete path

Input → core behavior → persisted or observable result → test. A narrow complete system demonstrates more judgment than five disconnected features.

Protect the score

Make failure visible

Validate early, return useful errors, keep setup deterministic, and include one test that proves the evaluator can detect a wrong result.

  • The README starts with the run command and a 30-second explanation.
  • The design names the main tradeoff and the alternative you rejected.
  • The test suite covers the happy path, an edge case, and a failure or recovery case.
  • AI-assisted code has been read, simplified, and verified by you.
  • Known limitations are explicit; unfinished ideas are not presented as shipped functionality.

08 · Questions for Deeptune

Ask questions that reveal how the work is actually done

Environment contract

What is the contract between an environment, the agent interface, and the evaluator? Which parts are standardized across environments?

Rollout diagnosis

When a rollout fails, what instrumentation helps distinguish model, task, and environment failures?

Realism

How do you decide which product behaviors, data distributions, latency, permissions, and failure modes must be high fidelity?

Engineering ownership

How much of the role is building a new environment versus improving shared tooling, deployment, QA, and replay infrastructure?

“What does a great environment engineer make easier for the next person on the team?”

03 · Your opener

The first ninety seconds, written out

Zara opens conversationally. This is the one answer worth having word-perfect, because it seeds every focus area so later answers become callbacks rather than fresh stories.

Say this in the first minute

I'm an engineer who builds machine-learning systems and then owns them in production, which in my experience is where most of the actual work is. The clearest example is a pricing and matching service — a gradient-boosted model served from a long-lived Python process, sitting behind an entity-resolution step that decides whether two records from different sources describe the same thing. The modelling was the small part. The hard parts were keeping the training path and the serving path from drifting apart, and making the process survive weeks without anyone touching it. More recently I've built a platform that coordinates many AI coding agents working on one codebase at once, which is where the security thinking comes from: model output is untrusted input, so those agents get a list of allowlisted operations rather than raw access to a filesystem or a database. The habit I'd want you to take from all of it is that I treat an incident as a detector failure — the thing worth fixing is usually whatever should have caught it and didn't.

Three focus areas, and this opener seeds all three by design: Python systems, then production ownership, then security. Practise it at ninety seconds so each later answer is a callback.

04 · Python systems engineering

A long-lived process, not a script

The focus area says systems, and that word is doing the work. They are not asking whether you know list comprehensions; they are asking whether you have run Python as a process that stays up — where memory grows, the GIL matters, a dependency resolves differently in production, and nobody restarts it for you. Answer everything in that register.

“Tell me about a Python system you have built.”

The one I'd use is a pricing and matching service: a gradient-boosted model served out of a long-lived Python process, in front of an entity-resolution step that decides whether two records from different sources are the same thing. The interesting part was never the model — it was that the process has to stay correct for weeks. Feature code and training code have to agree, or you get skew that no test catches because each half passes its own.

The shape I'd defend: the model is loaded once at start, not per request; the feature transformation is one module imported by both the training path and the serving path, so they cannot drift; and the boundary is typed, so a malformed row fails at the edge with a useful message instead of becoming a NaN that silently moves a price.

“asyncio, threads, or processes?” Likely

I pick by where the time actually goes, and I say which I measured. IO-bound and high-concurrency — fan-out to APIs, a database, a queue — is asyncio: one thread, explicit await points, and the cost is that a single blocking call poisons the whole loop. Blocking libraries that I cannot replace go in a thread pool via run_in_executor, which is really just quarantining them. CPU-bound work — inference, big transforms — goes to processes, because the GIL means threads buy nothing there.

The sentence I'd add unprompted, because it is the one that gets probed: the GIL is not a throughput problem for IO, it is a throughput problem for CPU. Getting that backwards is the classic tell.

Evidence Your own platform runs an embedded Postgres and several sidecar processes, so the process-vs-thread choice is one you have actually made.

“How do you keep a Python service reproducible?”

Pinned, hashed dependencies and a lockfile committed — not a floating requirements.txt. The same interpreter version everywhere, declared rather than inherited from whatever the host happens to have. And the environment built in the image, not on the box, so ‘works on my machine’ stops being a category of bug.

What I'd flag as the underrated one: import side effects. A module that opens a connection or reads config at import time makes the process order-dependent and almost impossible to test. Construct at call time, wire at the edge.

If they ask about typing

Say you use type hints as an enforced boundary, not decoration — checked in CI, strictest at the edges where untrusted data arrives. The honest limit, which is worth volunteering: hints are erased at runtime, so they are a development-time guarantee and you still validate real input at the boundary.

05 · Production ownership

What you did after it broke

This focus area is almost always scored on one thing: do you distinguish a mitigation from a fix. Restarting the thing, widening a timeout, retrying around a broken call and deleting the bad input are all mitigations. They stop the bleeding and they leave the trap armed. Say that distinction out loud and then give an example where you did the second one.

“Tell me about something that broke in production.”

My best one is a storage bug in the desktop app. The webview persists localStorage as a SQLite database in WAL mode. A long-lived reader kept the write-ahead log from ever checkpointing, so it grew — to about 127 gigabytes, for roughly a megabyte of actual data. Something like a hundred-thousand-fold.

The mitigation is obvious and wrong: delete the file. That returns the disk and guarantees a recurrence. The fix was to checkpoint at boot, before the webview reopens the database, because that is the one moment no reader is holding it. Then the part I care about more — I asked what should have caught it. Nothing was watching that file's size at all, so the detector was the real defect, and a disk-growth check was the actual deliverable.

Evidence The WAL incident is on the Answer Bank with the numbers.

“How do you stop bad code reaching production?”

A release gate that owns the decision rather than a human remembering. In mine, the promotion branch only ever fast-forwards to a commit that passed the suite — nothing else can push it. A red suite holds the branch, and the deploy carries auto-rollback, so the worst case is a short window rather than a bad build sitting there.

The consequence I'd be honest about, because it is the interesting trade-off: that gate is shared, so one person's red freezes everyone. That is a feature only if the team treats a red gate as everyone's job. If it becomes ‘not my tests’, the gate turns into a queue and people start routing around it.

“How do you decide what to be paged for?” Likely

Page on symptoms the user would notice, not on causes. CPU at ninety percent is not an incident; requests failing or a queue that stops draining is. And I treat a false alarm as a real bug in the alarm — if it fires and nobody acts, it has trained everyone to ignore the next one, which is strictly worse than not having it.

The trap in this area

Do not attribute a failure to “high load”, “low memory” or “thrashing” without naming a mechanism. Used swap and a big load average are not evidence on their own. If you tell an incident story, say what you measured that tied the symptom to the cause — that single habit reads as more senior than the story itself.

06 · Secure engineering

Make the bad thing impossible, not discouraged

For an AI/ML role this is mostly about untrusted input reaching powerful things — model output treated as a command, a prompt carrying data it should not, a tool surface that is too broad. The framing that scores: a convention nobody can enforce decays, so the goal is designs where the unsafe action is not expressible.

“How do you handle secrets?”

Never in the repository, and not only because of leaks — a secret in the tree ends up in every fork, every backup and every model's training context. Injected at runtime from outside the checkout, scoped to the one process that needs it, and redacted at the logging boundary rather than remembered about at each call site. If a credential does leak, rotation has to be routine, which means nothing can hardcode it anywhere.

“How do you give an agent or a client access to the system safely?”

Allowlisted capabilities instead of raw primitives. In my own platform the untrusted side cannot call the filesystem or the database directly; it calls named operations that are individually gated, so ‘what can this thing do’ is an enumerable list rather than a judgement call. The webview is treated as hostile territory on purpose — it gets a bridge, never the host.

Where that pays off is path handling. Rather than validating a path and hoping the check is airtight, the operation takes an identifier and resolves it against a fixed root, so a traversal has nowhere to express itself. Impossible by construction beats checked.

“What about the AI-specific risks?” Likely

Three I'd name. Prompt injection: anything a model reads is untrusted input, so model output must never be executed directly — it proposes an action, and the action is validated against the same allowlist a user would hit. Data leakage: prompts and traces are logs, so PII in a prompt is PII in a log, and it needs the same redaction and retention rules. And supply chain: a model, a dataset and a package are all third-party code, pinned and checksummed.

The one I'd volunteer as genuinely hard is tenant isolation in a shared vector store — a filter you have to remember to apply is a breach waiting for one missed query, so the tenant belongs in the key, not the WHERE clause.

Say the limit of your own claim

This focus area punishes overclaiming more than most. You have not run a formal threat-modelling process or a pen-test programme, and saying so costs nothing next to the concrete designs above. “Here is what I built, here is the class of attack it makes impossible, here is what I have not done” is the answer.

Drill 1 · Length-prefixed frame codec

A pipe or socket hands you arbitrary chunks. Reassemble whole messages from [4-byte length BE][1-byte type][payload] with struct.unpack_from, cap them at 16 MiB on the decoder — that is where the untrusted number arrives — and handle a frame split across chunks, several frames in one chunk, and a declared length that is a lie. The Python-specific half: slicing bytes copies, so the natural buf = buf[total:] per frame is accidentally O(n²). Use a memoryview plus an offset, and say why.

# You never see framing inside a single Python process — a queue hands you whole objects. You see it
# the moment bytes cross a process boundary: a subprocess pipe, a socket, a model-server sidecar.
# A stream gives you BYTES, not messages. The OS will hand you half a frame, or two and a half
# frames, and a decoder that assumes message boundaries works in dev and corrupts under load.
#
# Wire format:
#   [4B payload length, big-endian][1B type][payload]
# Big-endian because every other wire protocol is, and an endianness bug stays invisible until a
# length crosses 256. A 16 MiB cap so a corrupt or hostile length field cannot make the peer
# allocate a gigabyte — that cap is the secure-engineering half of this drill, and it belongs on the
# DECODER, where the untrusted number arrives, not only on the encoder.
#
# The Python-specific trap, and the reason this drill is not the JavaScript one:
# slicing bytes or bytearray COPIES. The natural line to write after consuming a frame is
#     self._buf = self._buf[total:]
# and it copies the entire REMAINING buffer, once per frame — accidentally O(n^2) over a long
# stream. It is invisible on a unit test with three frames and it melts under a real one. The fix
# is an offset plus a memoryview (which slices WITHOUT copying), compacting only occasionally.

# is an offset plus a memoryview (which slices WITHOUT copying), compacting only occasionally.

HEADER_BYTES = 5
MAX_PAYLOAD = 16 * 1024 * 1024
COMPACT_THRESHOLD = 64 * 1024

Frame = namedtuple("Frame", "type payload")


class FrameType:
    REQUEST = 1
    RESPONSE = 2
    ERROR = 3
    CANCEL = 4


def encode_frame(ftype, payload):
    """Encode one frame. `payload` may be bytes-like or a str (encoded UTF-8).

    Raises ValueError for a type that is not a single byte, or a payload over the cap."""
    if not isinstance(ftype, int) or isinstance(ftype, bool) or not 0 <= ftype <= 255:
        raise ValueError(f"frame type must be a byte, got {ftype!r}")
    body = payload.encode("utf-8") if isinstance(payload, str) else bytes(payload)
    if len(body) > MAX_PAYLOAD:
        raise ValueError(f"frame payload {len(body)}B exceeds {MAX_PAYLOAD}B cap")
    return struct.pack(">IB", len(body), ftype) + body


class FrameDecoder:
    """Accumulates bytes; returns every COMPLETE frame so far and keeps the remainder.

    Never returns a partial frame and never blocks waiting for one."""

    def __init__(self, max_payload=MAX_PAYLOAD, compact_threshold=COMPACT_THRESHOLD):
        self.max_payload = max_payload
        self._compact_threshold = compact_threshold
        self._buf = bytearray()
        self._start = 0          # everything before this offset is consumed but not yet reclaimed
        self.compactions = 0     # instrumentation, so the O(n^2) property is TESTABLE, not timed
        self.bytes_compacted = 0

    @property
    def pending_bytes(self):
        return len(self._buf) - self._start

    def push(self, chunk):
        """Feed arbitrary bytes. Returns a list of Frame. Raises ValueError on an over-cap length."""
        self._buf += chunk
        frames = []
        # A memoryview slices without copying, so the parse loop touches each byte once.
        view = memoryview(self._buf)
        try:
            start, end = self._start, len(self._buf)
            while end - start >= HEADER_BYTES:
                (length,) = struct.unpack_from(">I", view, start)
                if length > self.max_payload:
                    # Unrecoverable: the stream is desynchronised or the peer is hostile.
                    # Raising is correct — resyncing by scanning for a plausible header INVENTS
                    # message boundaries, which is how a corrupt stream becomes corrupt data.
                    raise ValueError(
                        f"declared frame payload {length}B exceeds {self.max_payload}B cap")
                total = HEADER_BYTES + length
                if end - start < total:
                    break  # partial frame: keep the bytes, wait for more
                # bytes(...) copies THIS payload out, which is required — the caller keeps it and
                # the buffer underneath is about to be reused. Copying each payload once is O(n);
                # copying the remaining BUFFER once per frame is the O(n^2) mistake.
                frames.append(Frame(view[start + 4],
                                    bytes(view[start + HEADER_BYTES:start + total])))
                start += total
            self._start = start
        finally:
            # Releasing before the `del` below is not optional: a bytearray with a live memoryview
            # export cannot be resized, and Python raises BufferError if you try. Worth naming out
            # loud — it is the failure people hit the first time they reach for memoryview.
            view.release()

        # Reclaim the dead prefix only when it is genuinely large, or when the buffer is fully
        # drained (in which case there is nothing left to move and the copy is free).
        if self._start and (self._start >= self._compact_threshold
                            or self._start == len(self._buf)):
            self.bytes_compacted += len(self._buf) - self._start
            del self._buf[:self._start]
            self._start = 0
            self.compactions += 1
        return frames
Drill 2 · Bounded concurrency with real backpressure

asyncio.Semaphore for the bound, a bounded asyncio.Queue for the rejection path — put_nowait raising QueueFull is the backpressure, and raising it synchronously at submit time is what lets the producer react. Then map_limit, which must keep input order while completing out of order. Volunteer the GIL boundary here: this shape is right for IO-bound work and wrong for CPU-bound, which needs a process pool. Knowing which one you are looking at is the thing being scored.

Skeleton · target ≈12 min
# "Python has a GIL" is not why this matters, and saying only that is the thin answer. Async work is
# cheap to START and that is the trap: asyncio.gather over 10,000 items opens 10,000 sockets, file
# handles or database connections at once. The answer is a bounded pool whose QUEUE is also bounded
# — an unbounded queue just moves the failure out of the connection table and into the heap, which
# is worse because it is invisible until the OOM killer arrives.
#
# Backpressure means the producer LEARNS it is too fast. A pool that silently buffers is not
# applying backpressure, it is hiding the need for it. Here the bounded asyncio.Queue is the
# admission ledger and put_nowait raising QueueFull IS the backpressure signal — raised
# SYNCHRONOUSLY at submit time, so the caller finds out immediately rather than in a callback.
#
# THE BOUNDARY SENTENCE, volunteered before you are asked:
#   IO-bound (HTTP calls, database round-trips, reading model shards off disk) -> asyncio, and this
#   pool is the right shape. The GIL is irrelevant because the thread is not holding it while
#   awaiting.
#   CPU-bound (tokenising, feature extraction, numeric work in pure Python) -> this pool is the
#   WRONG shape: the coroutines serialise behind the GIL and you have written a slow for-loop with
#   extra steps. Use concurrent.futures.ProcessPoolExecutor, or a library that releases the GIL
#   (numpy, a native tokeniser) in which case threads are fine.
# Knowing WHICH of the two you are looking at is the actual skill being scored.


class BoundedPool:
    """At most `limit` coroutines in flight, plus at most `max_queue` admitted and waiting.

    Construct inside a running event loop. Total admission capacity is `limit + max_queue`; one more
    submit than that raises asyncio.QueueFull rather than growing a queue nobody is watching."""

    def __init__(self, limit, max_queue=0):
        if not isinstance(limit, int) or limit < 1:
            raise ValueError("limit must be >= 1")
        if not isinstance(max_queue, int) or max_queue < 0:
            raise ValueError("max_queue must be >= 0")
        self.limit = limit
        self.max_queue = max_queue
        self._sem = asyncio.Semaphore(limit)
        self._slots = asyncio.Queue(maxsize=limit + max_queue)
        self.active = 0
        self.peak_active = 0

    @property
    def admitted(self):
        return self._slots.qsize()

    def submit(self, factory):
        """Admit or reject NOW, synchronously. `factory` is a zero-arg callable returning an
        awaitable — not an awaitable, so nothing is created for a job that gets rejected.

        Returns an asyncio.Task. Raises asyncio.QueueFull when the pool and its queue are both
        full; that exception is the backpressure the producer is supposed to react to."""
        # implement this — the contract is in the docstring above
        raise NotImplementedError("not implemented")

    async def _run_admitted(self, factory):
        try:
            async with self._sem:
                self.active += 1
                self.peak_active = max(self.peak_active, self.active)
                try:
                    return await factory()
                finally:
                    self.active -= 1
        finally:
            self._slots.get_nowait()  # free the admission slot even if the job raised

    async def run(self, factory):
        """Convenience: submit and await. Still rejects synchronously on a full queue."""
        return await self.submit(factory)

    Construct inside a running event loop. Total admission capacity is `limit + max_queue`; one more
    submit than that raises asyncio.QueueFull rather than growing a queue nobody is watching."""

    def __init__(self, limit, max_queue=0):
        if not isinstance(limit, int) or limit < 1:
            raise ValueError("limit must be >= 1")
        if not isinstance(max_queue, int) or max_queue < 0:
            raise ValueError("max_queue must be >= 0")
        self.limit = limit
        self.max_queue = max_queue
        self._sem = asyncio.Semaphore(limit)
        self._slots = asyncio.Queue(maxsize=limit + max_queue)
        self.active = 0
        self.peak_active = 0

    @property
    def admitted(self):
        return self._slots.qsize()

    def submit(self, factory):
        """Admit or reject NOW, synchronously. `factory` is a zero-arg callable returning an
        awaitable — not an awaitable, so nothing is created for a job that gets rejected.

        Returns an asyncio.Task. Raises asyncio.QueueFull when the pool and its queue are both
        full; that exception is the backpressure the producer is supposed to react to."""
        self._slots.put_nowait(None)  # raises asyncio.QueueFull — the whole point of the drill
        return asyncio.get_running_loop().create_task(self._run_admitted(factory))

    async def _run_admitted(self, factory):
        try:
            async with self._sem:
                self.active += 1
                self.peak_active = max(self.peak_active, self.active)
                try:
                    return await factory()
                finally:
                    self.active -= 1
        finally:
            self._slots.get_nowait()  # free the admission slot even if the job raised

    async def run(self, factory):
        """Convenience: submit and await. Still rejects synchronously on a full queue."""
        return await self.submit(factory)


async def map_limit(items, limit, fn):
    """Apply async `fn(item, index)` to every item with at most `limit` in flight.

    Results keep INPUT order regardless of completion order — the property people get wrong by
    appending to a list from inside the workers."""
    items = list(items)
    results = [None] * len(items)
    sem = asyncio.Semaphore(limit)

    async def one(index, item):
        async with sem:
            results[index] = await fn(item, index)

    await asyncio.gather(*(one(i, item) for i, item in enumerate(items)))
    return results
    # Worth saying: gather still materialises one coroutine per item up front, so this is fine for
    # thousands and wrong for millions. At that size you want BoundedPool fed from an iterator, so
    # the items themselves are also bounded — not just the concurrency.
Drill 3 · Invalidation coalescing

Many writes, one notification, carrying the latest value. Measure the window from the first dirty key, not the most recent — a debounce restarts its timer on every event, so the hottest key never flushes at all. Add a max-batch early flush so a burst is not also slow. Pure core, time passed in as an argument: no fake timers, and no event loop needed to test it.

class Coalescer:
    def __init__(self, window_ms, max_dirty=None):
        if window_ms < 0:
            raise ValueError("window_ms must be >= 0")
        if max_dirty is not None and max_dirty < 1:
            raise ValueError("max_dirty must be >= 1")
        self.window_ms = window_ms
        self.max_dirty = max_dirty
        self._dirty = {}  # key -> [first_ms, hits, value]

    @property
    def dirty_count(self):
        return len(self._dirty)

    def mark(self, key, now_ms, value=None):
        """Record that `key` changed. The newest value wins; the FIRST timestamp is kept."""
        entry = self._dirty.get(key)
        if entry is None:
            self._dirty[key] = [now_ms, 1, value]
        else:
            entry[1] += 1     # hits
            entry[2] = value  # last value wins
            # entry[0] deliberately untouched: the window is anchored to first-dirty

    def drain(self, now_ms):
        """Return and clear every key whose window has elapsed (or all of them, if at max_dirty)."""
        at_cap = self.max_dirty is not None and len(self._dirty) >= self.max_dirty
        due = [Due(key, value, hits, first_ms)
               for key, (first_ms, hits, value) in self._dirty.items()
               if at_cap or now_ms - first_ms >= self.window_ms]
        for item in due:
            del self._dirty[item.key]
        return due

    def next_due_ms(self, now_ms):
        """Milliseconds until the next drain is worth calling; 0 if now, None if nothing is dirty.

        This is what a real shell feeds to loop.call_later — one rearmed timer handle, not one
        timer per key."""
        if not self._dirty:
            return None
        if self.max_dirty is not None and len(self._dirty) >= self.max_dirty:
            return 0  # at cap: flush early, so a burst is not also slow
        earliest = min(entry[0] for entry in self._dirty.values())
        return max(0, earliest + self.window_ms - now_ms)
Drill 4 · Event-loop lag and an honest verdict

Percentiles by nearest rank, then a verdict. The finding worth stating: p99 over 100 samples is the sample a single 900 ms freeze gets dropped by, so carry a max leg as well as a percentile leg — and return unknown on zero samples, never healthy. The drill proves it both ways, including that statistics.quantiles interpolates and so gives a different answer on the same data until the sample count grows and it loses the freeze too.

Skeleton · target ≈10 min

# for T, see when it actually runs. The gap is everything that was hogging the loop — a synchronous
# CPU burst, a blocking library call someone forgot to run in an executor, a GC pause.
#
# The finding this drill exists to teach, and it generalises well past Python: a percentile cannot
# see a single freeze. Nearest-rank p99 over 100 samples IS the 99th sorted sample, so one 900 ms
# stall is exactly the sample it discards. A percentile-only monitor reports healthy straight
# through the outage its users are filing tickets about. So the verdict carries two legs — a
# percentile for sustained degradation, a max for the freeze — and returns "unknown" on zero
# samples, never "healthy". A monitor that cannot distinguish "measured, fine" from "measured

# nothing" is worse than no monitor, because it is trusted.

LagStats = namedtuple("LagStats", "count p50_ms p99_ms max_ms mean_ms")


def _nearest_rank(sorted_values, percentile):
    """Nearest-rank percentile: the smallest value at or above `percentile`% of the data."""
    rank = math.ceil(percentile / 100 * len(sorted_values))
    return sorted_values[max(1, rank) - 1]


def lag_from_samples(samples):
    """`samples` is an iterable of (scheduled_ms, actual_ms). Returns LagStats.

    Negative lag is clamped to 0 — a clock stepping backwards is not a callback arriving early,
    and letting it through drags the mean down exactly when something is wrong."""
    lags = sorted(max(0.0, float(actual) - float(scheduled)) for scheduled, actual in samples)
    if not lags:
        # No samples is NOT health. Every field is None so a caller cannot accidentally
        # compare its way to a healthy verdict.
        return LagStats(0, None, None, None, None)
    return LagStats(
        count=len(lags),
        p50_ms=_nearest_rank(lags, 50),
        p99_ms=_nearest_rank(lags, 99),
        max_ms=lags[-1],
        mean_ms=sum(lags) / len(lags),
    )


def saturation_verdict(stats, degraded_ms=50, saturated_ms=200, freeze_ms=250):
    """Two legs: a percentile leg for sustained degradation, a max leg for a single freeze.

    Returns 'unknown' | 'healthy' | 'degraded' | 'saturated'."""
    if stats.count == 0:
        return "unknown"
    if stats.max_ms >= freeze_ms:
        return "saturated"      # the leg a percentile-only monitor does not have
    if stats.p99_ms >= saturated_ms:
        return "saturated"
    if stats.p99_ms >= degraded_ms:
        return "degraded"
    return "healthy"

08 · Questions to ask

What to ask when Zara turns it around

An AI interviewer will ask if you have questions, and the answer is scored. These are ordered — ask the first two if you only get two.

  1. 01

    What does the AI/ML surface actually look like here — are you training models, serving them, or building the platform other people use to do both?

    ‘AI/ML Engineer’ covers all three and they are different jobs. The focus areas lean platform and production, so the answer may well surprise you.

  2. 02

    Given the focus areas are Python systems, production ownership and security rather than modelling, is this closer to an ML-platform or ML-infrastructure role?

    Shows you read the focus list as evidence, which is itself a signal. Ask it early so you can pitch the rest of the interview correctly.

  3. 03

    What does on-call look like for the ML systems, and who carries it?

    Directly feeds the ownership area, and the answer tells you whether ownership is real or aspirational here.

  4. 04

    How do you handle untrusted input reaching a model — is prompt injection or data isolation something the team has had to design around yet?

    Lands squarely in the third focus area and lets you talk about allowlisted capabilities rather than answering in the abstract.

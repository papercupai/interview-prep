03 · Your opener

The first ninety seconds, written out

Zara opens conversationally. This is the one answer worth having word-perfect, because it seeds every focus area so later answers become callbacks rather than fresh stories.

Say this in the first minute

I'm a fullstack engineer who has spent most of the last while on platform work — the layer other engineers build on rather than the product surface. The clearest example is a platform that coordinates many AI coding agents working on one codebase at once: a Node API over Postgres, a typed sync layer that pushes live invalidations to a React front end, a durable workflow layer for work that has to survive a restart, and a release gate that will not promote a red build. The data side is the part I'd point at for this role — a schema at around 975 migrations with no runtime schema changes anywhere, claim semantics built on row-level locking so a hundred concurrent workers can pull from one queue without stepping on each other, and change notification pushed rather than polled. The judgment I'd say I've developed is mostly about what not to build: the reflex to add a new table or a new service is usually one more field on something that already exists.

Cut this to sixty seconds for an eighteen-minute interview — it is the one place where the long version costs you a whole answer elsewhere.

04 · Full stack experience

One story that crosses every layer

“Full stack” is scored on whether you own a feature end to end, not on naming frameworks. Pick one feature and walk it from click to row and back.

“Walk me through a feature you built end to end.”

I will take live data sync, because it touches every layer. In the UI, a React view reads through one hook — not a hand-rolled fetch with an interval — so every query in the app has one cache, one invalidation path and one loading contract. State that a user would expect to share or reload into lives in the URL rather than component state, which also makes the whole UI scriptable by anything that can set a URL.

The API is a typed HTTP layer where each query name resolves to one resolver, so a query cannot exist without a server-side definition. Writes commit to Postgres and then publish an invalidation for the query names they touched; the stream pushes those names to connected clients, which refetch through the same audited path. Tests sit at both ends — unit tests for the resolvers, a headless browser run for the real UI.

The thing I would call out is that the boring part is the contract, not the code: one read path, one write path, one invalidation vocabulary. Every performance and correctness problem I have had at this layer came from a second path someone added because it was quicker.

EvidenceVite + React with URL-first state, a Hono API with a resolver registry, Postgres, and SSE invalidation; notifySyncInvalidate in 338 files (measured).

“How do you decide what goes in the URL versus component state?”

If it is meaningful to a person — which tab, which record, a filter, a search, a sort, pagination, whether a panel is open — it goes in the URL, typed and validated. If it is mechanical — in-flight loading, a half-typed draft, hover, a toast — it stays in component state. Two payoffs: a user can reload, bookmark and share exactly what they are looking at, and anything automating the app can read and drive the real state instead of guessing at the DOM. I enforce it as a convention with a bias — when in doubt, the URL — because the failure is always the same direction: state that should have been shareable and is not.

05 · System design and architecture reasoning

State the constraint, then the trade you are making

In a 27-minute conversational interview you will get one or two design prompts and no whiteboard. Structure beats detail: constraints, one design, the failure modes, the trade you accepted.

“Design a system that runs many long-lived jobs and survives restarts.”

I would ask two things first: is a job's effect safe to repeat, and what must survive a restart — the schedule, or also the job's progress? The answers change the design more than the scale does.

The shape I would build: work as rows in Postgres with an explicit state machine, claimed by workers with FOR UPDATE SKIP LOCKED under a lease with a heartbeat, so a dead worker's job returns to the pool on TTL rather than needing detection. Long jobs use durable execution — each step's result is persisted, so a restart resumes at the last completed step instead of re-running side effects. Scheduling is one mechanism, not several: a durable tier for anything that must not be missed and a bounded in-process tier for frequent sweeps, both declared in one inventory. The rule I hold to is that every recurring thing must be visible in one place — the failure I have actually seen is not a wrong schedule, it is a timer nobody knew existed.

Then the trade I would say out loud: putting the queue in Postgres costs me throughput a dedicated broker would give me, and buys transactional claims, one operational surface and no extra thing to run. At my volumes that is the right side of the trade, and I would name the volume where it stops being right.

EvidenceDurable workflow engine plus a two-tier scheduler with a single inventory; claims via SKIP LOCKED with leases and heartbeats.

“How do you keep a system like that observable?”

Every long-running thing has to answer three questions without me reading logs: is it running, is it making progress, and if not, why. Running is process-level and cheap. Progress is the one people skip — a heartbeat proves a process is alive, not that its work is advancing, so I record a work-level marker and treat a stalled marker as a failure even while the process looks healthy. And I measure from outside the suspect, because a component reporting on itself cannot report the failure that stops it reporting. The corollary I insist on: a monitor's verdict has to include unknown as distinct from healthy, or an unmeasured system will be reported as a passing one.

06 · Ownership and learning velocity

Evidence that you finish, and that you pick things up fast

These two are behavioural and they are scored. Have one story about owning something unglamorous to completion, and one about learning something you did not know on a deadline. Concrete, first person, with an outcome.

“Tell me about something you owned end to end.”

I built and now run a platform that coordinates many AI coding agents on one codebase at once — the coordination layer, the tool surface, the scheduler, the release gate and the evaluation rails. Ownership in practice has meant the parts nobody asks for: the release gate that refuses to promote a red build, the guards that make conventions executable instead of aspirational, the headless verification path so UI work is actually checked rather than claimed. The measure I would give is that rules which used to live in review comments are now enforced by the system, so ‘done’ has to arrive with evidence attached. That was not one feature, it was deciding the class of bug was mine to remove.

“Tell me about learning something quickly.”

The desktop shell. I needed a native host — a privileged process managing a webview, a Node sidecar, an embedded database and a custom protocol handler — in a language and framework I had not shipped before. What made it fast was not reading everything; it was picking the smallest end-to-end slice that had to work, getting it running, and then letting each real failure teach me the next thing. The file-descriptor limit, the write-ahead log that grew to 127 GiB, the framing bug across the process boundary — I did not know any of those existed when I started, and each one taught me more about the platform than a chapter would have. I would rather be the person who ships the slice and then reads the manual about the specific thing that broke.

What to do with a gap

Both of these focus areas are partly about how you handle not knowing something. The pattern that scores well is the same one you should use for Electron: name the gap precisely, say what the nearest thing you have done is, and say how you would close it. Vague confidence invites a probe; a precise gap ends the line of questioning.

07 · PostgreSQL

Schema discipline, locks, and the read you can trust

You have unusually strong material here: a schema with roughly 975 migrations and no runtime DDL, and real use of the concurrency primitives most candidates only name.

“How do you manage schema change on a live system?”

Migrations only, forward only, and no runtime DDL anywhere in the application — no “create table if not exists” on a code path. My current schema is around 975 numbered migrations, and the schema file is generated from them rather than hand-maintained, so the checked-in schema cannot drift from what actually applied.

Two details I would offer because they only show up with parallel developers. Numbering is allocated atomically under an advisory lock, because two people listing the directory and picking the next number will collide — we had that race and removed it. And a migration under construction carries a suffix that the runner ignores, so an unfinished file cannot be picked up and half-applied while it is being written.

For the risky shapes I separate the write from the read: add nullable, backfill in batches, deploy code that tolerates both, then enforce the constraint. Adding an index concurrently, and never taking a long ACCESS EXCLUSIVE lock on a hot table during business hours.

Evidence~975 migrations (counted 18 Sep 2026); numbering allocator under pg_advisory_lock; generated schema snapshot.

“What Postgres features do you reach for that most people do not?”

SKIP LOCKED for work queues, so the database is the queue and I do not run a broker. Advisory locks — usually transaction-scoped — for mutual exclusion across processes, because they release automatically when the transaction ends, which a lock table does not. LISTEN/NOTIFY to turn a commit into a push instead of having clients poll, with the caveat I would state unprompted: notifications are fire-and-forget and are lost if nobody is listening, so they are a wake-up signal, never the record. Partial and expression indexes, because most slow queries here were a predicate an index did not cover rather than a missing index. And JSONB for genuinely open-shaped payload data, with the columns I filter on promoted out to real columns — a query filtering inside JSONB is the one that surprises people at scale.

“A query got slow. Walk me through it.”

EXPLAIN (ANALYZE, BUFFERS) first, and I read the row estimates against the actual rows before I look at anything else — a plan that is wrong by orders of magnitude is a statistics problem, and adding an index to a bad estimate just gives you a bad plan faster. Then the usual suspects: a sequential scan on a predicate no index covers, a nested loop chosen from a bad estimate, or sorting in memory that has spilled to disk. But the first question I ask is whether the query is slow or whether it is waiting — lock contention and connection-pool starvation both present as a slow query while the plan is perfectly fine. I have chased a “slow query” that was actually a pooler killing idle transactions, and the fix was in the caller's transaction scope, not the SQL.

08 · Questions to ask

What to ask when Zara turns it around

An AI interviewer will ask if you have questions, and the answer is scored. These are ordered — ask the first two if you only get two.

  1. 01

    What does ‘data platforms’ mean here — pipelines and warehousing, or the transactional systems the product runs on?

    Those are very different jobs and the focus areas do not disambiguate. Ask it first; the answer should change which of your examples you reach for.

  2. 02

    Who are the platform's users, and what do they complain about most?

    Platform work is judged on adoption, not architecture. The complaint tells you what the job actually is.

  3. 03

    What is the largest thing in the system today, and what breaks first as it grows?

    Invites a real architecture conversation in the time you have, and it is the System & Architectural Judgment area in one question.

04 · Electron architecture

Processes first, APIs second

Electron's model is the whole interview: one main process that owns the OS (windows, menus, files, child processes), one renderer per window that owns the DOM and nothing else, and a preload script that is the only bridge between them. Everything people get wrong about Electron is a process-boundary mistake — so answer every question by saying which process the code runs in first.

“Walk me through Electron's process model.”

Main is a Node process: full filesystem and OS access, owns BrowserWindow, and it is single-threaded, so anything expensive I put there freezes every window. Renderers are Chromium processes, one per window, sandboxed, no Node. A preload runs in the renderer with access to both worlds and is where I publish a narrow API over contextBridge. For CPU work I add a utilityProcess — a child Node process supervised by main — rather than blocking main or giving a renderer Node access. The rule I follow is that the renderer is hostile territory: it renders remote-ish content, so it gets capabilities, never primitives.

“How do you expose a native capability to the UI safely?”

Never by turning nodeIntegration on. I keep contextIsolation: true and sandbox: true, and expose a verb, not a tool: contextBridge.exposeInMainWorld('files', { openProjectFile }) — not readFile, and never require or ipcRenderer wholesale. openProjectFile takes an id, main resolves it against an allowlisted root, and path traversal is impossible because the renderer never names a path. Then ipcRenderer.invoke + ipcMain.handle for request/response so every call has a reply and an error channel, and send/on only for genuine fire-and-forget events.

“You have built a desktop app, but in Tauri. What transfers?”

Say this once, early, without apologising: the process architecture transfers completely, the framework API surface is what I would be learning.

What I built maps one-to-one: a privileged host process, a webview that gets allowlisted commands instead of raw capabilities, a Node sidecar for the work neither should do, and a custom protocol handler for serving app content. I wrote the IPC layer myself — a length-prefixed binary frame codec, [4B length big-endian][1B type][payload] with a 16 MiB per-frame cap, implemented twice (Rust host, TypeScript client) and pinned byte-for-byte by golden-vector tests asserted on both sides. Electron hands you that layer, which means my time goes to the parts it does not solve.

Three things I would be learning, and I would say so: Chromium is bundled rather than the system webview, so I own its update and memory profile; packaging is electron-builder or Forge instead of the Tauri bundler; and Electron's IPC is structured-clone messages rather than my own bytes, so the failure modes move from framing bugs to serialisation and leak-a-handle bugs.

EvidenceRust host modules endpoint_ipc.rs + endpoint_ipc_framing.rs; TypeScript source of truth libs/generic/ipc-framing; golden vectors on both sides.

Do not overclaim Electron

You have shipped a desktop app and you have never shipped Electron. An AI interviewer probes inconsistency well; it rewards a named gap far more than it punishes one. If you bluff electron-builder internals you will be asked a second question about them.

05 · Cross-platform execution

The OS differences that actually bite

Cross-platform is not “it runs on three OSes”; it is knowing which specific assumptions break. Have two concrete per-OS defects ready — you have better ones than most candidates because you hit them in a shipped app.

“What breaks when you ship the same desktop app to macOS, Windows and Linux?”

Three real ones from my own app. On macOS, launchd hands a GUI app a file-descriptor soft limit of 256 — a GUI process starts far poorer than your shell, where it is a million. rlimits are inherited across fork and exec, so I raise RLIMIT_NOFILE once at the top of startup, before anything opens a handle or forks, and the whole process tree inherits it. Bolting it to one spawn site would miss every non-Node child.

On Linux the webview is WebKitGTK, which persists localStorage as a SQLite database in WAL mode. On Windows it is WebView2, and the interesting problem is path and runtime layout — I stage a runtime for the WSL case and hash its contents for a cache key, and enumerating that tree through the Windows-to-Linux filesystem bridge rather than natively reinstated a bottleneck I had already removed.

The general lesson I would give: the differences that hurt are not API differences, which the framework hides. They are resource limits, filesystem semantics and process lifecycle, which it does not.

Evidencefd_limit.rs (macOS 256 fd soft limit, raise-before-fork), localstorage_wal.rs, wsl_sidecar_staging.rs, sidecar_runtime_identity.rs.

“How do you test a desktop app in CI, with no desktop?”

I run the real shell headless rather than mocking it. Mine boots on its own virtual display with a software GL stack, its own port and its own sidecar, then a small CLI drives the webview — evaluate, query the DOM, click, type, screenshot, assert, and a teardown that runs even when the assertion fails. Two rules I learned the hard way: give the run its own display and its own database, because the first version wrote to live state and once leaked synthetic keystrokes into a real application window; and never let a test attach to a developer's session, because a focus-stealing test is a test nobody runs. For Electron this is the same shape with a different driver — Playwright's Electron support or a WebDriver session against the packaged binary.

Evidencescripts/verify-tauri-headless.sh (auto-picked display, VirtualGL, VERIFY_TAURI_ISOLATED_DB=1) and the tauri-agent-tools driver.

06 · Node.js · runtime and async

Where the work actually runs

Expect the event loop, and expect it to be asked as a scenario rather than a definition. Answer in terms of what blocks, what queues, and what starves.

“Something is slow. Walk me through how Node executes it.”

First I separate three cases, because they have different fixes. If it is CPU in JavaScript, nothing else runs at all — one thread, so timers, IPC replies and sockets all stop. The fix is a worker thread or a child process, not more async. If it is I/O, it is on libuv's threadpool, which defaults to four threads and is shared by filesystem, DNS and some crypto — so four slow fs calls can starve DNS resolution and look like a network problem. Raising UV_THREADPOOL_SIZE is the knob, doing less filesystem work is the fix. If it is queueing, the process is fine and my own concurrency is wrong.

And I would name the microtask trap: promise callbacks drain completely before the loop turns, so a recursive promise chain starves timers while looking perfectly asynchronous in a profile.

“How do you keep an async pipeline from falling over?”

Bound the concurrency and bound the queue. Promise.all over a map is the classic bug: ten thousand items open ten thousand handles because starting async work is cheap. I use a pool with a concurrency limit and a queue limit that rejects when full, because an unbounded queue does not remove the failure, it moves it from the socket table into the heap where it is invisible. Backpressure only exists if the producer learns it is too fast.

Then: an AbortSignal on anything a user can cancel, a timeout on anything crossing a process boundary, and idempotency on anything I retry.

EvidenceThe drill on this page implements exactly that pool, including the full-queue rejection.

“Tell me about a Node bug that taught you something.”

A child process printed a large JSON result and the parent received it truncated — but only sometimes, and only for big payloads. The cause is that process.exit() does not flush a pipe: stdout to a pipe is asynchronous, so exiting immediately after a large write discards whatever the kernel buffer had not taken. I had assumed the cutoff was the 64 KiB everyone quotes for pipe buffers; measuring it put it around 8 KiB and showed it was not a constant. The fix is to let the process end naturally, or write to a file and hand back the path. What it taught me is the habit: when a number disagrees with the folklore, measure it before designing around it.

EvidenceMeasured in the papercusp checkout; the truncation threshold was not the quoted 64 KiB.

07 · Real-time event processing

Fan-out, coalescing, and the cap nobody plans for

This focus area rewards one specific instinct: an event stream's hard problem is not delivery, it is volume and ordering. Lead with coalescing and idempotency.

“How would you push live updates to a desktop client?”

Server-sent events unless something genuinely needs a client-to-server stream. SSE is one HTTP response that stays open, so it reconnects by itself, replays from Last-Event-ID, and passes proxies that mangle WebSocket upgrades. I run SSE in every runtime deliberately, including the desktop webview, so the transport in development is the transport in production and I am never debugging a transport that only exists on one platform.

The invalidation model matters more than the transport: the server sends “this query is stale”, not the new rows. The payload stays tiny, the client refetches through one audited path, and I cannot leak data to a client that should not see it.

EvidenceSync layer with ~40 registered queries; notifySyncInvalidate appears in 338 files (measured 18 Sep 2026); EventSource in 151.

“A migration touches 4,000 rows and the UI locks up. What happened?”

Four thousand invalidations for the same query became four thousand refetches, and a browser allows about six concurrent connections per host — so request 4,000 queues behind request 1 and the app is not slow, it is stalled. The pathology is self-inflicted: the fan-out is ours.

The fix is coalescing, and the design point I would argue for is measuring the debounce window from when the key first went dirty, not the last event. Debouncing from the last event means a continuously hot key never flushes at all — it starves under exactly the load that made you add the debounce. So: per key keep the newest value, emit once the key has been dirty for the window, and flush early once too many keys are waiting, because a burst should not also be slow. I keep that policy as a pure function of a timestamp passed in, with the timer as a thin shell, which is why it is testable without fake timers.

EvidenceThat is the third drill on this page, including the hot-key starvation case.

“At-least-once or exactly-once?”

Exactly-once delivery does not exist across a network; exactly-once effect does, and you get it by making the consumer idempotent. So I design for at-least-once: every event carries a key, the handler is safe to run twice, and state transitions are conditional writes rather than blind ones. For work that must survive a crash I use durable execution — the workflow's steps and their results are persisted, so a restart resumes at the last completed step instead of re-running side effects. And I keep ordering per key rather than globally, because global ordering across a fan-out costs more than it is worth and is rarely what the product needs.

08 · Performance and reliability

Measure from outside the thing you suspect

The strongest answers here are war stories with a number and a mechanism. You have two that are genuinely excellent — a freeze that a percentile cannot see, and a 127 GiB file.

“The app freezes intermittently. How do you find it?”

I measure event-loop lag — schedule a timer for 10 ms, record how late it actually fires — and I measure it from a process that is not the suspect. A heartbeat emitted by a blocked thread cannot report that it is blocked: it is not running either, so silence looks exactly like health.

Then the part I would want to be asked about: a percentile alone will miss it. Nearest-rank p99 over 100 samples is the 99th smallest value, so the single worst sample is precisely the one it drops. I measured a 900 ms freeze in a 100-sample window and p99 read 2 ms — a clean bill of health through a user-visible freeze. So the monitor carries two legs: a percentile for sustained degradation and a max for single freezes, because one 900 ms hang is an incident the first time it happens. And with no samples the verdict is unknown, never healthy — an unmeasured system is not a passing one.

EvidenceThe fourth drill on this page asserts exactly this: p99 blind, max catches it, and the converse case where sustained lag has no single freeze.

“Tell me about a reliability bug you are proud of finding.”

A desktop install had a 127 GiB file in it — about 121,000 times the size of the 1 MiB database it belonged to. The webview stores localStorage as SQLite in WAL mode. SQLite can only reset a write-ahead log past its oldest reader, and the app is a long-lived page that holds a read connection open forever, so auto-checkpoint could never wrap the log — every write just appended. The second half is why it never self-healed: the shell is usually killed rather than closed, so the on-close checkpoint that would have reset the log never ran either.

The fix is not deleting the file, which loses committed-but-uncheckpointed frames and regrows anyway. It is checkpointing at boot, before the webview reopens the store, so no reader is holding an old frame. The class of bug is what I take from it: unbounded growth in a long-lived process, where the mechanism that would clean it up is the one the long-lived process prevents.

Evidencelocalstorage_wal.rs — boot-time WAL reclaim plus a runaway guard.

The trap in this focus area

Do not attribute anything to “low memory”, “high load” or “thrashing” without a mechanism. High memory use, used swap and a big load-average are not evidence of a bottleneck on their own. Say what you would measure to connect the symptom to the cause — major page faults on the hot path, IO-wait dominating wall-clock, a latency that tracks the pressure and recovers when it lifts. “I would not blame resources without that measurement” is a senior answer; guessing the cause is the exact failure this area screens for.

// Electron's ipcMain/ipcRenderer hands you whole structured-cloned messages, so you
// never see framing there. You see it the moment a second process is involved — a
// utilityProcess, a spawned sidecar, a socket — because a stream gives you BYTES,
// not messages. TCP will hand you half a frame, or two and a half frames, and a
// decoder that assumes message boundaries works in dev and corrupts under load.
//
// Wire format (the one in libs/generic/ipc-framing, mirrored byte-for-byte in Rust):
//   [4B payload length, big-endian][1B type][payload]
// Big-endian because every other wire protocol is, and a mismatched endianness bug
// is invisible until a length crosses 256. 16 MiB cap so a corrupt length field
// cannot make the peer allocate a gigabyte.

const HEADER_BYTES = 5;
const MAX_PAYLOAD = 16 * 1024 * 1024;

const FrameType = { REQUEST: 1, RESPONSE: 2, ERROR: 3, CANCEL: 4 };

function encodeFrame(type, payload) {
  const body = Buffer.isBuffer(payload) ? payload : Buffer.from(String(payload), 'utf8');
  if (!Number.isInteger(type) || type < 0 || type > 255) {
    throw new RangeError(`frame type must be a byte, got ${type}`);
  }
  if (body.length > MAX_PAYLOAD) {
    throw new RangeError(`frame payload ${body.length}B exceeds ${MAX_PAYLOAD}B cap`);
  }
  const frame = Buffer.allocUnsafe(HEADER_BYTES + body.length);
  frame.writeUInt32BE(body.length, 0);
  frame.writeUInt8(type, 4);
  body.copy(frame, HEADER_BYTES);
  return frame;
}

class FrameDecoder {
  constructor({ maxPayload = MAX_PAYLOAD } = {}) {
    this.maxPayload = maxPayload;
    this.buffered = Buffer.alloc(0);
  }

  // Returns every COMPLETE frame in the bytes so far and keeps the remainder.
  // Never returns a partial frame; never blocks waiting for one.
  push(chunk) {
    this.buffered = this.buffered.length === 0
      ? Buffer.from(chunk)
      : Buffer.concat([this.buffered, chunk]);
    const frames = [];
    for (;;) {
      if (this.buffered.length < HEADER_BYTES) break;
      const length = this.buffered.readUInt32BE(0);
      if (length > this.maxPayload) {
        // Unrecoverable: the stream is desynchronised or the peer is hostile.
        // Throwing is correct — resync-by-scanning invents message boundaries.
        throw new RangeError(`declared frame payload ${length}B exceeds ${this.maxPayload}B cap`);
      }
      const total = HEADER_BYTES + length;
      if (this.buffered.length < total) break; // partial frame, wait for more bytes
      frames.push({
        type: this.buffered.readUInt8(4),
        payload: this.buffered.subarray(HEADER_BYTES, total),
      });
      this.buffered = this.buffered.subarray(total);
    }
    return frames;
  }

  get pendingBytes() {
    return this.buffered.length;
  }
}

// "Node is single-threaded" is not why this matters. Async work is cheap to START
// and that is the trap: `await Promise.all(items.map(work))` on 10,000 items opens
// 10,000 sockets / file handles / database connections at once. The sidecar answer
// is a bounded pool whose queue is also bounded — an unbounded queue just moves the
// failure from the socket table into the heap, which is worse because it is invisible.
//
// Backpressure means the producer LEARNS it is too fast. A pool that silently
// buffers is not applying backpressure; it is hiding the need for it.

class QueueFullError extends Error {
  constructor(limit) {
    super(`pool queue is full (${limit} waiting)`);
    this.name = 'QueueFullError';
  }
}

function createPool({ limit, maxQueue = Infinity }) {
  if (!Number.isInteger(limit) || limit < 1) throw new RangeError('limit must be >= 1');
  let active = 0;
  const waiting = [];

  const pump = () => {
    while (active < limit && waiting.length > 0) {
      const job = waiting.shift();
      active += 1;
      // Run outside the loop's control flow so a synchronous throw inside fn
      // rejects that job's promise instead of killing the pump.
      Promise.resolve()
        .then(job.fn)
        .then(job.resolve, job.reject)
        .finally(() => {
          active -= 1;
          pump();
        });
    }
  };

  return {
    run(fn) {
      if (waiting.length >= maxQueue && active >= limit) {
        return Promise.reject(new QueueFullError(maxQueue));
      }
      return new Promise((resolve, reject) => {
        waiting.push({ fn, resolve, reject });
        pump();
      });
    },
    get active() { return active; },
    get queued() { return waiting.length; },
  };
}

// Ordered fan-out over a bounded pool: results keep INPUT order even though
// completion order is arbitrary. The bug this avoids is pushing results as they
// land and quietly returning them shuffled.
async function mapLimit(items, limit, worker) {
  const pool = createPool({ limit });
  const results = new Array(items.length);
  await Promise.all(items.map((item, index) =>
    pool.run(() => worker(item, index)).then(value => { results[index] = value; })));
  return results;
}
Drill 3 · Invalidation coalescing

Many writes, one notification. Measure the window from the first dirty key, not from the most recent one, or a hot key starves forever — that starvation case is asserted in the tests. Add an early flush at maxDirty and expose nextDueMs so exactly one timer is ever armed.

Skeleton · target ≈12 min
// A real-time UI does not need every event; it needs the LATEST state, soon. When a
// migration touches 4,000 rows, 4,000 invalidations for the same query are 3,999
// wasted refetches — and on a browser's 6-connection-per-host cap they are a
// self-inflicted outage, because the 4,000th refetch queues behind the first.
//
// Policy, pulled apart from the clock so it is testable:
//   - per key, remember the newest event and when the key first went dirty
//   - emit a key once it has been dirty for windowMs (debounce), OR
//   - emit immediately once maxDirty keys are waiting (a burst should not also be slow)

// A real-time UI does not need every event; it needs the LATEST state, soon. When a
// migration touches 4,000 rows, 4,000 invalidations for the same query are 3,999
// wasted refetches — and on a browser's 6-connection-per-host cap they are a
// self-inflicted outage, because the 4,000th refetch queues behind the first.
//
// Policy, pulled apart from the clock so it is testable:
//   - per key, remember the newest event and when the key first went dirty
//   - emit a key once it has been dirty for windowMs (debounce), OR
//   - emit immediately once maxDirty keys are waiting (a burst should not also be slow)
// Time is an ARGUMENT here. That is the whole trick: no fake timers, no flaky test.

function createCoalescer({ windowMs, maxDirty = Infinity }) {
  if (!(windowMs >= 0)) throw new RangeError('windowMs must be >= 0');
  const dirty = new Map(); // key -> { firstSeenMs, lastSeenMs, value, hits }

  return {
    mark(key, nowMs, value = undefined) {
      const existing = dirty.get(key);
      if (existing) {
        existing.lastSeenMs = nowMs;
        existing.value = value;
        existing.hits += 1;
      } else {
        dirty.set(key, { firstSeenMs: nowMs, lastSeenMs: nowMs, value, hits: 1 });
      }
      return dirty.size;
    },

    // Everything due at nowMs, oldest-dirty first. Draining REMOVES it: a key
    // marked again after draining starts a fresh window rather than re-emitting.
    drain(nowMs) {
      const overCap = dirty.size >= maxDirty;
      const due = [];
      for (const [key, entry] of dirty) {
        if (overCap || nowMs - entry.firstSeenMs >= windowMs) {
          due.push({ key, value: entry.value, hits: entry.hits, dirtyForMs: nowMs - entry.firstSeenMs });
        }
      }
      for (const { key } of due) dirty.delete(key);
      return due;
    },

    // When the next key comes due, so a caller can arm ONE timer instead of polling.
    nextDueMs(nowMs) {
      if (dirty.size === 0) return null;
      if (dirty.size >= maxDirty) return 0;
      let soonest = Infinity;
      for (const entry of dirty.values()) {
        soonest = Math.min(soonest, Math.max(0, entry.firstSeenMs + windowMs - nowMs));
      }
      return soonest;
    },

    get dirtyCount() { return dirty.size; },
  };
}

// In Electron this is the difference between "the app is slow" and "the app is
// frozen": a saturated main/renderer thread stops the event loop, so every timer,
// every IPC reply and every repaint stops with it. The cruel part is that a
// heartbeat emitted BY the blocked thread cannot report the block — it is not
// running either. Measure from outside, or measure the loop's own late-ness.
//
// Pure core: given scheduled-vs-actual sample pairs, return the lag distribution
// and a verdict. Percentile convention: nearest-rank on the sorted sample.

function lagFromSamples(samples) {
  if (!Array.isArray(samples) || samples.length === 0) {
    return { count: 0, p50Ms: null, p99Ms: null, maxMs: null };
  }
  const lags = samples
    .map(({ scheduledMs, actualMs }) => Math.max(0, actualMs - scheduledMs))
    .sort((a, b) => a - b);
  const at = fraction => lags[Math.min(lags.length - 1, Math.ceil(fraction * lags.length) - 1)];
  return {
    count: lags.length,
    p50Ms: at(0.5),
    p99Ms: at(0.99),
    maxMs: lags[lags.length - 1],
  };
}

// Two legs, deliberately. A percentile answers "is it sustained"; it CANNOT answer
// "did we freeze once", because nearest-rank p99 over 100 samples is the 99th
// smallest — the single worst sample is exactly the one it drops. A 900ms freeze is
// user-visible on its first occurrence, so max gets its own threshold.
function saturationVerdict(stats, { warnMs = 50, critMs = 250, freezeMs = 500 } = {}) {
  if (stats.count === 0) return 'unknown'; // never report "healthy" from no measurement
  if (stats.p99Ms >= critMs || stats.maxMs >= freezeMs) return 'saturated';
  if (stats.p99Ms >= warnMs) return 'degraded';
  return 'healthy';
}

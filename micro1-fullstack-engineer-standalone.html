04 · Full stack experience

One story that crosses every layer

“Full stack” is scored on whether you own a feature end to end, not on naming frameworks. Pick one feature and walk it from click to row and back.

“Walk me through a feature you built end to end.”

I will take live data sync, because it touches every layer. In the UI, a React view reads through one hook — not a hand-rolled fetch with an interval — so every query in the app has one cache, one invalidation path and one loading contract. State that a user would expect to share or reload into lives in the URL rather than component state, which also makes the whole UI scriptable by anything that can set a URL.

The API is a typed HTTP layer where each query name resolves to one resolver, so a query cannot exist without a server-side definition. Writes commit to Postgres and then publish an invalidation for the query names they touched; the stream pushes those names to connected clients, which refetch through the same audited path. Tests sit at both ends — unit tests for the resolvers, a headless browser run for the real UI.

The thing I would call out is that the boring part is the contract, not the code: one read path, one write path, one invalidation vocabulary. Every performance and correctness problem I have had at this layer came from a second path someone added because it was quicker.

EvidenceVite + React with URL-first state, a Hono API with a resolver registry, Postgres, and SSE invalidation; notifySyncInvalidate in 338 files (measured).

“How do you decide what goes in the URL versus component state?”

If it is meaningful to a person — which tab, which record, a filter, a search, a sort, pagination, whether a panel is open — it goes in the URL, typed and validated. If it is mechanical — in-flight loading, a half-typed draft, hover, a toast — it stays in component state. Two payoffs: a user can reload, bookmark and share exactly what they are looking at, and anything automating the app can read and drive the real state instead of guessing at the DOM. I enforce it as a convention with a bias — when in doubt, the URL — because the failure is always the same direction: state that should have been shareable and is not.

05 · JavaScript and TypeScript proficiency

Types as a design tool, not decoration

Expect language mechanics and expect a type-modelling question. The senior answer to both is about making wrong states impossible rather than about syntax.

“How do you use TypeScript beyond annotating parameters?”

I use it to make illegal states unrepresentable. A discriminated union instead of an object with four optional fields and a comment about which combinations are valid — then the compiler enforces the state machine and an exhaustive switch tells me every place that needs updating when I add a case. Narrow types at the boundary: parse and validate untrusted input once, at the edge, into a type the rest of the code can trust, instead of sprinkling optional chaining everywhere downstream.

And I treat any and a non-null assertion as debts I am taking on deliberately, usually at a boundary I have not modelled yet. The mistake I have made and would warn about: satisfying the compiler by loosening a type — making a new required field optional to clear the errors — which silences the exact signal that was telling me where the change had not landed.

“Explain something people get wrong in JavaScript.”

Equality and coercion are the usual answer; the one I would give is that await in a loop looks like ordering and is often just slowness, while Promise.all over a big array looks like speed and is often a resource exhaustion bug. Both are the same misunderstanding — that concurrency is a syntax choice rather than a capacity decision. The other one I see constantly is a floating promise: an async call with no await and no .catch, which does not fail loudly, it fails in an unhandled rejection handler far from the cause, usually after the request it belonged to has already returned a success.

06 · Problem solving and debugging

Make it reproducible, then make it small

This is the focus area where a real story beats any framework. The method matters more than the bug: what you measured, what you ruled out, and how you knew you were right.

“Walk me through debugging something hard.”

My order is: reproduce it, shrink it, then explain it — and I do not fix anything before the explanation, because a change that makes a symptom disappear without a mechanism is how you ship the same bug twice. Shrinking is the step that does the work: remove variables until the smallest thing that still fails, and every removal either eliminates a hypothesis or reproduces without it.

The specific discipline I have learned is to distrust my instrument before my hypothesis. I have had a tool answer that a process was gone while it was very much running, because the flag I passed did not exist on that system and the usage error exited with the same code as a clean negative. A well-formed wrong answer is far more expensive than an error, so when a result surprises me, my first move is to prove the measurement can show the opposite.

And when a number is the surprise, I find the code that writes it before I believe it. I have reported a metric as a catastrophic regression when the column mixed two different scales — a clean-looking 99.9 per cent that was a definitional artefact, not a distribution. The tell is that the more alarming a number looks, the likelier I am misreading its units.

“You cannot reproduce it. Now what?”

Then I stop trying to reproduce it and start narrowing it with evidence from where it happens. I add the measurement that would distinguish the two or three candidate mechanisms — not more logging, a specific discriminator — and I say in advance what each hypothesis predicts, so the data can actually choose between them rather than being read to confirm whichever I prefer. Meanwhile I bound the damage: a timeout, a guard, a circuit breaker, so the failure is survivable while I work. I label that explicitly as a mitigation, not a fix, with the durable fix tracked — the mitigation that gets mistaken for a fix is the one that leaves the trap armed for the next person.

// Electron's ipcMain/ipcRenderer hands you whole structured-cloned messages, so you
// never see framing there. You see it the moment a second process is involved — a
// utilityProcess, a spawned sidecar, a socket — because a stream gives you BYTES,
// not messages. TCP will hand you half a frame, or two and a half frames, and a
// decoder that assumes message boundaries works in dev and corrupts under load.
//
// Wire format (the one in libs/generic/ipc-framing, mirrored byte-for-byte in Rust):
//   [4B payload length, big-endian][1B type][payload]
// Big-endian because every other wire protocol is, and a mismatched endianness bug
// is invisible until a length crosses 256. 16 MiB cap so a corrupt length field
// cannot make the peer allocate a gigabyte.

const HEADER_BYTES = 5;
const MAX_PAYLOAD = 16 * 1024 * 1024;

const FrameType = { REQUEST: 1, RESPONSE: 2, ERROR: 3, CANCEL: 4 };

function encodeFrame(type, payload) {
  const body = Buffer.isBuffer(payload) ? payload : Buffer.from(String(payload), 'utf8');
  if (!Number.isInteger(type) || type < 0 || type > 255) {
    throw new RangeError(`frame type must be a byte, got ${type}`);
  }
  if (body.length > MAX_PAYLOAD) {
    throw new RangeError(`frame payload ${body.length}B exceeds ${MAX_PAYLOAD}B cap`);
  }
  const frame = Buffer.allocUnsafe(HEADER_BYTES + body.length);
  frame.writeUInt32BE(body.length, 0);
  frame.writeUInt8(type, 4);
  body.copy(frame, HEADER_BYTES);
  return frame;
}

class FrameDecoder {
  constructor({ maxPayload = MAX_PAYLOAD } = {}) {
    this.maxPayload = maxPayload;
    this.buffered = Buffer.alloc(0);
  }

  // Returns every COMPLETE frame in the bytes so far and keeps the remainder.
  // Never returns a partial frame; never blocks waiting for one.
  push(chunk) {
    this.buffered = this.buffered.length === 0
      ? Buffer.from(chunk)
      : Buffer.concat([this.buffered, chunk]);
    const frames = [];
    for (;;) {
      if (this.buffered.length < HEADER_BYTES) break;
      const length = this.buffered.readUInt32BE(0);
      if (length > this.maxPayload) {
        // Unrecoverable: the stream is desynchronised or the peer is hostile.
        // Throwing is correct — resync-by-scanning invents message boundaries.
        throw new RangeError(`declared frame payload ${length}B exceeds ${this.maxPayload}B cap`);
      }
      const total = HEADER_BYTES + length;
      if (this.buffered.length < total) break; // partial frame, wait for more bytes
      frames.push({
        type: this.buffered.readUInt8(4),
        payload: this.buffered.subarray(HEADER_BYTES, total),
      });
      this.buffered = this.buffered.subarray(total);
    }
    return frames;
  }

  get pendingBytes() {
    return this.buffered.length;
  }
}

// "Node is single-threaded" is not why this matters. Async work is cheap to START
// and that is the trap: `await Promise.all(items.map(work))` on 10,000 items opens
// 10,000 sockets / file handles / database connections at once. The sidecar answer
// is a bounded pool whose queue is also bounded — an unbounded queue just moves the
// failure from the socket table into the heap, which is worse because it is invisible.
//
// Backpressure means the producer LEARNS it is too fast. A pool that silently
// buffers is not applying backpressure; it is hiding the need for it.

class QueueFullError extends Error {
  constructor(limit) {
    super(`pool queue is full (${limit} waiting)`);
    this.name = 'QueueFullError';
  }
}

function createPool({ limit, maxQueue = Infinity }) {
  if (!Number.isInteger(limit) || limit < 1) throw new RangeError('limit must be >= 1');
  let active = 0;
  const waiting = [];

  const pump = () => {
    while (active < limit && waiting.length > 0) {
      const job = waiting.shift();
      active += 1;
      // Run outside the loop's control flow so a synchronous throw inside fn
      // rejects that job's promise instead of killing the pump.
      Promise.resolve()
        .then(job.fn)
        .then(job.resolve, job.reject)
        .finally(() => {
          active -= 1;
          pump();
        });
    }
  };

  return {
    run(fn) {
      if (waiting.length >= maxQueue && active >= limit) {
        return Promise.reject(new QueueFullError(maxQueue));
      }
      return new Promise((resolve, reject) => {
        waiting.push({ fn, resolve, reject });
        pump();
      });
    },
    get active() { return active; },
    get queued() { return waiting.length; },
  };
}

// Ordered fan-out over a bounded pool: results keep INPUT order even though
// completion order is arbitrary. The bug this avoids is pushing results as they
// land and quietly returning them shuffled.
async function mapLimit(items, limit, worker) {
  const pool = createPool({ limit });
  const results = new Array(items.length);
  await Promise.all(items.map((item, index) =>
    pool.run(() => worker(item, index)).then(value => { results[index] = value; })));
  return results;
}

// A real-time UI does not need every event; it needs the LATEST state, soon. When a
// migration touches 4,000 rows, 4,000 invalidations for the same query are 3,999
// wasted refetches — and on a browser's 6-connection-per-host cap they are a
// self-inflicted outage, because the 4,000th refetch queues behind the first.
//
// Policy, pulled apart from the clock so it is testable:
//   - per key, remember the newest event and when the key first went dirty
//   - emit a key once it has been dirty for windowMs (debounce), OR
//   - emit immediately once maxDirty keys are waiting (a burst should not also be slow)
// Time is an ARGUMENT here. That is the whole trick: no fake timers, no flaky test.

function createCoalescer({ windowMs, maxDirty = Infinity }) {
  if (!(windowMs >= 0)) throw new RangeError('windowMs must be >= 0');
  const dirty = new Map(); // key -> { firstSeenMs, lastSeenMs, value, hits }

  return {
    mark(key, nowMs, value = undefined) {
      const existing = dirty.get(key);
      if (existing) {
        existing.lastSeenMs = nowMs;
        existing.value = value;
        existing.hits += 1;
      } else {
        dirty.set(key, { firstSeenMs: nowMs, lastSeenMs: nowMs, value, hits: 1 });
      }
      return dirty.size;
    },

    // Everything due at nowMs, oldest-dirty first. Draining REMOVES it: a key
    // marked again after draining starts a fresh window rather than re-emitting.
    drain(nowMs) {
      const overCap = dirty.size >= maxDirty;
      const due = [];
      for (const [key, entry] of dirty) {
        if (overCap || nowMs - entry.firstSeenMs >= windowMs) {
          due.push({ key, value: entry.value, hits: entry.hits, dirtyForMs: nowMs - entry.firstSeenMs });
        }
      }
      for (const { key } of due) dirty.delete(key);
      return due;
    },

    // When the next key comes due, so a caller can arm ONE timer instead of polling.
    nextDueMs(nowMs) {
      if (dirty.size === 0) return null;
      if (dirty.size >= maxDirty) return 0;
      let soonest = Infinity;
      for (const entry of dirty.values()) {
        soonest = Math.min(soonest, Math.max(0, entry.firstSeenMs + windowMs - nowMs));
      }
      return soonest;
    },

    get dirtyCount() { return dirty.size; },
  };
}

function lagFromSamples(samples) {
  if (!Array.isArray(samples) || samples.length === 0) {
    return { count: 0, p50Ms: null, p99Ms: null, maxMs: null };
  }
  const lags = samples
    .map(({ scheduledMs, actualMs }) => Math.max(0, actualMs - scheduledMs))
    .sort((a, b) => a - b);
  const at = fraction => lags[Math.min(lags.length - 1, Math.ceil(fraction * lags.length) - 1)];
  return {
    count: lags.length,
    p50Ms: at(0.5),
    p99Ms: at(0.99),
    maxMs: lags[lags.length - 1],
  };
}

// Two legs, deliberately. A percentile answers "is it sustained"; it CANNOT answer
// "did we freeze once", because nearest-rank p99 over 100 samples is the 99th
// smallest — the single worst sample is exactly the one it drops. A 900ms freeze is
// user-visible on its first occurrence, so max gets its own threshold.
function saturationVerdict(stats, { warnMs = 50, critMs = 250, freezeMs = 500 } = {}) {
  if (stats.count === 0) return 'unknown'; // never report "healthy" from no measurement
  if (stats.p99Ms >= critMs || stats.maxMs >= freezeMs) return 'saturated';
  if (stats.p99Ms >= warnMs) return 'degraded';
  return 'healthy';
}

// Thin shell over the pure core: the only part that touches real time.
async function measureLag({ intervalMs = 10, samples = 5 } = {}) {
  const collected = [];
  let scheduledMs = Date.now();
  for (let i = 0; i < samples; i += 1) {
    scheduledMs += intervalMs;
    await delay(intervalMs);
    collected.push({ scheduledMs, actualMs: Date.now() });
  }
  return lagFromSamples(collected);
}

09 · Questions to ask

What to ask when Zara turns it around

An AI interviewer will ask if you have questions, and the answer is scored. These are ordered — ask the first two if you only get two.

  1. 01

    What is the role title and level? The email I received started at the format section, so I want to make sure I am pitching at the right level.

    Ask this of the recruiter by email before the interview if you can — it is a reasonable question and it changes how you present.

  2. 02

    What does the stack look like, and how much of it would I own?

    ‘Fullstack’ ranges from ‘React plus an API route’ to owning schema, services and deploys.

  3. 03

    What does the coding exercise cover — is it algorithmic, or building something small in the stack?

    Worth asking. Either way the drills on this page rehearse the narration, which is what is actually scored.

  4. 04

    What would the first ninety days look like, and what would make them a success?

    Directly feeds the ownership focus area, and the answer tells you whether they have thought about onboarding at all.

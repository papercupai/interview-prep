03 · Your opener

The first ninety seconds, written out

Zara opens conversationally. This is the one answer worth having word-perfect, because it seeds every focus area so later answers become callbacks rather than fresh stories.

Say this in the first minute

I'm a software engineer who has spent the last stretch of my career on the question of how you know software is correct — not just whether it runs. I built and run a platform where many AI coding agents work on one codebase at once, and the interesting half of that problem is evaluation: what does done mean, what evidence has to come with it, and which rules can be enforced by the system instead of by review. So a lot of my work is review and test design in a literal sense — guards whose baselines only shrink, tests that pin documented claims to the code so prose cannot rot silently, and a habit of proving a guard can actually fail before I trust it. I care about the writing side too, more than most engineers do: I've watched a hedged note of mine harden into a confident claim across a few re-readings and send someone off investigating a mechanism that didn't exist, so I now separate what I observed from what I inferred and label which is which.

This opener is deliberately about judgement rather than shipping, because all four scored areas are. Your Turing AI-evaluation page is the closest sibling to this interview — reread its rubric material first.

04 · Code quality and correctness review

Read for the class of defect, not the diff

This focus area is asking whether you can find the bug someone else's tests will not. Lead with what you look for first, and make it about failure classes.

“How do you review a change?”

I read the change for what it makes newly possible, not line by line. In order: does it do what the description says; what breaks at the boundaries — empty, one, duplicate, concurrent, retried, partially failed; does it create a second way to do something we already have one way to do; and could this defect class recur. That last question is the one that changes the review, because the answer is usually a test or a guard, not a comment.

The specific things I catch most often: an unbounded fan-out, an error that is caught and swallowed, a retry on a non-idempotent operation, a new required field that strands call sites the author's own tests do not reach, and state that should be shared sitting in a place only one component can see.

“How do you stop the same mistake coming back?”

I turn the review comment into a check, because a convention nobody can enforce decays. In my own system the rules that matter are executable: an unenrolled background timer fails a lint whose baseline is empty, a process spawn that escapes the task ledger fails another, and a documented claim about the code is pinned by a test that fails when the prose and the code diverge — so the documentation cannot rot quietly.

The discipline that makes those trustworthy: a guard that has never failed is a guard I have not tested. So I prove falsifiability — mutate the thing it protects and confirm the guard goes red. I run that against a copy or a historical commit rather than the shared tree, and require a positive control, because a scan that silently measured nothing reports a clean pass that looks exactly like a real one.

EvidenceLint guards with shrink-only baselines, doc-claim tests pinning prose to code, and a mutation-probe harness with required positive controls.

“You find a bug in review. The author says it is unlikely. What do you do?”

I try to make it concrete rather than argue about likelihood, because “unlikely” is a claim about a distribution neither of us has measured. If I can write the failing input in two minutes, I write it — a failing test ends the discussion without it being a disagreement between people. If I cannot, I say plainly which conditions I think it needs and ask whether those conditions can occur, and if the honest answer is “probably not this quarter”, then it is a filed follow-up rather than a blocker. What I do not do is hold a change hostage to a hypothetical, or let a real defect through because the person was confident. Severity times reachability, not volume of opinion.

05 · Problem and test design

Design the falsifier, not the happy path

The question underneath this focus area is whether your tests can fail for the right reason. Your best material is the taxonomy of false greens you have collected.

“How do you design tests for something you have just built?”

I start from the invariant rather than the implementation: what must be true for every input, and what input would make it false. Then the boundaries — empty, one, the cap, one over the cap — and then the sequences that only break in combination: retried, reordered, interleaved, cancelled halfway. If a test can only fail when the code is rewritten, it is documentation, not a test.

I also design for time explicitly. Anything with a clock gets a pure core that takes the timestamp as an argument and a thin shell that reads the real clock, so the behaviour is tested deterministically and the flaky part is one line I can inspect. That single choice removed most of the flake I used to have.

“A test suite is green. Why might that be worthless?”

Because green and “nothing ran” are the same colour, and I have collected the ways: a test-name filter that matched zero tests and exited zero; a runner invoked where it matched no files at all; a database query against a status value the column can never contain, which returns zero rows and reads as “no failures”; a search piped into head, where the truncation is invisible and the absence of a hit looks like proof of absence. Every one of those is indistinguishable from a real pass by construction.

So the habit is a positive control: before I believe a negative result, I check the instrument can produce a positive one. And I make the tools refuse instead of reporting a vacuous zero — the test runner I use now fails the call when a pattern matched no tests, rather than exiting green.

EvidenceZero-work false-green class: name-filter no-match, zero matched files, wrong-relation zero-row SQL, truncated search.

“Where do you draw the line on coverage?”

Coverage tells me what was executed, not what was verified, so I do not manage to a number — a suite can be at ninety per cent and assert almost nothing. I ask instead which behaviours would be caught if they broke, and I test at the level where the defect actually lives: units for logic and boundaries, integration for anything crossing a process or a schema, and a small number of end-to-end runs for the paths a user would notice. The ordering discipline I would mention because it bit me: run the typechecker last, after the final edit, including the edit that fixed a failing test — otherwise the clean type result was banked before the last change and the green test run cannot stand in for it, because the runner strips types rather than checking them.

06 · System design and architecture reasoning

State the constraint, then the trade you are making

In a 27-minute conversational interview you will get one or two design prompts and no whiteboard. Structure beats detail: constraints, one design, the failure modes, the trade you accepted.

“Design a system that runs many long-lived jobs and survives restarts.”

I would ask two things first: is a job's effect safe to repeat, and what must survive a restart — the schedule, or also the job's progress? The answers change the design more than the scale does.

The shape I would build: work as rows in Postgres with an explicit state machine, claimed by workers with FOR UPDATE SKIP LOCKED under a lease with a heartbeat, so a dead worker's job returns to the pool on TTL rather than needing detection. Long jobs use durable execution — each step's result is persisted, so a restart resumes at the last completed step instead of re-running side effects. Scheduling is one mechanism, not several: a durable tier for anything that must not be missed and a bounded in-process tier for frequent sweeps, both declared in one inventory. The rule I hold to is that every recurring thing must be visible in one place — the failure I have actually seen is not a wrong schedule, it is a timer nobody knew existed.

Then the trade I would say out loud: putting the queue in Postgres costs me throughput a dedicated broker would give me, and buys transactional claims, one operational surface and no extra thing to run. At my volumes that is the right side of the trade, and I would name the volume where it stops being right.

EvidenceDurable workflow engine plus a two-tier scheduler with a single inventory; claims via SKIP LOCKED with leases and heartbeats.

“How do you keep a system like that observable?”

Every long-running thing has to answer three questions without me reading logs: is it running, is it making progress, and if not, why. Running is process-level and cheap. Progress is the one people skip — a heartbeat proves a process is alive, not that its work is advancing, so I record a work-level marker and treat a stalled marker as a failure even while the process looks healthy. And I measure from outside the suspect, because a component reporting on itself cannot report the failure that stops it reporting. The corollary I insist on: a monitor's verdict has to include unknown as distinct from healthy, or an unmeasured system will be reported as a passing one.

07 · Technical writing and structured feedback

Write so the next person cannot misread it

Being scored on writing in a spoken interview means they want to hear structure: how you organise a finding, and how you separate what you saw from what you concluded.

“How do you write up a technical finding?”

Same skeleton every time, because the reader should not have to learn my format: what is wrong, the evidence, the mechanism, the fix, and what stops it recurring. The rule I hold hardest is separating the observation from the inferred mechanism and labelling which is which — ‘the probe reported the process gone while it was still running’ is what I saw; ‘the liveness check matches on command text’ is what I think explains it. Written together as one confident sentence, the guess inherits the credibility of the measurement, and the next person spends a day on a mechanism that does not exist. I have watched that happen from a note I wrote.

So an unverified cause is tagged as unverified and carries the probe that would settle it. A finding with a number in it says how the number was measured. And documentation that describes code gets derived or pinned to a test where it can be, rather than hand-maintained, because a hand-maintained description of code is a copy that will drift and there is no warning when it does.

“How do you give feedback someone will act on?”

Specific, addressed to the work, and it must contain the next action. I separate ‘this is wrong and here is the failing case’ from ‘this is a preference’ explicitly, because blending them makes the real defect negotiable and the preference feel mandatory. I lead with the most severe item rather than working up to it, since people act on the first thing they read. And I make it falsifiable — a reproduction, a line reference, a measurement — so we are discussing evidence rather than taste. When I am wrong, I say so in the same place I said the original thing, immediately: a quietly dropped bad finding is worse than the mistake, because people keep acting on it.

Why this role looks different

These four focus areas — review someone else's code, design problems and tests, reason about architecture, write structured feedback — describe someone who evaluates and documents engineering work rather than only shipping it. That is the profile for authoring technical assessments, reviewing AI-generated code, or building evaluation content. Inference — the role description was not supplied. It is worth asking in your questions, and if it is that, your Turing AI-eval material and your evaluation-rails work are the centre of your fit, not a side note.

08 · Questions to ask

What to ask when Zara turns it around

An AI interviewer will ask if you have questions, and the answer is scored. These are ordered — ask the first two if you only get two.

  1. 01

    What is being reviewed — human code, AI-generated code, or candidate submissions?

    The four focus areas fit all three, and the answer changes which of your stories leads. Ask it early.

  2. 02

    What does the written deliverable look like — a review comment, a rubric, an assessment, a design document?

    ‘Technical Writing & Structured Feedback’ being scored means there is a written artefact. Find out what it is.

  3. 03

    How do you currently tell a good review from a bad one?

    A senior question: it asks about their evaluation of evaluation, and it is the same question you answered when you built rubrics.

  4. 04

    Is there an existing quality bar written down, or is establishing it part of the role?

    Tells you whether you are applying a standard or authoring one — a very different job.

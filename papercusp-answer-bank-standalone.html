Turing · coding challenge · added 21 September 2026

Two timed exercises: review first, then implement

Assessment snapshot

The test page lists a 20-minute Code Review Task followed by a 30-minute Code Implementation Task. The recruiting email gives a deadline of 12:00 noon Pacific Time on Monday, September 21, 2026. The exact prompt and language are not included here, so this section prepares the operating method rather than guessing the hidden question.

T1 · Code review 20 minutes maximum review → prioritize → explain

Your job is not to rewrite the code. Your job is to find the highest-risk behavior, explain why it matters, and make the fix obvious.

A short review is scored on signal density. Five precise findings beat fifteen speculative comments.

0–2 min
Read the goal, inputs, outputs, and surrounding tests.
2–10 min
Trace the happy path and boundary cases.
10–15 min
Check errors, state, security, and complexity.
15–18 min
Rank findings by user impact and confidence.
18–20 min
Write a concise summary and recommended next step.
Review in this order
  1. Correctness: Does the code satisfy the stated behavior for normal and boundary inputs?
  2. Failure behavior: What happens for empty, missing, malformed, duplicated, or unexpectedly large input?
  3. State and side effects: Can partial work leak, mutate shared state twice, or leave a resource open?
  4. Security and privacy: Is untrusted input used in a query, command, path, log, or authorization decision?
  5. Complexity: Is there an avoidable nested scan, repeated I/O, unbounded loop, or memory-heavy copy?
  6. Tests: Is the risky behavior covered, and does the test assert the outcome rather than merely exercise the line?
Use this finding format

Severity + location → concrete failure → why it matters → smallest fix. Example: “High — the lookup occurs before the input is normalized. A blank key reaches the map and returns the default record, so an invalid request is treated as valid. Normalize and reject the empty key before lookup; add an empty-input test.”

Avoid

Style preferences presented as defects, comments without a failure mode, vague “this could be cleaner,” and a long list with no priority. If you are uncertain, label it as a question instead of overstating it.

Close the review with three sentences

“The main risk is ... because .... I would fix ... first, then add tests for .... The remaining comments are lower priority and can follow once the behavior is correct.”

Practice drillTake one small function from a real project. Set a 20-minute timer. Submit only three findings: one correctness issue, one failure/edge-case issue, and one maintainability or performance issue. Each finding must name the failure it prevents.

T2 · Code implementation 30 minutes maximum clarify → build → test

Make the smallest correct implementation you can explain, then spend the last minutes proving it works.

The trap is using the whole clock to code and submitting without checking the cases that define correctness.

0–3 min
Restate the contract and write down assumptions.
3–7 min
Choose the simplest suitable data structure and complexity.
7–22 min
Implement the happy path plus validation and clear helpers.
22–27 min
Run examples and test empty, boundary, duplicate, and invalid cases.
27–30 min
Read the diff, remove accidental complexity, and submit.
Before typing
  • What exactly is the input and output?
  • Are inputs allowed to be empty, duplicated, negative, null, or unsorted?
  • What should happen on invalid input: reject, skip, default, or return an error?
  • What complexity is reasonable for the likely input size?
  • What is one example that would distinguish a correct solution from a plausible wrong one?
Implementation habits that score well
  • Use names that expose the invariant: seen, remaining, bestIndex, or normalizedInput.
  • Keep validation at the boundary and the core algorithm focused.
  • Prefer one clear pass over clever abstractions unless the prompt requires more.
  • Do not change the public function shape or invent requirements that were not asked for.
  • If a trade-off is unavoidable, state it in a short comment or final note.
Do not spend the last five minutes

Refactoring names, adding a framework, optimizing before measuring, or polishing a solution you have not tested. A correct, readable solution with explicit edge-case behavior is the target.

Use the final-minute checklist

Does it compile or run? Does the simplest example work? What happens for empty input? What happens at the smallest and largest meaningful values? Did I accidentally mutate input, skip an item, or return the wrong shape? Is the complexity consistent with the approach I chose?

If you get stuck

Write down the invariant in plain English, solve one example by hand, and implement that behavior directly. If the optimized approach is uncertain, a correct straightforward approach plus a clear complexity note is usually stronger than half-finished cleverness.

Practice drillChoose a small array, string, hash-map, or interval problem. Give yourself 30 minutes, stop coding at minute 22, and reserve the final eight minutes for tests and a diff review. Repeat with a different problem until the time box feels boring.

T3 · Submission checklist before clicking submit 60 seconds
  • I answered the requested task, not a larger imagined one.
  • I can state the main review finding or implementation invariant in one sentence.
  • I checked normal input, empty input, boundary input, and at least one invalid or duplicate case where relevant.
  • I know the time and space complexity of the implementation.
  • I removed debug output, dead code, accidental secrets, and unrelated edits.
  • If something remains uncertain, I named the assumption instead of hiding it.

Part 1 · the core bank, revised

Standard interview questions, mapped to Papercusp

Fourteen questions that recur in almost every technical interview, each with a Papercusp answer that is specific and checkable rather than generic. Employer-neutral — nothing here is tied to a particular company or role. Each card now ends with a where it lives line: the files behind the claim, so you can re-read the source the night before instead of trusting a draft.

The recipe — every question in this bank

The constraint → why the obvious approach fails → what you did → the guarantee.

Most candidates give beat three only. The constraint is what makes the answer yours; the guarantee — what you did so it can't silently come back — is what separates an engineer from someone who closed a ticket. Keep it under ninety seconds and let them ask.

Every number below is taken from the code, not from memory. That precision is the whole advantage — don't round it up. One inflated figure invites a probe, and every probe after it lands on softer ground.

Q1 · CI/CD Near-universal for platform roles ~2:00 answer

Walk me through your CI/CD pipeline. How does code get to production safely?

Most answers are a tool list — “Actions, run the tests, deploy on merge.” Forgettable. Talk about what your pipeline does when it is red; that is where the engineering is.

the constraint → the feedback loop → watermark + freeze → the guarantee

“We have a constraint most teams don't: about a hundred AI agents commit into one shared branch, continuously — no feature branches, no pull requests. A background routine sweeps the tree and commits every three minutes; a gate has to certify that branch before it promotes to main and deploys.

The interesting failure was a feedback loop, not a slow test. The affected-test selector diffed against main, and main only moves when the gate is green. So the moment the gate went red, the diff base froze and every run got bigger — at worst 4,572 changed paths against a base 3,868 commits behind, 75 workspaces and 105 test tasks, where the change that actually mattered was 5 workspaces and 23. Recovery cost scaled with the age of the outage, so it never self-healed. And the outage that motivated the work was failing on typecheck — the tests were never what broke.

Two halves to the fix. First, the selector diffs against a test-certified watermark — a git ref that advances only when the affected-test leg passes in full at that commit — instead of against main. Second, when the gate goes red we freeze: the first real red pins that commit as the candidate, fixes land on top, and each repair run re-runs only the tests still failing plus the tests whose related files changed. Anything that passed at freeze time and hasn't been touched is inherited, not re-executed. Re-cutting at tip after every fix is a treadmill — you re-admit the whole sweep and import breakage faster than fixes land.

And it fails safe in one direction only: anything we can't positively verify falls back to the full run. A silently narrowed run would hand you a false green, and that is the one outcome that has to be impossible.”

If there's room — the deploy half

“Past the gate it's closer to blue-green than canary: main fast-forwards to the green commit, a separate release checkout is pinned to it, health-checked, and auto-rolls back. No canary on purpose — a single-instance internal system has no traffic volume for a canary to tell you anything. Commit to live is minutes; we deploy several times an hour.”

If they push

“How is narrowing the run sound?”
Promotion never narrows — only selection does. Each verdict is rendered against its predecessor's anchor, so the chain composes back to the last green pin. Inheritance, not omission.
“What if a fix breaks something that was passing?”
It gets re-selected. A fix is a file change, and that change's affected radius pulls in the tests covering it — that's the “related files changed” half doing the work.
“Couldn't a partial run certify code nobody tested?”
Any run carrying a scope flag measured less than its full radius and is barred from advancing the watermark. The subtlety: the flag has two spellings — --changed-paths a,b and --changed-paths=a,b — and a naive substring check misses the second, so we reproduce the CLI's own parsing instead of approximating it.
“Isn't the frozen candidate just stale code?”
The freeze is the verdict anchor, not the work — the head being repaired converges forward onto the live branch when it's safe. Naming that cost first is the honest move.
“How do you stop two people fixing the same red?”
One queue, single ownership, a live status cell naming the holder. Measured before that: 37 agents, 97 attempts, one failure.
“Why a git ref for the watermark and not a database row?”
It's git's own primitive for a commit pointer — atomic, no extra dependency inside the gate's isolated checkout, and it cannot drift from the objects it names.
Don't say

“We run tests on every commit and deploy when they pass.” True of everyone.

Do say

Lead with the constraint. “A hundred agents on one branch” is the sentence that makes them lean in and ask a question only you can answer.

Q2 · TestingVery likely

How do you decide what to test? How do you know your tests are actually catching anything?

Everyone answers “unit, integration, e2e, aim for coverage.” Coverage is an input metric. Answer the second half instead.

wrong metric →the real check →the committed mutant →the silent-pass trap

“Coverage tells you a line executed, not that anything would have noticed if it broke. The question I actually care about is: has this test ever failed? A guard that has never failed is a guard you haven't tested.

So we made that checkable. There's a probe that deliberately breaks the thing under test and asserts the guard catches it. It refuses a mutation that changed nothing — a no-op mutant makes any test look strong — and it can run against the commit that actually preceded the fix, with a positive control that has to be present in both versions, so you're not guessing that the current tree is still ‘before'.

The reason it runs against a copy rather than the live file is a real incident: the obvious idiom — back up, mutate, run the suite, restore — got a mutant committed, because our tree is auto-committed every few minutes and the suite held the file mutated across a sweep. The committed version had the fix's function defined but never called: syntactically clean, shaped exactly like a finished change.

The subtler version of the same problem is a suite that measures nothing and exits zero. We had commands selecting zero test files and reporting success. Now the runner refuses a run that matched no tests, the typechecker refuses a run that compiled no files — and one ordering rule: typecheck last, because a green test run carries zero type information, so if you typecheck, then edit a test, your clean verdict predates your last edit.”

“Isn't mutation testing too slow to run?”
It's a targeted probe at authoring time, not a matrix. You prove falsifiability at the moment you write the test — the only point where it's cheap.
“How do you pick what to test at all?”
Ask what a false negative looks like. If it's identical to success — an empty result, a zero exit, a ‘no failures' from a query against the wrong table — that's the test worth writing, with a positive control beside it.
“What frameworks?”
Vitest 4 with testcontainers for Postgres, Playwright for the browser suite, Cargo tests in the Rust shell, and a scenario framework for LLM behavior — exactly four, enforced by a lint that fails on a new ad-hoc script.

Q3 · DebuggingNear-universal

Tell me about the hardest bug you've had to debug.

They want your diagnostic method, not the bug. Pick one where the instrument was wrong — it's a level above “I read the stack trace.”

the symptom →why it was hard →the class →the guard

“The hardest ones share a shape: the instrument lies, and it lies in a way that looks like a clean answer.

Concrete one — a liveness check reported a process was gone. It wasn't; it was running and burning a full core. The check used a flag that didn't exist on that build of the tool, so it exited with a usage error, and the shell turned that non-zero exit into ‘gone.' When we counted the same processes the honest way there were thirteen of them. A well-formed answer to the question we asked, and completely false.

What makes that hard is there's no error to find. It's the same class as a search truncated before the match, a query against the wrong table returning zero rows, a test command that matched zero files and exited zero. Every one returns ‘nothing,' and ‘nothing' is indistinguishable from a real absence.

The fix wasn't the flag — it was the rule: never act on an empty result from an instrument that can't prove it measured. Run a positive control against something you know is there. Existence checks return counts or file lists, not truncated output. And the liveness check itself became a small tool that walks its own ancestor chain before matching — because a process-table search from inside a shell matches the shell's own command line, which contains the pattern you're searching for.”

“How do you catch that class in general?”
Ask what a false negative would look like. If it's identical to success, you need a positive control — run the same check against something you know is there.
“What changed so it can't recur?”
Not just the call sites — the shapes that produce it are refused at the tool gate before they run. Every incident is also a detector failure, so you fix the detector too.
“Did the guard itself have failure modes?”
Three, found in order: it matched its own shell; it matched agent launchers whose argument list carried a prompt naming the process; and — the one that grows with fleet size — it matched peers whose JSON payload mentioned the process by name. The last needed a structural discriminator: an argument that parses as JSON is data, not a command.

Q4 · ConcurrencyLikely for platform roles

Tell me about a race condition or concurrency problem you've dealt with.

Extends Q3 above. Two examples beat one, if the second is small and sharp.

the race →why convention failed →enforcement →the second race

“Two of them, same lesson.

First: dozens of agents editing one shared codebase. Two edit the same file and the second write erases the first — no error, no trace. We enforced it at the tool layer rather than by convention: a pre-write hook claims a lock before every edit, and a blocked writer is told who holds the file, why, and when it expires, so it can pivot instead of just failing. One detail I care about: the refusal is returned on the channel the agent reads. The earlier version signalled with an exit code and stderr, which the client shows to the human — so the agent never learned why it was blocked and just retried.

Second, smaller and I like it more. Adding a database migration meant picking the next number by listing the directory and adding one — two agents doing that concurrently pick the same number, and on our box that silently applies one file and dark-starts the other. Now the number comes from an allocator that reserves it under a Postgres advisory lock, so there's no gap to race in. The file is written with a suffix the migration runner ignores, so a half-written migration can't be picked up and executed while you're still editing it. And a second-order guard: the number is unique but the work may not be — after a gate red, several agents race to write the same fix — so the allocator refuses a near-identical filename reserved moments ago.

If a rule matters, enforce it in the system. A documented convention is the one that gets violated at 3am by whoever didn't read the doc.”

“Why not just serialize everything?”
Safe and useless. The point of per-file arbitration is that concurrent work stays concurrent — you only serialize the actual collision.
“What if a lock holder dies?”
TTL plus heartbeat — in the shared lock core the default TTL is three heartbeats with per-peer jitter, so peers don't all expire on the same tick. A lock that can't expire means one crashed process wedges everyone.
“How do you create-and-claim a unit of work without a race?”
One write. Creating a work-item with an assignee claims it in the same statement; the scheduler's pull is a FOR UPDATE SKIP LOCKED select, so two workers can never take the same item.

Q5 · DesignVery likely

Walk me through a design decision you're proud of. / How do you keep a large system from rotting?

Answer with a rule, not a component. It generalizes, which is what they're testing for.

the recurring bug →the reframe →the ladder →what made it stick

“The design I'm proudest of is a rule rather than a component.

We kept hitting the same bug in different costumes: a value in config or documentation that describes the code — a path, a flag name, an ‘is this enabled' boolean, a list of who emits an event. It's a second copy of a truth the code already owns, and it always drifts. Our worst instance: the event catalog listed which events had emitters, by hand. The single most-fired event in the whole system was recorded as unregistered — and fourteen subscribers were parked waiting on an event with no emitter anywhere.

So we wrote it as a ladder and you take the highest rung that fits. Derive it from the source. If you can't, pin it — the prose stays, but a build check fails when it diverges. If static analysis can't see it, attest it against a runtime ledger on a schedule. Only if none of those work do you hand-maintain it, and then you have to say why.

There are forty-seven of those pin tests now. My favourite pins one sentence in the docs — ‘the gate cuts its candidate from the local branch and never fetches' — to the code that resolves the candidate. The line numbers that sentence used to cite rotted within weeks while the claim stayed true, which is the whole failure mode in miniature: pin the expression, not the location.

What made it stick is that ‘a new config field restating what the code already knows' became a review smell people name out loud. It stopped being a bug we fixed and became a category we recognize.”

“Isn't deriving everything expensive?”
That's why it's a ladder. Pinning is one test. The expensive thing is rediscovering the drift six months later.
“How do you know the derived value is right?”
It fails the build when it disagrees with the source — a much stronger property than being correct on the day someone wrote it.
“Give me an example of rung three, attestation.”
Tool-guidance weight. A static read of the source under-counts tools that compose their description from constants, so the check runs against the runtime-projected catalog at registration time — and re-runs on every hot reload.

Q6 · Being wrongHighest-value answer here

Tell me about a time you were wrong, or made a significant mistake.

Heavily weighted, and most candidates give a disguised brag. A real one with a real mechanism is disproportionately convincing — and you have one.

the mistake →the pattern →the rule →the retraction

“A real one — and it happened three times in a single day, which is what made me take it seriously.

I reported a metric as evidence of a serious regression: a relevance score sitting at 0.03 against a documented threshold of 0.45, which read as 99.9% of results falling below the floor. It was wrong. That column stores two different things depending on which code path wrote it, and on one of those paths the maximum possible value is 0.033. I was comparing numbers on two different scales. The same day I'd also called a feature unimplemented based on one search in one file — it was implemented in a different file — and told someone a finding hadn't been recorded when it had, as a comment I hadn't read.

Same pattern each time: I asserted a conclusion from a single artifact without reading the thing that produced it. So the rule I hold now is before you report a number, find the code that writes it — confirm the units and the scale first.

And the tell is counterintuitive: the more damning a finding looks, the more likely you're misreading it. A real regression rarely produces a perfectly clean 99.9%; a suspiciously round number is usually a definitional artifact.

The other half is retraction. I'd already told someone it was real, so that has to be corrected immediately and in the written record, not quietly dropped — a bad finding you don't retract keeps directing other people's work.”

“How do you apply that under time pressure?”
It's cheap — reading the writer is one file. The expensive path is the one where someone spends a day investigating a mechanism that doesn't exist; we measured exactly that cost once, from a carried-forward hypothesis that had lost its hedging.
“Did anything change beyond your own habit?”
Yes. The surfaces that carry a claim forward now require you to tag whether it's something you observed or something you inferred, and a checkpoint can carry the claim with its re-check — { claim, recheck, verified } — so the next reader can falsify it instead of inheriting it.
“What did the ‘find the writer' rule catch most recently?”
A stored ‘which cgroup confines this task' column that was wrong for 1,326 of 2,373 agent rows — it recorded the spawner's cgroup because the launcher forks. The tell was calibration: the four process classes that derive the path instead of reading the column were wrong zero times out of 870.

Q7 · ObservabilityLikely

How do you know when something is wrong before a user tells you?

Skip the tool names. Three specific properties beat “we use Datadog.”

provenance →deltas not snapshots →the self-report trap →re-read, don't transcribe

“Three things I'd point at, and one habit.

First, our process list carries provenance. Standard tools tell you what's running; ours tells you who launched it, for which piece of work, and what it costs. That's the difference between ‘something is using four cores' and ‘this task is, and here's who owns it.' It also means we terminate by task identity rather than by process name — killing by name pattern has twice taken down the owner's live desktop — and identity can't hit a recycled process ID, which on our box wraps roughly daily.

Second, CPU usage is a delta, not a reading. A single sample gives you a lifetime average, so a process idle for an hour and saturated right now reads as idle. You sample twice and difference — and you measure the whole process tree, because the parent is usually at zero while a child burns a core.

Third, the one I'd emphasize: a health signal emitted by the thing being judged cannot detect that thing being saturated. A blocked event loop stops emitting its own heartbeat while looking perfectly asynchronous from the inside. If it matters, observe from outside the process.

The habit: live values are registered as cells you re-read at the moment you act, never transcribed from an earlier turn. There are about 150 of them — the gate verdict, the deployed commit, who owns an incident. The tool that reports a pipeline position hands you the re-read handle beside every number, so a correct observation can't become a confidently wrong report an hour later.”

“What do you alert on?”
Transitions, not levels. A level tells you where you are; a transition tells you something changed, which is what a human can act on. Waiting for a threshold crossing is a subscription on the cell, not a poll loop.
“How do you avoid alert fatigue?”
Anything that fires and self-recovers is still a bug — file it rather than silence it. A false alarm is a defect in the alarm.
“What about a value you can't currently measure?”
The cell says so in-band — not-measured, resolver-failed, insufficient-data — and each is branchable. ‘Unknown' is never allowed to read as zero or as fine.

Q8 · AI evaluationMost role-relevant

How do you evaluate whether an AI system is actually doing a good job?

For any AI-platform role this is the question that decides it. Almost everyone answers with benchmarks; answer with accountability, then have the benchmark answer ready as a probe.

the real failure mode →evidence →independence →what counts as proof

“The failure mode with AI output isn't wrong answers — it's confident, plausible ones. So the design goal is to make ‘done' a claim that has to be substantiated rather than asserted.

Three pieces. Completion requires evidence — what was tested, what the result was, how it was verified. A bare ‘done' gets reopened by an integrity audit.

For anything substantial there's a graded rubric: three to seven outcome criteria written against what was actually built rather than against the plan, and every rating cites concrete evidence.

And the part I'd want to talk about — the grader can't be the implementer, enforced structurally rather than by policy. The system resolves who authored the work and refuses any grader in that author's lineage, including one they spawned themselves. So you can't launch your own grader; you have to route the work to somebody independent. That constraint is annoying in exactly the right way.

We also distinguish kinds of evidence: a citation to code or a test counts as verification, with the file's content hash stored; a citation to a document explicitly does not. It's very easy to prove you wrote about something instead of proving you built it.”

“Isn't that a lot of process?”

Q11 · PerformancePossible

“The one that taught me the most wasn't a slow function — it was a transport choice.

The fix was to make the streaming transport the only path, with no runtime branch — one long-lived connection, and a drift-repair refetch every three minutes rather than every five seconds. Polling stayed as an explicitly degraded mode, never a default a branch could silently select.

The second class is admission, not compute. Heavy jobs on the box queue behind a shared admission ticket; a test run through that queue took fourteen minutes without starting under load, and 1.5 seconds through a direct path. The lesson was to route by what a job needs, not by what's convenient.

The discipline that came out of it: we keep a written list of the anti-patterns that have actually bitten us — serial file loops, a connection pool per item, duplicate React keys — and it's required reading before non-trivial changes. N2 · System designnewVery likely for platform roles~3:00 · whiteboard

Design a system where many autonomous workers share one codebase. How do you keep them from stepping on each other?

A design question you've actually built. Draw four boxes — claims, locks, events, presence — and name the invariant each one owns. The senior signal is saying which race each box eliminates.

claims: pull, don't push →locks at the write →events: declare, then latch →presence: one oracle

“Four pieces, each owning one invariant.

Work is pulled, never hand-assigned. Every unit is a row; a worker asks the scheduler for the next one and the claim is a single FOR UPDATE SKIP LOCKED select, so two workers can't take the same item. A leader shapes what a worker sees with a claim spec — a filter and a rank — but the spec can only narrow within global floors: it can never hand out a blocked or taken item. That means an idle worker with a non-empty queue is a spec bug, not something a human dispatches around.

Files are arbitrated at the write. A hook claims a lock before every edit; on contention the writer gets holder, intent and expiry back on the channel it reads, and pivots. Concurrent editing is safe by design, so nobody has to coordinate-before-editing out of fear.

Waiting is an event, declared first. The side that owns a completion declares the gate and gets back a key; the waiting side awaits that returned key — copied, never retyped, because a hand-typed key that drifts by one character never rendezvouses and the waiter sleeps forever. The declaration latches when fired, so a worker that registers after the fire is told immediately instead of waiting on something that already happened.

Liveness has exactly one oracle. Every surface that answers ‘is this worker alive' derives from one function, because when three surfaces compute it three ways you get a worker that is ‘dead' on one screen and holding a lock on another.

The thing to say out loud: none of these is a convention. Each is a refusal at a write.”

“Why pull instead of a leader assigning work?”
Assignment makes the leader the bottleneck and the failure point; a spec makes the leader's judgment durable and lets the worker self-select. Re-steering is a spec revision, not N messages.
“What about a worker that crashes holding a claim?”
Claims lease; presence marks a confirmed-dead owner with claims as suspect until cleanup reconciles. Nothing is silently reassigned while the holder might still be mid-write.
“How does a worker discover what to wait on?”
Its orientation call folds in the announced gates in scope — zero messages. If a key is already fired, the await returns already_fired, which is the latch saying ‘proceed now.'
“Where does git fit?”
Nowhere in coordination. A background routine commits the whole tree; workers never branch or stash to isolate ‘their' diff. Tree isolation is exactly the tool you reach for when you don't have locks.

N3 · Distributed systemsnewLikely

How do you tell a dead worker from a slow one?

The textbook answer is “heartbeats and a timeout.” Say why that's wrong first, then give the ordering of evidence. This is where you can cite two named algorithms without sounding like you're reciting.

heartbeat ≠ working →the evidence ladder →two axes, not one →φ-accrual + a second opinion

“Start with what a heartbeat proves: the process is scheduled. It doesn't prove the worker is doing anything. We had the ‘warm-dead' case constantly — heartbeat fresh, session ended — so the first rule was that heartbeat freshness is raw keepalive and never the verdict.

The verdict is one function with an evidence ladder, in order. A direct OS observation wins: a local probe that gets ‘no such process' is authoritative and beats any timer — a co-located dead worker is detected in seconds instead of thirty minutes. Then a hard-stale heartbeat. Then, before anything about reachability, a turn genuinely in flight wins: recent activity with no end marker means alive. Only after all that does ‘not reachable and idle' mean ended. And a confirmed-dead worker still holding claims is ‘suspect,' not ‘ended,' until cleanup reconciles — so nothing gets reassigned under a possibly-live write.

The bug that taught us the ordering: reachability and liveness are orthogonal axes. A one-shot worker mid-build never registers an inbox, so it isn't wakeable — and the old logic short-circuited ‘not wakeable, therefore ended' ahead of the activity check. Messages to a live worker were black-holed as ‘recipient dead,' and people wrote root causes about a crash that never happened.

For eviction across machines we replaced the fixed timeout with φ-accrual — a continuous suspicion level fitted to each peer's own inter-arrival jitter, so a naturally noisy peer isn't evicted for being noisy — and SWIM-style indirect probing before acting: ask a few relays to check; one ack clears it. High threshold for the expensive action, low threshold for a cheap hint.”

“What do you return when you try to wake someone and nothing happens?”
Not a boolean. woken:1 means queued, not picked up; a miss is split into recipient_dead (relaunch), recipient_alive_not_wakeable (mid-turn — retry), and recipient_dormant_scheduled (an armed loop with a known next fire — never grounds for reassignment). Collapsing those into one flag is how work gets double-placed.
“Why is the heartbeat from inside the process not enough?”
A saturated main thread stops every timer while looking perfectly asynchronous. The beat can't report the failure it's inside of. Observe from outside.
“Where does that failure detector live?”
In a standalone library with zero I/O and zero timers — the host injects the transport and a peer label. That's how it got unit-tested, and how it stays borrowable.

N4 · SystemsnewPossible · strong for infra roles

How do you keep background processes from leaking, and how do you kill one safely?

Most answers stop at “we track PIDs.” The answer here is confine the roots and let the kernel do the accounting — and a killing rule with a real incident behind it.

the no-escape property →kill by identity →the wrong column →the lint

“The property I wanted was: nothing our platform starts can outlive our ability to find it. Tracking PIDs can't give you that — a process double-forks, reparents to init, and it's gone from your list while very much alive.

So anything spawned to outlive its caller is enrolled as the root of a cgroup scope under one slice. Membership is inherited, so the kernel accounts for every descendant including the ones that reparent. Ordinary short-lived children need nothing. A lint fails a new un-enrolled detached spawn, and the handful of genuinely-not-ours lifetimes — a human's terminal window, a release cut that has to survive the restart it performs — sit in an allowlist with a stated reason each.

Killing follows from that. Never by name or pattern. A pattern kill has twice taken down the owner's live desktop and peer agents' virtual displays, because a pattern matches whatever happens to contain it — including the shell issuing the kill. We kill by task identity: the whole scope goes, and the row records what the process was, so if the PID has been recycled — which happens roughly daily on this box — the kill refuses with an identity mismatch rather than signalling a stranger.

And the recent one: the ledger stored which cgroup confined each task, and that column was wrong for 56% of agent sessions and 97% of shell jobs. The launcher forks, so the read returned the spawner's cgroup. The calibration was the four process classes that derive the path rather than read it — zero wrong out of 870. The stored answer is now a resolver, not a column.”

“What about relieving pressure without losing work?”
Freeze the scope rather than kill it. Same identity handle, reversible.
“What does an identity-mismatch refusal look like operationally?”
It's the rail working, not a bug. The row says ‘recorded identity X, PID now holds Y'; the operator re-lists and decides. A refused kill is cheaper than a wrong one every time.
“How does someone see what's running and why?”
One list that joins process to launcher, work-item and cost. The plain process table is still there for the whole host — it's the right tool for a different question, and the tool says so instead of answering wrong.

How would you design recurring / scheduled work in a service?

“Two execution mechanisms and one place to declare, and the rule is that nobody adds a third.

N7 · AI platformnewLikely for agent roles

How do you handle context limits and memory in long-running agent sessions?

Everyone says “summarize.” The interesting answer is what summarization breaks, and the one failure — manufactured authority — that most people haven't seen yet.

write-through, not flush →index, not dump →the telephone game →provenance the text can't fake

“Three principles and one bug.

Write through; don't flush at the end. A conclusion goes to its durable surface the moment it forms — a checkpoint on the work-item, a standing fact with a declared lifetime, a decision on the plan. Compaction then finds the state already parked. The summary itself is an index into live sources to re-verify, not a self-contained dump, because in a live multi-agent system it's stale the moment it's written.

The transcript survives. Compaction loses context, not data. Every prior turn is on disk and indexed, scoped to the agent's whole identity chain, so a successor retrieves what was dropped instead of re-deriving it.

The bug: attribution rots first. We traced one directive end to end — an agent wrote ‘do not resolve this until the UI pass is done' as its own note-to-self. The same mechanism pointed at a risky action manufactures false permission, which is worse.

So provenance is mechanical now. The ledger decides, never the text. A directive is only the owner's if it traces to a turn stamped human; anything else is tagged as self-imposed or inferred and can't be promoted by re-summarizing.”

Per-result caps are pinned to the hop floor on purpose; a bigger window doesn't buy a bigger result, it buys more stale results. The fix is reduction at the source, not capacity.

One call re-delivers structurally what prose loses: the held work-items' checkpoints, whether a self-wake is armed, and the pointer to its own searchable transcript — with the transcript force-indexed first so the pointer is fresh.

What does the managed sandbox actually enforce?

Also distinguish containment types: a cgroup provides process/resource accounting and control; it is not, by itself, a filesystem or network sandbox. A generic shell can perform work that a typed file or domain tool would reject unless its actual credentials and OS permissions prevent it. Command-string matching helps catch known mistakes but cannot prove the behavior of arbitrary programs.

Is deny-by-default already built, or would it have to be built?

Built and wired. The gap is configuration. This is worth separating carefully in an interview, because “we have no enforcement” and “we have enforcement that is barely configured” sound similar and call for completely different work — the second is an afternoon of policy authoring, the first is a quarter.

The shared dispatcher runs a fixed step order, and four of its steps are authorization. default-deny refuses any tool that declares no gate at all — no capability, no roles, no authorizer — unless it is explicitly marked public; the host wires this on, and it is deliberately not bypassable, because an ungated tool is a declaration gap rather than a trust question. Then a per-tool role allowlist, a per-principal capability check, and the capability envelope. tools:invoke, the generic dispatch route, goes through the same stack, which matters: a client-side tool ban that a generic dispatcher can route around is theatre.

The envelope supports both directions. A role can carry deny globs, and it can carry an allow list — and the allowlist branch is implemented, so a non-empty allow list means anything unlisted is refused. Turning a role deny-by-default is filling in one field, not writing a subsystem.

What I measured on 9 September: papercusp-capability-envelope resolves true with no override row, so the gate is armed and running at its code default. But the per-role table carries deny entries for only three roles; every other autonomous role is default-allow under a universal protected floor of raw secret reads and process kills. So the honest sentence is that the enforcement point is live and the policy authored into it is thin.

The design detail I would actually lead with is the exemption. The envelope deliberately skips superuser and power-user callers — the stated reasoning is that the policy is a safety net precisely where there is no human. That is a defensible choice, but it was keyed to the wrong predicate for one population: an autonomous implementer that needs superuser identity for other reasons inherits the exemption too. Rather than punching a hole in it, there is a second, differently-shaped gate — a launch-declared session confinement that runs before the exemption and holds regardless of privilege. Its two guarantees are structural rather than procedural: it cannot be bypassed by privilege because it never receives privilege — the decision function takes no context, no role, no superuser flag, so there is no check to get wrong — and it cannot widen because it has no allow dimension at all, only a deny list. Removing the dangerous vocabulary beats policing its use. State its status precisely: implemented, tested and wired into the dispatch seat, but zero confinements have ever been declared — the store holds one empty per-workspace container. The transferable part is the design pattern, not a running deployment, and saying so is what keeps the rest of the answer credible.

“I'd give a run an explicit execution envelope: allowed actions, a deadline, an agreed spend ceiling, tool-call and retry budgets, and a limit on concurrent side effects. Those are enforced by the runtime and workers; a prompt asking the model to be economical isn't enough.

G8 · Failure containment60–90 seconds

What happens when an agent goes wrong after it has already started taking actions?

contain →reconcile →repair →regression test

“First I contain the scope: suspend the affected agent or tool version, revoke the relevant credential if needed, and stop new side effects. A kill switch has to be enforced by the workers, not just remove a button from the UI.

Then I reconcile each in-flight action using its stable ID and the downstream system's receipt. A timeout means the response was lost or late; it does not tell us whether the action happened. I'd retry only where the operation is idempotent or reconciliation establishes that the original did not complete.

For committed actions, use a compensating change where the business permits it. You can't unsend an email or erase what someone already saw, so do not promise rollback where none exists. “Can you guarantee exactly once?”

A clear stopped/partial/unknown-outcome state, what completed, what did not, and the next safe action—not a success toast because a request was accepted.

Storage

“Why Postgres for everything? Why not just files?”

“Because every state file eventually became a second store that disagreed with the first. Postgres by default, schema only through migrations — 920 of them — and no runtime CREATE TABLE, so the schema can't be invented by whichever process booted first.”

Concurrency · a favourite

“How do you stop two agents picking the same migration number?”

“An allocator reserves it under a Postgres advisory lock instead of listing the directory and adding one — that read-then-write gap is a guaranteed collision at this concurrency. It hands back a .DRAFT filename, and the runner only ever applies *.sql, so a half-written migration is invisible to the auto-apply until you deliberately rename it.”

“Where do secrets live?”

“Never in the tree. Four platform provider keys go through one save-key verb into injected config outside the repo, and everything else is refused. A pre-write hook scans content before the write lands, so a secret pasted into a file never becomes a commit that has to be scrubbed from history.”

Process control

“What's the thing you're proudest of building?”

“Killing a process by identity instead of by name. pkill -f twice killed things it shouldn't have — the pattern matched the wrong process, including the shell running the search. PIDs wrap about daily here under load, so ‘kill 48213' is a coin flip.”

AI2 · Overfittingmicro1 · AI Engineer track~1:15 answer

What are the most effective strategies for optimizing deep learning model performance and reducing overfitting?

“The first strategy is measurement: a held-out set the model never touches, split by time when the data has a time axis, so the validation number means what you think it means. AI6 · Imbalanced datamicro1 · AI Engineer track~1:30 answer

Part 6 · durable workflows

Saga cleanup that survives a restart

A saga is a long operation split into local steps T1…Tn, each paired with a compensation C1…Cn that undoes its effect in business terms. There is no global transaction, so a crash can land between any two effects. For cleanup to survive a restart, three things must hold. Its progress is durable. Every step and compensation is safe to run twice. And something other than the crashed process is guaranteed to finish the job.

Grounded in Papercusp's DBOS durable workflows and its workspace-host lifecycle runner, re-checked against the tree on 22 September 2026. G8 (recovery & containment) covers the outward-facing half: reconciling actions whose response was lost.

The thirty-second answer

“Four properties. One: every step writes its state to a durable log before and after its side effect, so the truth lives in the database, not the process. Two: every step and every compensation is idempotent, because recovery is at-least-once. That means a deterministic idempotency key, or a step written as ‘reach this state’ instead of ‘do this action.’ Three: on boot, a recovery pass finds every saga that hasn't finished and resumes it, forward or backward, through the same code path as a normal run. Four: an independent reaper sweeps for tagged resources that no live saga owns, because the log can be wrong. Add fencing so a zombie worker can't act, and a terminal needs-human state so nothing retries forever.”

SG1 · RestartnewThe opening question~1:45

How does a saga-based system clean up after itself if the process dies halfway through?

This opens most durable-workflow rounds. They're listening for “durable log, at-least-once, idempotent,” not for the word “saga.” Bring up the gap between the side effect and the checkpoint before they do.

state in the DB, not memory →recovery scans unfinished sagas →same code path →at-least-once ⇒ idempotent

“The process can't be trusted to clean up after itself, because in the crashes that matter no handler runs: kill -9, the OOM killer, a lost host. So the saga's progress lives in the database. Each step records that it's starting, performs its side effect, then records that it finished.

On boot, a recovery pass finds every saga that hasn't reached a terminal state and resumes it. If the failure was transient, it continues forward. If a step failed permanently, it runs the compensations backward from the last completed step. The key design choice is that recovery isn't a separate cleanup script. It's the same state machine re-entered from its last checkpoint, so every normal run exercises it too.

The consequence is at-least-once execution: whatever step was in flight at the crash runs again. So every step and every compensation has to be idempotent. That's the whole trick.

We use DBOS for this. Each step's output goes into an operation_outputs table. After a crash, DBOS finds the pending workflow, replays the completed steps from their stored outputs without re-running them, and re-executes only the step that was in flight.”

“Why not exactly-once?”
Exactly-once across your database and an external system needs both to commit atomically, and they don't share a transaction. At-least-once delivery plus idempotent effects gets you an exactly-once outcome.
“Who runs the recovery pass?”
Whichever instance boots against the same system database with the same app version. Pin the version: resuming an old workflow on changed code is its own failure (SG12).
“Forward or backward recovery?”
Forward by default, because most restarts should simply finish the job. Compensate only when a step fails permanently or a business rule says abort.

SG2 · IdempotencynewTechnique, not definition~1:30

What makes a cleanup script idempotent? Give me concrete techniques, not the definition.

Everyone can define idempotent. The senior answer is a set of techniques, plus the ways cleanup quietly stops being idempotent.

converge, don't replay →absent = done →deterministic identity →conditional transitions →never target by name

“Five techniques. First, describe the end state instead of the action. ‘Make sure the VM doesn't exist’ is idempotent; ‘delete the VM’ fails the second time. The runner observes what's actually there, compares it with the desired state, and acts only on the difference.

Second, absent counts as done. A 404 on a delete is success for a cleanup step. Our workspace-host runner records each resource as planned, applied, unchanged or absent, and absent counts as settled.

Third, deterministic identity. Name or key each resource from the saga ID and the step, so a second run finds the first run's resource instead of creating a twin.

Fourth, conditional state transitions: update … set state='compensated' where state='applied'. On a second run that updates zero rows, and the step moves on.

Fifth, never target anything by pattern. We learned that one the hard way: pkill -f on a binary name twice killed the owner's live desktop window and other agents' virtual displays. Cleanup now kills by a recorded task identity, meaning the whole cgroup, and refuses if the PID has been recycled.”

“What breaks idempotency in practice?”
Appends and counters with no dedup key, created_at = now() in an upsert, triggers that fire on every call, and a cascade delete of something the next run recreates.
“Is DELETE always idempotent?”
The resulting state is; the side effects may not be. Audit rows, emitted events and returned counts can all differ on the second call. Judge the effects, not the verb.

SG3 · Crash windownewSeparates practice from reading~1:45

Where can the crash happen, and which window is the dangerous one?

This separates people who've run sagas from people who've read about them. Draw a timeline with three marks (intent, effect, checkpoint) and point at the gap between the last two.

intent → effect → checkpoint →the gap after the effect →observe, don't assume →a timeout means “unknown”

“Put three marks on a timeline: record intent, perform the effect, record the checkpoint. A crash before the effect is harmless, because recovery just runs it. A crash after the checkpoint is harmless, because recovery skips it. The dangerous window is after the effect and before the checkpoint. The world has changed, and your log doesn't know it.

You can't close that gap with a transaction, because the effect lives in someone else's system. So you make the gap survivable. Pass an idempotency key the provider deduplicates on, so the retry is a no-op. Or check before you act: ask the provider whether a resource with this key exists, and if it does, record it instead of creating another. If the effect is a message, use the outbox pattern. Write the message in the same database transaction as the state change, and have a relay deliver it at-least-once.

Timeouts follow the same logic. A timeout doesn't mean the call failed; it means you don't know. Reconcile using the key before you retry or compensate. Treating a timeout as a failure is how you refund a charge that never happened, or retry one that already did.”

“Why record intent if the key deduplicates anyway?”
So recovery knows there's something to look for. Without an intent row, a resource created just before the crash is invisible to the saga, and only a reaper can find it.
“Outbox, or publish to the broker directly?”
A direct publish has the same gap as any other effect. The outbox moves the gap inside one database transaction, where it disappears.

SG4 · KeysnewScope is the real question~1:30

How do you choose an idempotency key, and how do keys go wrong?

Tests whether you know the scope trade-off. Too broad, and a legitimate second operation gets swallowed; too narrow, and nothing is ever deduplicated.

derive from durable identity →never time or random at retry →one key = one intended effect →bind the payload →retention ≥ recovery delay

“A key identifies one intended effect, so you derive it from durable facts about that intent, never from the attempt. Ours for workspace-host operations joins the workspace, host, target revision, operation ID and action. Retry that operation a hundred times and it's still one key. Upgrade to a new revision and you get a new key, because that's a different intended effect.

Three failure modes. If you generate the key at retry time, from a fresh UUID or a timestamp, every retry looks new and deduplication never fires; if you need a random ID, generate it once and persist it before first use. If you scope it too broadly, say just the host, a legitimate second upgrade gets discarded as a duplicate. If you scope it too narrowly, say by including the attempt number, it defeats the purpose.

Two details people miss. Bind the payload: if the same key arrives with a different body, reject it instead of returning the old result. And the provider's deduplication window has to outlast your longest recovery delay. If you're down for two days and the provider forgets keys after 24 hours, the retry becomes a duplicate.”

“How do keys stay stable across a replay?”
Derive them from workflow inputs and step identity, never the wall clock. Our crash-resume test keys each turn as slug:feature:role:t<turn>, so a recovered process computes byte-identical keys.
“What if the downstream API has no idempotency support?”
Check before you act, using a deterministic name or a searchable tag, and hold a lease on the saga so two runners can't race the check.

SG5 · CompensationnewThe trap question~1:30

The compensation itself fails, or the process dies halfway through the rollback. Now what?

“Roll back the rollback” is the wrong answer. They want to hear that compensations are real steps, retried until they succeed, with an honest terminal state.

compensation = a step with its own checkpoint →retry to success →you can't abort an abort →bounded, then needs-human

“A compensation is a step like any other, with its own checkpoint, its own idempotency key and the same retry rules. In our lifecycle runner, when a failed upgrade strands a host, the precomputed rollback runs as its own leg. It has its own checkpoint key, the step ID plus :rollback, and the same apply, reconcile and bounded-retry loop as a forward step. So a rollback interrupted by a restart resumes on the next turn, and it's never issued twice.

Compensations have to be written so that retrying eventually succeeds. You can't abort an abort, so there's no compensation for the compensation. Transient failures retry with backoff.

But the retries are bounded. Once the budget runs out, the saga parks in an explicit terminal state that says a human is needed, with the evidence attached and an alert raised. What you're avoiding is an infinite retry loop that looks like progress, or a catch-and-log that silently drops the problem.”

“What goes in the needs-human record?”
Which steps were applied, which compensations finished, the keys, the last provider responses and the exact next action. Whoever picks it up should be able to resume without investigating.
“Why give the rollback its own checkpoint?”
If it shares the forward step's row, recovery can't tell ‘step applied’ from ‘step applied, rollback half done.’ It will either skip the rollback or issue it twice.

SG6 · finally / trapnewBe humble here~1:30

Why not just put the cleanup in a finally block, or a trap in the shell script?

Those handlers are fine as a first line of defense. The point is knowing the two ways they fail, and that the cheapest cleanup is the one you designed away.

handlers don't run on SIGKILL/OOM →observers see the window →mitigation, not fix →isolate instead of undo

“Use them, but don't rely on them. They fail in two ways.

First, they don't run in the crashes that matter: kill -9, the OOM killer, a lost host. Only durable state plus recovery on the next boot covers those. Our crash-resume test is built around this. The child process deliberately SIGKILLs itself in the middle of a step, so no destructors run, and a second process has to finish the job from the database.

Second, and less obvious: even a handler that runs perfectly can't hide the intermediate state from someone who's watching. We had a mutation probe that backed up a file, mutated it, ran the tests, then restored it from a trap. The trap fixes the death race. It doesn't fix the sweep race. A background job commits the whole working tree every few minutes, so it could commit the mutated file mid-test even when nothing went wrong. So we stopped mutating shared state. The probe now mutates a copy outside the tree, and there's nothing to clean up.

The general lesson: the cheapest cleanup is the one you designed away by isolating the work.”

“So is trap useless?”
No. It's a mitigation for process death in code you don't control. Label it as one and keep the durable path.
“Where else do you isolate instead of undo?”
The release checkout and the green-checkpoint test tree are reset and cleaned at the start of every run. Cleanup becomes a converge at the start of the next run, not an undo at the end of the last one.

SG7 · FencingnewDistributed-systems probe~1:45

After a restart, two workers both think they own the same saga. How do you prevent double cleanup?

Name leases and fencing tokens. Then point out that “the old worker is dead” is an inference, not a fact.

one owner via dedup or lease →fencing token checked by the store →“dead” is an inference →suspect, not reassigned

“Two layers. First, make two owners structurally hard. Provisioning runs as a DBOS workflow with a deduplication ID. That replaced a hand-rolled Postgres claim that needed a TTL and a 30-second heartbeat. A pending workflow holds its dedup slot for its whole lifetime, with no keepalive to miss.

Second, assume that fails anyway, and fence at the write. Every owner carries a token, an epoch or the operation ID, and the store rejects writes that carry a stale one. Our lifecycle store works that way: it refuses an event whose operation belongs to a different host. A worker that wakes up after a GC pause or a network partition can believe whatever it likes; its writes bounce.

And be careful what you call dead. A missed heartbeat means the owner is late, not gone. When an owner is confirmed dead, we mark its claims suspect until reconciliation runs, instead of handing them to someone else while the original might still be mid-write.”

“Why isn't a lease with a TTL enough?”
Clocks and pauses. A holder can believe its lease is still valid after it expired. Only a check at the resource, against a monotonically increasing token, closes that gap.
“What about ownership by PID?”
PIDs wrap; here they recycle roughly daily under load. Identity has to be the PID plus its start time, or better, the cgroup. Our kill path refuses with identity_mismatch rather than signal a stranger.

SG8 · OrphansnewSecond line of defense~1:45

What if the saga's own log is wrong, and a resource exists that nothing records?

“The log is the first line of defense, not the only one. Logs get lost, a bug skips a write, someone creates a resource by hand. So every resource is tagged at creation with its owning saga and a creation time, and a reaper takes a census: everything tagged, minus everything a live saga claims.

The reaper has to be more careful than the saga, because it's working with less information. Its grace period is longer than any step's runtime, so it won't reap something whose checkpoint just hasn't landed yet. It quarantines before it deletes, and it runs a dry run first so a person can review the list.

We have a real example of why. A bug in our lifecycle runner dropped the provider identity when it recorded a snapshot checkpoint. So the host never registered its own recovery point, and every later destroy census flagged that snapshot as an untracked orphan. The cleanup machinery was pointing at the host's own backup. The fix was to record identity at creation. The lesson is that ‘I don't recognize this’ is a reason to investigate, not to delete.”

“How long should the grace period be?”
Longer than the slowest step plus the recovery delay, and measured, not guessed. A reaper that reaps a resource during its creation window creates the very orphan it was built to find.
“Should the reaper compensate, or just delete?”
Delete only things with no business meaning, like temporary VMs or scratch directories. Anything with business meaning goes back to the owning saga's compensation, or to a human.

SG9 · OrderingnewDesign maturity~1:30

How do you order saga steps so a rollback is possible at all? What about effects you can't undo?

They want to hear “pivot transaction,” compensations prepared and validated in advance, and honesty that some undo is only possible in business terms.

reversible first →the pivot →forward-only after →validate the undo before destroying →business undo, not literal

“Order steps by reversibility. Everything you can compensate goes first. Then comes the pivot, the point of no return. After the pivot, steps must be retryable to success, because you're only moving forward.

Prepare the compensation before you need it, and validate it before the destructive step. In our lifecycle runner, every upgrade carries a rollback target, and the provider validates it before the destructive step runs. If you only discover the rollback image is missing after replacing the running one, you never had a rollback.

And a compensation undoes the business effect, not the literal operation. You don't delete a charge, you issue a refund. You can't unsend an email, so either you send a correction or you put the email after the pivot. Be explicit with the business about which steps are truly reversible, instead of promising a rollback that doesn't exist.”

“Where does ‘send the confirmation email’ go?”
Last, after the pivot, sent from an outbox with a dedup key. Then a restart re-delivers it at-least-once, and no email goes out for a saga that later compensates.
“What if a step fails after the pivot?”
Retry it, and escalate to needs-human if retries run out. Undoing past the pivot is a new business process, not a rollback.

SG10 · ProcessesnewOS-level orphans~1:30

Your saga spawns processes. How do you guarantee none of them leak after a crash?

The OS-level version of the orphan question. Say “cgroups,” and explain why process groups and PIDs don't hold up.

enroll the root →the cgroup captures every descendant →kill the subtree →identity, not PID →never by name

“Confine the root processes and let the kernel track everything below them. Any process meant to outlive its caller goes through one spawn helper. The helper records it in a task ledger and gives it its own cgroup, and a linter fails the build on any new detached spawn that skips it. Children inherit the cgroup. That includes processes that double-fork and get reparented to init, which process groups and parent-PID tracking both miss.

Cleanup kills the whole cgroup subtree. The cgroup outlives the process that launched it, so after a crash the subtree is still addressable as one unit.

Two rules came from incidents. Never kill by name: pkill -f matched the owner's live desktop window and other agents' displays. And never kill by bare PID. PIDs wrap about daily here, so the kill path checks identity and refuses with identity_mismatch rather than signal whatever process inherited the number.”

“Why not a process group and kill(-pgid)?”
Any child can call setsid and leave the group. An unprivileged process can't leave its cgroup.
“Kill or freeze?”
Freeze first when you want to keep the evidence, or relieve pressure without losing work. Kill once you've decided.

SG11 · TestingnewBe concrete~1:45

How do you prove the system actually survives restarts?

This is where to be specific. Describe a crash-injection test and the invariants it checks, not “we have integration tests.”

kill -9 at every boundary →recover against the same DB →assert invariants →run everything twice →a fake provider that counts calls

“Crash injection at each boundary, with invariant checks afterward. Ours is a real test in the suite. A child process boots DBOS, starts a pipeline, and records the invocation and the spawn row. Then it SIGKILLs itself in the middle of a worker step: a true crash, no destructors. A second process boots against the same system database and the same app version, DBOS recovers the pending workflow, and the test asserts it finishes with the right result. The fake runner behaves identically in both processes, because its decisions come from the replay-stable idempotency key.

Generalize that. Kill before the effect, after the effect but before the checkpoint, and in the middle of a compensation. Then assert the invariants: one resource per key, no orphans, the saga ended in a terminal state, and each compensation reached the fake provider at most once, which the fake records.

Add a cheap property test: run every step and every compensation twice, and assert the second run changes nothing.”

“Why the same app version?”
Recovery replays the workflow's history against the code. Different code can take a different path and diverge from its own checkpoints. That's a versioning problem, and you test it deliberately and separately.
“Chaos testing in production?”
Only once the invariants can be checked. Chaos without an invariant check just produces restarts you can't evaluate.

SG12 · Durable executionnewTemporal / DBOS fluency~1:45

You're using a durable-execution engine like Temporal or DBOS. What catches people out?

Determinism, versioning and step granularity are the standard answers. A specific trap you actually hit is what makes the answer credible.

deterministic workflow body →versioning in-flight runs →step granularity →the silent nested-step trap

“Four things. First, the workflow body must be deterministic. Wall-clock time, random numbers and I/O belong inside steps, whose results are checkpointed. Otherwise the replay takes a different branch than the original run did.

Second, versioning. If you change workflow code while instances are in flight, recovery replays old history against new code. Either version the workflow or drain it before you deploy.

Third, granularity. Make steps too coarse and a crash re-runs a lot of work; too fine and you pay for a checkpoint on every trivial call. Our provisioning deliberately runs a whole phase as one step, because the provision script is idempotent at the phase level. Re-running setup is the recovery path.

Fourth, the one that got us. In DBOS, calling runStep from inside another step silently degrades to a plain function call: no checkpoint, no error. Our git-sync phases ran inside a single engine step that way, so their progress was invisible. The helper now checks that it's inside a workflow and not already inside a step before it checkpoints.”

“What did the nested-step bug look like from outside?”
The executor reaper treats checkpoint rows as proof of progress. With the phases uncheckpointed, a long git-sync looked like one opaque fire with no output, which you can't tell apart from a stall.
“Temporal or DBOS?”
Temporal is a separate service with its own history store. DBOS is a library that checkpoints into the Postgres you already run. For a Postgres-first system, the library costs far less to operate.

SG·RF · Rapid-firenewOne-breath answers~0:15 each

Short saga probes and the one-breath answer to each.

“Saga or two-phase commit?”
2PC holds locks across services and blocks if the coordinator dies. Sagas give up isolation to stay available. And services you don't own won't join your 2PC anyway.
“What isolation do sagas lose?”
Other transactions can see intermediate state. Countermeasures: semantic locks (a ‘pending’ status), commutative updates, and re-reading values before acting on them.
“Orchestration or choreography?”
Orchestration when compensations have to run in order and you need to answer ‘what state is saga X in?’ with one query. Choreography for loosely coupled reactions where each consumer is independently idempotent.
“Is exactly-once possible?”
An exactly-once outcome, yes: at-least-once delivery plus idempotent processing. Exactly-once delivery across systems, no.
“Where does saga state live?”
In the same database as the business data when possible, so the state change and the outbox row commit together.
“How do you know recovery is working?”
Track sagas by state and age, alert on anything unfinished past its expected duration, and watch the count of needs-human sagas, which should trend toward zero.

The three points to make in 30 minutes

1 · You've built Neo's hard parts

Papercusp runs about a hundred agents on one production codebase. The hard work was the runtime: tool interfaces, recovery when an agent stalls, approval before risky actions, and checks that the work is actually done.

2 · Approve before apply is your default

In Neo, users watch the agent and approve operations. Papercusp makes risky operations dry-run by default, requires an explicit confirm, and has an independent grader review completed work before it ships. Same instinct as pulumi preview before pulumi up.

3 · You own production end to end

Before Papercusp you ran a commerce business for twelve years: over $1M a month, small team, on-call included. Gilad is a manager, so say plainly that you take ownership and know when to ask for help.

Early in the call: "Is this for the Neo / Agentic AI team, or another team?" The role is my best inference from Pulumi's open engineering posting; nothing in the invite names it. If it's another team (ESC, Cloud, IaC engine), lead with point 3 and use the durable-execution story.

04 · Your evidence for each responsibility

Neo ↔ Papercusp

Neo responsibilityWhat you built in Papercusp
Tool interfacesAn MCP catalog of roughly 550 tools. Each tool has guidance for when to use it, a budget for how much it adds to the prompt, and capped results with projections, so agents don't flood their context. Agents find tools by describing what they need.
Agent orchestrationFleets of agents working one codebase: plans broken into work items, file locks enforced before every edit, presence and liveness tracking, and waking a stalled peer when work is handed off.
Approve before applyDeploy operations are dry runs unless the agent passes confirm. Irreversible or outward-facing actions need owner approval. Every owner instruction is recorded and has to be closed with done or declined plus a reason.
Self-correction and feedback loopsA test gate decides what reaches main. When it fails, the failing candidate is frozen and fixes are added on top of it, so the gate converges instead of chasing a moving target. A fix isn't done until it has a guard that fails if the bug returns.
EvaluationScenario tests for agent behavior. Plans ship only after an acceptance rubric is graded by an agent that didn't implement the work. "Done" requires structured evidence: tests run, results, and how it was verified.
Watch the agent workA Tauri desktop app shows fleets, plans, and work items live, synced over server-sent events.
ReliabilityDurable workflows (DBOS) so long-running work survives a crash; idempotency keys; recovery verified with a real process kill.

05 · Answers to rehearse

Questions an engineering manager is likely to ask

"What was the hardest technical problem in Papercusp?"

Pick recovery: agents stall, crash, or lose context mid-task. The fix was to make durable state the source of truth rather than an agent's memory: work-item checkpoints, durable workflows, and idempotency keys, verified with a real process kill. For Neo, the same question is what happens when an agent is halfway through changing infrastructure. Expand from SG11 / SG3 in the Answer Bank.

"How do you make an agent safe enough to change production?"
  1. Plan, then apply: the agent proposes, and a human or a policy approves the changes that matter. Pulumi's preview step is ideal for this.
  2. Limit scope: give the agent only the tools and permissions the task needs, and enforce that in code at dispatch rather than in the prompt.
  3. Verify the outcome: check that the change actually did what was intended. A successful tool call isn't enough.
  4. Make it observable: a record the user can read of what the agent did and why.
"How would you evaluate an agent like Neo?"

Separate the layers. Grade single-tool calls on correctness. Run each capability area (migrations, compliance, cost) as scenario tasks in sandbox accounts, with checkable end states such as plan diffs and policy results. Then track trust signals in production: approval rate, rollbacks, and cases where a human had to step in. Lesson from Papercusp: before trusting a metric, check what writes it. Once we nearly made a decision from a number that was measuring the wrong population.

"Tell me about working with a team" / "How do you handle disagreement?"

Your business: a small team, you owned the systems, and you made calls with people who knew things you didn't. In Papercusp, decisions that affect other workstreams are recorded with a written rationale, so anyone can go back and check them instead of relying on someone's paraphrase. That habit carries over to people.

"Why leave building your own platform?"

Papercusp proved the ideas. You want to apply them where customers have real stakes, with a team and a product that already has users. You'd rather build the agent layer than also run the company.

"How do you use AI tools day to day?"

Directly: about a hundred agents work on your codebase, and you use Claude Code all day. Talk about managing them: breaking work down, giving each agent the right context, and deciding when to step in. (If this is the Gilad who wrote that post, that's his theme.)

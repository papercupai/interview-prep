Python gotchas that cost you points

Every one of these produces code that runs, returns a plausible value, and passes a casual read. That is exactly why they show up in review exercises: the grader is testing whether you spot a defect the interpreter will never complain about. Scan for these first, before you start reasoning about the algorithm.

The 60-second scan

Run this checklist over any snippet before you write a word

  1. Does any parameter default to a list, dict, or set? → shared-state bug, every time.
  2. Is there a slice ([:-1], [1:])? → off-by-one; ask what it drops.
  3. Does it mutate an argument the caller owns? → check the contract for "new list" / "do not modify".
  4. Is there an in against a list inside a loop? → O(n·m); should be a set.
  5. Does the contract say unique / no duplicates / sorted? → check that the code enforces it.
  6. Does a function mutate and return, or return None from .sort()/.append()?
  7. Is the container modified while being iterated?
  8. Are there falsy-but-valid inputs (0, "", []) hitting an or default or a bare if x:?

01

Defaults and shared state

The single most-tested family. All four are the same bug wearing different clothes: a mutable object created once and then shared.

Mutable default argument

Critical

Defaults are evaluated once, at def time — not per call. Every call that omits the argument shares the same object.

def add(item, bucket=[]):      # ⛔
    bucket.append(item)
    return bucket

add("a")   # ["a"]
add("b")   # ["a", "b"]  ← leaked from the previous call

def add(item, bucket=None):    # ✅
    if bucket is None:
        bucket = []
    bucket = [*bucket, item]
    return bucket

Use is None, not bucket or [] — the latter also discards a caller's legitimate empty list. Immutable defaults (None, numbers, strings, tuples) are always safe in the signature.

Say in reviewCritical — bucket=[] is evaluated once at definition time, so state leaks across calls. Use bucket=None and build the list inside the function.

Mutable class attribute

Critical

The same bug at class scope: one list shared by every instance.

class Cart:
    items = []              # ⛔ shared by ALL instances
    def add(self, x): self.items.append(x)

class Cart:                 # ✅
    def __init__(self): self.items = []

Dataclass field default

High

@dataclass raises on a mutable default, so people reach for the wrong escape. The correct one is default_factory.

@dataclass
class Job:
    tags: list = field(default_factory=list)   # ✅ fresh list per instance

Late-binding closures in a loop

High

A closure captures the variable, not its value at creation time. After the loop ends, every closure sees the final value.

fns = [lambda: i for i in range(3)]
[f() for f in fns]                  # [2, 2, 2]  — not [0, 1, 2]

fns = [lambda i=i: i for i in range(3)]   # ✅ bind at definition
# or: functools.partial(lambda i: i, i)

02

Copying and aliasing

[[0] * 3] * 3 makes three references to one row

Critical
grid = [[0] * 3] * 3     # ⛔
grid[0][0] = 1
# [[1,0,0], [1,0,0], [1,0,0]]   — all three rows are the same list

grid = [[0] * 3 for _ in range(3)]   # ✅

The inner [0] * 3 is fine — 0 is immutable. Only the outer repeat of a mutable element is the bug.

Every builtin copy is shallow

High

list(a), a[:], a.copy(), copy.copy(a) and {**d} all copy exactly one level. Nested containers stay shared.

b = a[:]            # top level copied
b[0].append(9)      # ⚠ still mutates a[0]
b = copy.deepcopy(a)  # ✅ when nesting matters
Say in reviewThe copy is shallow, so nested values remain aliased to the caller's data. Either deep-copy or document that nested structures are shared.

Augmented assignment into a tuple

Trivia

It both succeeds and raises — the list is mutated, then the tuple assignment fails.

t = ([1], 2)
t[0] += [3]     # TypeError … and t is now ([1, 3], 2)

03

Identity, equality, truthiness

is vs ==, and why is seems to work

High

CPython interns small integers (−5…256) and many short strings, so is passes on test data and fails in production.

a, b = 256, 256;  a is b    # True
a, b = 257, 257;  a is b    # False  ← same code, different answer

Use is only for None, True, False and sentinel objects. Use == for values. Also prefer is None over == None: == calls __eq__, which a class can override.

x or default swallows valid falsy values

Critical
def f(limit=None):
    limit = limit or 10      # ⛔ f(0) silently becomes 10
    limit = 10 if limit is None else limit   # ✅

Falsy-but-valid: 0, 0.0, "", [], {}, False. The same trap hides in if not items: when an empty list is a legitimate input.

if x == 1 or 2: is always true

High

Parsed as (x == 1) or (2), and 2 is truthy.

if x == 1 or x == 2:   # ✅
if x in (1, 2):        # ✅ better

any([]) is False, all([]) is True

Edge case

Vacuous truth. all(...) over an empty collection passes every validation you wrote — a classic empty-input edge case.

04

Iteration

Mutating a list while iterating it

Critical

The index advances while the list shrinks, so elements are silently skipped — no error.

for x in items:
    if bad(x): items.remove(x)     # ⛔ skips the element after each removal

items = [x for x in items if not bad(x)]   # ✅
for x in list(items): ...                  # ✅ iterate a copy

A dict or set is stricter: changing its size mid-iteration raises RuntimeError. Lists fail silently, which is worse.

Generators are single-use

High
g = (x for x in data if ok(x))
total = sum(g)
count = len(list(g))     # ⛔ 0 — g is exhausted

Also: len(g) is a TypeError, and the body doesn't run until you consume it — so exceptions surface at a surprising line.

zip truncates to the shortest input

High

Mismatched lengths lose data with no warning.

zip(a, b, strict=True)          # ✅ 3.10+, raises on mismatch
itertools.zip_longest(a, b)     # ✅ pad instead

Iterating a dict gives keys

Trivia

for k in d and sorted(d) both yield keys. Use d.items() when you want pairs. dict preserves insertion order (guaranteed since 3.7); set does not — never rely on set iteration order.

05

Silent returns and silent success

Operations that return a wrong-but-valid value instead of raising. These are the hardest to spot and the most rewarded to catch.

In-place methods return None

Critical
x = items.sort()       # ⛔ None
x = items.append(1)    # ⛔ None
x = sorted(items)      # ✅ returns a new list

Same family: reverse(), extend(), update(), add(). Convention: mutating methods return None; builtins that return a value leave the input alone.

Out-of-range slices clamp; out-of-range indexes raise

High
items = [1, 2]
items[5]      # IndexError — loud
items[5:]     # []         — silent
items[:-1]    # drops the last element, [] when len <= 1

This is why [:-1] bugs survive testing: on a one-element list they return [] rather than crashing.

strip() takes a character set, not a suffix

High
"example.com".strip(".com")    # ⛔ "exa"  — strips any of . c o m
"example.com".removesuffix(".com")   # ✅ 3.9+

d.get(k) returns None instead of raising

Medium

A missing key becomes a None that propagates several frames before failing somewhere unrelated. Use d[k] when the key is required, d.get(k, default) when it isn't — and never bare d.get(k) unless None is genuinely meaningful.

06

Numbers

Division and modulo floor toward −∞

High

Unlike C, Java, and Go. If you ported the algorithm, the negative branch is wrong.

-7 // 2     # -4   (C gives -3)
-7 %  2     #  1   (C gives -1; Python's result takes the divisor's sign)
int(-7 / 2) # -3   ← truncation, if that's what you meant

Float equality

High
0.1 + 0.2 == 0.3        # False
math.isclose(a, b)      # ✅
Decimal("0.1")          # ✅ for money

Integers never overflow

Worth saying

Python ints are arbitrary precision, so overflow bugs ported from other languages disappear — but so do the guards. Large-n arithmetic gets slow rather than wrong, which matters in a complexity discussion.

Hidden complexity

Each of these is correct code with the wrong asymptotics — exactly what the "Complexity" section of a review is for.

s += piece in a loopO(n²)"".join(parts)

Name both variables

Phrasing

Saying "O(n²)" when two collections are involved is imprecise and graders notice. Write O(n·m) where n = len(items) and m = len(allowed), then add "which is O(n²) when the inputs are comparable in size."

08

Scope and exceptions

Assignment makes a name local for the whole function

High
count = 0
def bump():
    count += 1      # UnboundLocalError — not a read of the global
def bump():
    global count; count += 1     # ✅ (or nonlocal in a closure)

Bare except: catches control-flow exceptions

High

except: swallows KeyboardInterrupt and SystemExit; except Exception: does not. Neither should be silent.

try: ...
except:        pass    # ⛔ un-killable, un-debuggable
except Exception as e: log.exception(e); raise   # ✅

return in finally discards the exception

Medium

A return or break inside finally silently replaces an in-flight exception, so the failure never surfaces.

09

Untrusted paths and traversal

A path that came from a request is hostile until it has been resolved. Python gives you primitives for this and never a one-call helper — knowing that is itself the answer.

Two independent holes, and they get conflated

Critical

Containment checks fail in two unrelated ways. Most wrong answers close one and believe they closed both.

.. escapesibling dir
startswith(root)passespasses
startswith(root + os.sep)passesrejected
is_relative_to(root), no resolvepassesrejected
resolve() + eitherrejectedrejected

Row three is the one that surprises people. is_relative_to is a lexical check over path components, and pathlib deliberately does not collapse .. — with symlinks in play, a/b/.. is not necessarily a. On its own it is no safer against traversal than startswith; it only closes the sibling-directory hole.

resolve() is the load-bearing step, not the comparison

Once both sides are resolved, every comparison form is correct — including a prefix check. Without it, none of them are.

from pathlib import Path

LOG_ROOT = Path("/var/log/app").resolve()

def _validated(path):
    resolved = Path(path).resolve()               # normalise .., absolutise,
                                                  # AND follow symlinks
    if not resolved.is_relative_to(LOG_ROOT):     # py3.9+
        raise ValueError(f"path escapes {LOG_ROOT}: {path!r}")
    return resolved

Three jobs in one call: collapses ..; makes relative input absolute; and follows symlinks, which kills a symlink planted inside the allowed directory. No lexical check can see that third one — it is the real argument for resolving over string work. strict=False is the default, so a nonexistent path still resolves and you validate before opening.

Pre-3.9: resolved.relative_to(root) in a try/except, or os.path.commonpath([realpath(p), root]) == root.

commonprefix is not commonpath

Critical

They differ by four characters, both live in os.path, and one of them is a security bug. commonprefix is a string function, and it fails open:

commonprefix(['/var/log/app-secrets/x', '/var/log/app'])  ->  '/var/log/app'   # == root: PASSES
commonpath  (['/var/log/app-secrets/x', '/var/log/app'])  ->  '/var/log'       # != root: rejected

The insecure one returns a value equal to your root, so the equality check succeeds and the traversal goes straight through.

Joining to a trusted root does not contain it

Costly

The reflex fix — “just join it under the root” — silently discards the root when the untrusted side is absolute:

Path('/var/log/app') / '/etc/passwd'         ->  /etc/passwd
os.path.join('/var/log/app', '/etc/passwd') ->  /etc/passwd

True in both pathlib and os.path. Validate the component first — or better, do not accept a path at all. Take a name, allowlist it, and build the path yourself so traversal is unrepresentable:

if not re.fullmatch(r"[A-Za-z0-9._-]+", name) or name in (".", ".."):
    raise ValueError(f"bad log name: {name!r}")
target = LOG_ROOT / name        # no separators possible

There is no stdlib helper — and saying so is the right answer

Interview

Python ships no general “is this path contained in that root” function. It gives you two columns that you compose:

normalisePath.resolve · os.path.realpath · abspath · normpath
comparePath.is_relative_to · relative_to · os.path.commonpath

⚠ abspath and normpath sit in the normalise column but are not substitutes for realpath: they collapse .. lexically and do not follow symlinks. Swapping one in is a real downgrade.

The stdlib does ship traversal defence — but only at specific dangerous operations, never as a general predicate: tarfile's PEP 706 filters (3.12+) with AbsolutePathError, OutsideDestinationError and LinkOutsideDestinationError; zipfile.extract and http.server.translate_path sanitise internally but expose nothing reusable.

Say in interviewThere is no stdlib helper — the idiom is two calls: resolve, to normalise .. and follow symlinks, then is_relative_to or commonpath to check containment. Python only ships traversal defence at the dangerous operation itself, like tarfile's PEP 706 filters, because whether to follow symlinks and whether to fail closed are application policy.

If you want to show depth: TOCTOU

Depth

Resolve-then-open has a race: between resolve() and open(), anyone who can write in that directory can swap a component for a symlink. The mitigations are os.open(..., os.O_NOFOLLOW) for the final component, or opening the root once and passing dir_fd= for everything under it. Raise it only if the directory is attacker-writable — correctly scoping it out of the threat model scores as well as fixing it.

10

Review phrasing that scores

Graders reward evidence, not vocabulary. Each finding should name four things.

The four-part finding

  1. Severity — Critical / High / Medium, so the reader can triage.
  2. Trigger input — the concrete value that breaks it, with actual vs expected output.
  3. Which clause it violates — quote the contract. If you can't name the clause, it isn't a finding.
  4. The corrected line — not a paragraph describing it.

Recommendation vocabulary

AcceptCorrect as written. Name the checks you actually ran — never just "LGTM".
Accept with changesDo not merge yet, but the defects are clear and local to this function. Most review exercises land here.
RejectWrong algorithm or data model, security / data-loss risk, or several interacting components need redesign. Not "many lines to change".
The line that does the work"Accept with changes — do not merge until the skipped final element, duplicate handling, and membership complexity are fixed." It states non-mergeable and bounded, in one sentence.

The hint list names areas to EXAMINE, not bugs to find

Critical

A prompt that says “look especially for: touching boundaries, empty input, complexity, mutation of caller-owned data” is not a list of four defects. It is four places the grader wants you to look — and on a well-designed exercise some of them are clean on purpose, to see whether you will manufacture a defect to fill the slot.

Measured instance, merge-ranges exercise with exactly that hint list: only one of the four areas held a real defect. Empty input returned [] correctly — a comprehension over an empty list is a no-op, not an error. Caller data was never mutated — sorted() returns a new list and the merge appends freshly-built ones. Two of the three findings filed were fabrications, and one proposed fix (“copy the list before sorting”) would have added a redundant allocation to already-correct code.

Say in reviewEmpty input: returns [] correctly; the comprehension over an empty list is a no-op. Caller data: not mutated — sorted() returns a new list and the merge builds fresh ones, so neither the caller's sequence nor its elements are touched. Both named areas check out.

Stating a clean result explicitly scores. Silence on a named area reads as “didn't check”; a fabricated finding there reads considerably worse — it means you cannot tell working code from broken code, which is the whole job.

Where each observation goes — the three-way sort

Method

Noticing more is never the problem. Filing it in the wrong section is. Your Correctness list is a claim about what is broken, and every item in it implicitly reads “change this before merge” — so a non-defect placed there is a request to change working code. Route, don't filter: everything you noticed goes somewhere, and nothing is thrown away.

A code change, and the contract supports it?→ Correctness finding. Severity · trigger input · the clause it violates · the corrected line.
A code change, but the contract is silent or ambiguous?→ Question for the author. “The contract doesn't specify X; I assumed Y.”
No change — you just want credit for having checked?→ Verified clean. One line naming what you traced.

Same exercise, identical amount of noticing, routed two ways. As filed: 3 correctness findings, 1 real — precision 33%, and two changes requested to code that already worked. Routed: 1 finding, 2 verified-clean notes, 1 question — precision 100%, one change. The second reads as thorough; the first reads as unable to distinguish working code from broken code.

Why precision is the thing being graded: a review's entire value is that the reader can act on it without re-deriving it. The moment one item proves false, every other item has to be re-checked — and the review has added work instead of removing it. One caveat on volume: keep questions to two or three. Fifteen open questions on a ten-line function reads as an inability to prioritise.

When complexity is a finding — and when it is just a number

Method

“Complexity” appearing in the brief's hint list does not mean the complexity is wrong. State it either way; call it a defect only on one of two triggers:

  1. The contract states a scale the code cannot survive. “The file may be 10 GB” turns readlines() from an O(n) observation into a guaranteed crash on the documented input. The scale statement is the trigger input — the brief handed it to you.

  2. The complexity class itself is wrong. An accidental O(n²): list.insert(0, x) in a loop, membership tested against a list instead of a set, += on a string in a loop. A different curve is a defect at any scale.

Neither trigger fires on a constant factor. A rewrite that cuts peak memory by a third while both versions stay O(n) is an optimisation, and recommending it with no stated performance requirement is premature — the same false-positive family as inventing a correctness bug, just quieter.

Say in reviewTime O(n log n), dominated by the sort — optimal for this problem. Space O(n), unavoidable given the output size. Both appropriate; no change recommended. Minor note, not a recommendation: the intermediate list-of-lists plus the final tuple conversion keeps two full structures alive at once, roughly 1.5× the necessary peak. Not worth changing absent a stated scale.

That closing clause is the senior signal — it proves you traced the allocations and that you know not to act on it. Knowing an optimisation exists and declining it scores higher than either missing it or demanding it.

Don't invent defects

Costly

A false positive costs more than a missed nitpick — it signals you can't distinguish a contract violation from a style preference. If the contract says "normalized" and the code calls .strip().lower(), that is the requirement being met, not a defect. When the code is correct, say so with evidence:

"No actionable correctness issues found. I traced the loop bounds and checked [], [x], duplicates, and the final-element case. Complexity is O(n) time and O(n) space, appropriate for the stated constraints. Recommend Accept."

Complexity vs edge cases — they don't overlap

Ask which question you're answering. "How long / how much memory as input grows?" → Complexity. "What result does it give for this specific unusual input?" → Edge cases. Large-input performance is complexity; a one-element list returning the wrong value is an edge case, even though both involve size.

Every finding gets a fix; every fix traces to a finding

Structure

Count them before you submit. Two findings and three fixes means at least one is untethered — either you fixed something you never reported (reads as guessing) or you reported something you have no fix for (reads as an unfinished review). Number the findings and reference the numbers in the recommendation.

Say in reviewAccept with changes — (1) compare the level field exactly, (2) stream the file. Finding (3), the path check, is a question for the contract rather than a code change.

A fix that swallows the failure is worse than the failure

Costly

“Wrap it in try/except” is not a recommendation until you say what the except does — and the obvious implementation usually destroys information:

try:
    ...
except FileNotFoundError:
    return 0          # "the log is missing" now reports "zero errors"

An exception propagating out of open() is defensible current behaviour when the contract is silent. Report the silence; do not patch over it with a value that makes a missing input indistinguishable from a clean one.

Say in reviewMissing file: FileNotFoundError propagates. The contract does not specify this case. Failing loudly is reasonable; returning 0 instead would make a missing log indistinguishable from a clean one, so that has to be an explicit decision.

State the complexity you are recommending, not just the one you found

Phrasing

Reporting O(n) memory in one section and recommending streaming in another leaves the grader to join them. Join them yourself — the recommendation is the point of the measurement.

Say in reviewMemory is O(n) because the whole file is materialised, and a log file is precisely the input you should assume is large. Iterating the handle makes it O(1).

Delimited lines: field-exact beats substring, and maxsplit beats regex

Technique

"ERROR" in line is a substring test over the entire line, so a timestamp or message merely containing the word is counted. Compare the field:

line.split("|", 2)[1] == "ERROR"

maxsplit=2 stops after the fields you need, so a | inside the message is left intact — which removes the usual objection to split. Reach for a regex only when the field structure itself is variable; here it is slower, more fragile and easier to get subtly wrong.

02 · The coding round

This session is a shared editor, not a conversation

Format — owner-supplied

The 45 minutes on the Zoom is a live HackerRank CodePair round. You will write code in a shared editor while the interviewer watches and talks to you. Everything else on this page—the opener, the stories, the questions—still applies, but it now lives in the margins of the session rather than filling it. Prepare accordingly.

What CodePair gives you, and takes away

  • A shared IDE with live execution. Both of you see every keystroke. You can run code, and REPL support lets you execute one block at a time instead of writing everything and hoping.
  • Deliberately sparse libraries. HackerRank supports 30+ languages but keeps the available libraries thin on purpose, so raw skill is what gets measured. Plan to hand-roll structures rather than import them—and confirm your language is offered before the clock starts.
  • Diagram questions are in-format. CodePair supports architecture sketches as well as code, so an ML-system-design detour is a normal part of the tool, not a derailment.
  • Continuity from earlier rounds. Interviewers can import code from a previous screen and raise its complexity live. Anything you have already submitted to ServiceNow can come back with a twist.
  • Every keystroke is visible. A long silent pause reads as being stuck. Narration is not a nicety here—it is the only channel the interviewer has into your reasoning.

The reported question profile

Candidate accounts of ServiceNow senior/staff CodePair rounds converge on: two problems, LeetCode medium to medium-hard. One 45-minute account describes a hashmap design problem with extended edge-case discussion, plus conceptual follow-ups—BFS vs DFS, how a hash table works, and what its downsides are. Recurring topic areas across reports: arrays and hashmaps, strings, graphs and BFS/DFS, and basic dynamic programming.

The ML-coding variant

For ML-engineer roles the round sometimes swaps LeetCode for implement-from-scratch work: linear or logistic regression with gradient descent, k-means, KNN, or a metric like AUC or precision@k. Reports on this are inconsistent, and in at least one documented case the recruiter's description of the format was simply wrong. Prepare a thin layer of both rather than betting on either.

The thing that is actually scored

The most consistent signal across every account: explanation and complexity analysis matter more than getting the code to compile. One candidate reported a round where execution was beside the point and the discussion was effectively language-agnostic. At Staff level this is doubly true—they are buying judgment, and the code is the medium it arrives in.

The first ninety seconds — buy yourself the whole round

Ask before you type

  • “Is it useful if I think out loud, or would you rather I work quietly and explain after?” Almost always the former—and now it is sanctioned rather than assumed.
  • “What can I use here—autocomplete, docs, any AI assist?” Ask once, explicitly, and abide by the answer. HackerRank runs AI-usage detection, and ServiceNow's own policy requires technical evaluations be completed independently unless they say otherwise.
  • “Do you want the brute force first, or should I go straight for the optimal?” Staff-level framing, and it protects you from spending twenty minutes on an optimization they did not want.
  • Restate the problem in your own words and name one edge case before writing a line. This is the cheapest competence signal in the round.

Then work the loop: state the approach → state its complexity → write it → run a small case in the REPL → improve it. Validate incrementally rather than writing the whole thing and hitting run once.

What to drill beforehand, in priority order

Highest value first

  • LeetCode Medium in Python—hashmaps and arrays, strings, graphs with BFS/DFS, and basic DP. This is the single most-cited bar for the ServiceNow screen.
  • Narrating aloud while coding. Genuinely rehearse it; it is a separate skill from solving, and it degrades badly under observation if untrained.
  • The conceptual quickies—hash table internals and their downsides, BFS vs DFS and when each is correct. Directly reported from a ServiceNow round.
  • One from-scratch ML implementation—logistic regression with gradient descent is the highest-leverage single choice; it touches the loss, the update rule, and the metric in one exercise.
  • A SQL refresher (CASE, window functions) and one RAG or LLM-serving design sketch. Both have surfaced in recent ServiceNow-adjacent assessments, and CPQ AI makes them plausible here.

Where your existing prep still pays: if the round includes a diagram question or drifts into system design, the interruptible-session and Harness/MCP-boundary material in section 06 is directly on target. Do not discard it—just stop treating it as the main event.

06 · Technical drills

Likely probes and the shape of a Staff-level answer

1. Why do three agent architectures run side by side—and what governs which one you reach for?

Do not walk in with “framework vs custom”

The posting is explicit that they run multiple production agent architectures concurrently: ReAct-style tool-calling agents, hand-rolled LangGraph state machines, and the Harness. So this is not a question about which one wins. It is a question about why a mature system tolerates three, and what decides the boundary between them. Answering “custom beats the framework” reads as not having read the job.

Answer spine

  • Three coexisting runtimes is usually a correct outcome, not debt: they sit at different points on the control/ceremony curve, and forcing one to cover all three costs more than maintaining three.
  • Name the selector. ReAct for short bounded tool loops where the model's own control flow is good enough; a LangGraph state machine where the transitions are known and worth making explicit; the Harness where you need interruption, durable state, and concurrency the framework's hidden control flow will not let you test.
  • Say what would make you collapse two of them—the real Staff answer. Convergent semantics, a maintenance cost that outgrows the benefit, or a framework that finally exposes the extension point you were working around.
  • Start from required semantics: interruption, durable state, concurrent work, observability, latency, and evolution.
  • Use a framework when its execution model matches those semantics and its extension points remain honest.
  • Build the narrow custom layer only where a framework’s hidden control flow makes invariants untestable or forces expensive workarounds.
  • Keep portable pieces—tool contracts, event schemas, evaluation, persistence—separate from the scheduler so the choice is reversible.
  • Measure operational complexity and failure recovery, not just first-demo velocity.

Expect the follow-up: “What invariant would justify owning a runtime?” Pick one concrete example such as exactly-once state transition, interrupt latency, or resuming parallel work without duplicating side effects.

2. How would you design a full-duplex, interruptible agent session?

Answer spine

  • Give every run, task, tool call, and emitted chunk a stable identity.
  • Persist state transitions before acknowledging externally visible progress.
  • Treat interruption as a typed event with an ordering rule—not an arbitrary prompt appended to a buffer.
  • Use structured cancellation: stop accepting new side effects, cancel safe children, checkpoint unsafe ones, and report what completed.
  • Separate transport backpressure from execution backpressure; bound queues and define shedding behavior.
  • Make resume idempotent with dedupe keys and replayable event history.

Failure drill: the user redirects while two tools are running and one has already committed. Explain which work is cancelled, which result is retained, and how the next turn learns the truth without replaying the side effect.

3. They have already drawn the Harness/MCP boundary—defend it, then name its cost

They have already published their answer—open by acknowledging it

The posting states the direction plainly: the Harness is becoming primary for internal agents, with MCP retained as “the secondary, standards-based surface for external interop.” Arriving with a freshly-derived answer to a question they have already settled reads as not having done the reading. Say their direction back, say why it is the right call, then earn the conversation by naming what it costs—two surfaces to keep honest, and a versioning burden on the external one.

Also aim at the qualification bullet directly: they want someone “ideally having built an MCP server, not just consumed one.” Lead with the server side—schema design, capability discovery, auth at the boundary, and what you learned that a consumer never sees.

Answer spine

  • The harness owns execution semantics: lifecycle, state, scheduling, interruption, retries, checkpoints, and progress.
  • MCP is a stable capability boundary: discoverable tools/resources with typed inputs and outputs, especially across teams or systems.
  • Do not leak scheduler internals into every tool contract or force chatty internal event streams through a request/response surface.
  • Put authorization and validation near the system of action; the harness must not become a privilege bypass.
  • Version contracts, bound payloads, make idempotency explicit, and instrument end-to-end latency across the seam.

Decision test: if a capability must be callable by third-party agents, MCP-first is attractive. If it exists only to coordinate internal resumable tasks at sub-second cadence, a native harness interface may be cleaner.

4. How is A2A different from a tool call?

Answer spine

  • A tool exposes a bounded capability; an agent owns reasoning, state, and a task lifecycle.
  • Discovery needs a capability/agent card; delegation needs authenticated identity and explicit authority.
  • Model submitted, working, blocked, completed, failed, and cancelled states; make updates replayable.
  • Define responsibility for retries and deduplication at the boundary so both peers do not repeat work.
  • Stream progress as advisory; terminal state and committed side effects require authoritative receipts.

ServiceNow connection: its public product material describes A2A for communication among ServiceNow and third-party agents, while MCP connects agents to external tools, data, and systems.

5. How would you build tenant-safe RAG and context assembly?

Answer spine

  • Enforce tenant identity in storage, retrieval, caches, queues, and telemetry—not only in the prompt.
  • Separate ingestion lineage from retrieval ranking; preserve source, version, permissions, and observed-at time.
  • Use deterministic filters before semantic retrieval and re-check authorization at read time.
  • Budget context by information value; cache stable prefixes while keeping user- and tenant-specific material out of shared cache keys.
  • Evaluate retrieval recall, answer grounding, permission leakage, stale-document behavior, latency, and cost independently.

Expect the follow-up: “What happens when permissions change?” The answer needs invalidation or read-time enforcement; an old embedding index cannot be the authority.

6. How do you evaluate an agent system before and after launch?

Answer spine

  • Decompose quality: task success, constraint adherence, tool correctness, recovery, latency, cost, and user intervention.
  • Build a frozen representative corpus plus adversarial and mutation cases that prove guards can fail.
  • Evaluate components and end-to-end traces; aggregate scores must not hide one critical failure class.
  • Use deterministic assertions where possible and calibrated human review where judgment is unavoidable.
  • In production, sample traces, watch cohort drift, preserve privacy, and connect incidents back into the regression set.

Staff signal: name the release decision rule. “We monitor it” is not a gate; define what blocks, what degrades gracefully, and who owns the response.

7. How do you reason about cost, latency, and backpressure?

Answer spine

  • Set an end-to-end user budget, then allocate it across retrieval, model calls, tools, and rendering.
  • Measure p50/p95/p99 and queue time separately; averages hide overload and tail failures.
  • Use prefix caching, smaller decision models, speculative parallelism only when cancellable, and bounded concurrency.
  • Propagate deadlines and cancellation; a timed-out parent must not leave expensive orphan work.
  • Choose degradation deliberately: partial result, bounded workflow, queued completion, or explicit refusal.

Bad answer: “Use a faster model.” A Staff answer identifies the critical path, queue ownership, accuracy floor, and how the system behaves when demand exceeds capacity.

8. When is classical ML better than an LLM?

Answer spine

  • Prefer a supervised model when the label is stable, data is plentiful, output space is bounded, and latency/cost or calibration matters.
  • Prefer an LLM when language understanding, open-ended synthesis, or rapidly changing instructions dominate.
  • Consider a hybrid: classical candidate/risk model, rules for hard constraints, LLM for explanation or ambiguous long-tail cases.
  • Compare on the same offline set and production objective, including abstention, maintenance cost, drift, and observability.

CPQ example: field-value prediction may be a calibrated classifier problem; translating a user’s ambiguous configuration intent into a multi-step plan may favor an LLM plus deterministic rule validation.

9. How do you turn Forward Deployed work into product leverage?

Answer spine

  • Begin with the customer workflow and failure cost; observe the real constraints rather than accepting a feature request literally.
  • Instrument before customizing so you can distinguish a product gap from bad configuration or missing data.
  • Ship the smallest safe adapter behind stable contracts, with rollback and explicit ownership.
  • Extract recurring patterns into core capability, fixtures, and tests; avoid permanent customer-specific branches.
  • Close the loop with product, support, and engineering using evidence from the deployment.

Ask back: how much of this role’s FDE work is discovery, incident response, implementation, or platformization? That reveals the operating model without sounding resistant to customers.

10. What changes when the agent edits a CPQ transaction?

Answer spine

  • A generated plan is a proposal; pricing, compatibility, entitlements, and approval rules remain authoritative.
  • Use staged changes with validation and a human-visible diff before committing consequential edits.
  • Attach provenance: user intent, retrieved context, rule version, tool calls, approvals, and final transaction version.
  • Make operations idempotent and protect against concurrent edits with version checks.
  • Design recovery around business semantics: a partially applied quote is not equivalent to a failed chat response.

Domain humility: say what you would learn from CPQ experts—constraint models, pricing/approval semantics, and common deployment failure modes—then show the systems principles you already bring.

Part two — the Python scoring stack

The one-sentence answer

pandas, scikit-learn and XGBoost are three layers of a single prediction path; compute-regression.py is not a fourth library but the process that hosts them. pandas owns how the data is represented, scikit-learn contributes two utilities and the fit/predict convention everything conforms to, XGBoost is the only component that actually learns, and the script is a long-lived sidecar holding the trained model in memory while it answers JSON commands from the Node service.

The contract that makes them compose

The reason scikit-learn utilities work on an XGBoost model at all is that XGBRegressor is XGBoost's scikit-learn-compatible wrapper around its native booster. It implements the estimator interface, so train_test_split can feed it, .score() returns R² by sklearn's convention, and the imputer's output drops straight in. Had the code used xgb.DMatrix with xgb.train, none of those pieces would have fitted together.

That contract is not an assertion about the code — it is recorded in the artifact. The saved model file carries attributes.scikit_learn = {"_estimator_type": "regressor"}, which is XGBoost noting that it was driven through the sklearn interface.

Where the feature schema lives — and why that is the hard part

get_dummies derives its columns from whatever data is in front of it. At inference a batch may lack categories the model saw during training and may carry categories it never saw, so the one-hot column set silently diverges from the fitted matrix. That is the standard way a tabular model begins returning confident nonsense.

The schema therefore has to be reconciled across four places it independently lives:

  • TypeScript — ASIN_OFFER_COLUMNS declares the features once and drives the SQLite CREATE TABLE, the row serialization order, and the columns array in the predict payload.
  • SQLite — the physical training table built from that declaration.
  • The persisted column list — training writes dummy_columns_<model>.json, the exact post-one-hot column names; inference re-adds any missing ones as zero-filled columns.
  • The booster itself — inference then reindexes with X = X[model.get_booster().feature_names], so a correct set in the wrong order is corrected too.

Two independent guards against one failure mode. That redundancy is the design decision worth narrating.

Say this

The framing that travels

“We hand-rolled what ColumnTransformer and Pipeline give you for free — because the transform boundary was a process boundary. The fitted encoder lived in Python and the feature schema lived in TypeScript, so the column contract had to be an artifact on disk rather than an object in memory. Given the same problem now I would persist a fitted Pipeline and make that the model artifact.”

It names the trade-off, its cause, and the revision — which is the staff-level shape of the answer.

Do not overclaim

What the sklearn footprint really is

“We used scikit-learn” invites “which estimators? did you use Pipeline?” — and the honest answer is an imputer and a train/test split. Claim the integration, not a modeling framework that was never used here.

There is likewise no PyTorch, no TensorFlow and no deep learning anywhere in this path. Gradient-boosted trees over tabular features is the entire model.

Weaknesses to volunteer before they are found

  • The imputer re-fits at inference. The transform function is shared by both paths, so fit_transform runs on every prediction batch. It is harmless only because strategy='constant' learns nothing from the data — change it to 'mean' and predictions start depending on batch composition. A good answer to “what would you fix first.”
  • Prediction rows carry a dummy price = 0, because that shared function unconditionally splits out the target column.
  • Evaluation is thin. The only metric is print(model.score(X_test, y_test)) — R² on a single 80/20 split with a fixed seed, printed and never persisted. No cross-validation, no hyperparameter search, no metric history.

If asked how you knew the model was good: its output fed a downstream buying decision, so bad predictions surfaced as bad economics rather than as a metric regression. Present that as a deliberate reliance on downstream signal — then say what you would add now.

Part three — cross-marketplace product matching

The frame that wins this question

“How would you match product descriptions across marketplaces?” reads as a text-similarity problem and is not one. Marketplace titles are keyword-stuffed and adversarial, and the discriminative signal is a handful of discrete attributes — so treat it as entity resolution, not similarity. That reframe is the answer; everything below is evidence you actually did it.

The five stages, with the code behind each

  • Attribute extraction from free text — Services/Matcher/, 10,206 lines across Matcher.js, Config.js and LIB.js. Regex/config-driven extraction of family, series, model, cpu, ram, resolution and condition; allFamiliesRegex alone enumerates roughly seventy product families across Dell, HP, Lenovo, Acer and Asus.
  • Inference and disambiguation — applyImplicationsForPropMap propagates attributes the seller never stated (series implies panel and resolution); chooseBiggers, chooseAllSameCharactersButMore and chooseWorsts resolve competing candidate values when a title supports several readings. This is what turns a messy string into one defensible spec object.
  • Canonicalization — getStrippedSpecObj and groupSpecObjsByStrippedSku strip a spec object to its identity-defining attributes and group on the result. That group is the canonical product entity; every marketplace listing resolves into one.
  • The comparison relation — Services/Transformer/SpecObjComparator.js, 2,071 lines. Per-property ordinal scales loaded from a curated ranking CSV (getCleanRankingCsvJson → createRankGraphMap), composed into a dominance relation materialized as betterThanGroupIdBitSets (SKUTransformer.js:1768), alongside weighted fromToEdgeCosts between SKUs.
  • Economic validation and linking — the XGBoost model in part two prices a group from its specs, and group-to-ASIN links persist as bidirectional LMDB maps (KEYS_asin_groupId / KEYS_groupId-asin).

Spend your time here — this is the differentiator

You did not stop at binary match. Binary matching is a classification problem any candidate can describe. A partial order with edge costs is a modeling decision, and it answers the question the business actually had — not “are these the same product” but “can this item satisfy this obligation, and what does the upgrade cost.”

It also hands you a ready answer to “what was hard”: the relation is partial. 16GB/256GB versus 8GB/512GB is genuinely incomparable, so the system has to represent incomparability rather than force a total order.

The ninety-second spoken version

“Cross-marketplace matching looks like a text-similarity problem and isn't. Marketplace titles are keyword-stuffed and adversarial, and the discriminative signal is a handful of discrete attributes — so we treated it as entity resolution, not similarity.

We extracted a typed spec object from each listing, applied implication rules to fill in attributes the seller left out, and resolved ambiguity when a title supported several readings. Then we stripped each spec object down to its identity-defining attributes and grouped on that — the group became our canonical product entity, and every marketplace listing resolved into one.

The part I'd call the actual design decision: we didn't stop at binary match. We built a partial order over spec vectors — per-attribute ordinal scales composed into a dominance relation, stored as bitsets so comparison was a set operation rather than pairwise scoring. That let us answer the question the business really had, which wasn't ‘are these the same product' but ‘can this item satisfy this obligation, and what does the upgrade cost.'”

When they push on embeddings — and they will

Do not get defensive. Argue the cost structure: “Embedding similarity is least reliable exactly where our cost was highest. The same laptop with 256GB versus 512GB is near-identical in embedding space and economically completely different — and a false positive meant buying or listing the wrong item, so it cost real money plus marketplace account health, while a false negative was only a missed opportunity. That asymmetry pushed us to a representation where a match was auditable: I could point at which attribute drove it. Where we did want fuzzy — aligning the same listing across regional sites — we used Jaro-Winkler on titles, which was proportionate.”

That last clause is true (MarketplaceStuff.js:1582) and it matters: “I used the fuzzy method where fuzzy was appropriate” is far stronger than “fuzzy methods are bad.”

Own this gap

There is no labelled benchmark

No precision or recall was ever measured. The Transformer golden files are thin and stale — one stored result is literally an error payload. Say so first: “our ground truth was operator corrections, and the first thing I'd build again is a labelled pair set so I could state precision at a threshold.”

The real feedback loop was human-in-the-loop: manual spec overrides by group id (getManualSpecObjs) and an ops-curated blacklist pulled from a Google Sheet (Matcher.js:939). That is a legitimate answer — volunteering it reads as senior; being caught without it does not.

Your LLM bridge

The 7,272-line rule config

Hand-maintained extraction rules are fine for the head of the distribution and brutal for the tail — every new product family was a config change. That is the honest weakness, and it is where LLMs enter your story legitimately:

“I'd keep the deterministic path for the head, where it's auditable and cheap, and use an LLM for the tail: extract structured attributes from listings the rules don't cover, then treat those as labels to generate new rules or distil a small extractor. The expensive model proposes, the deterministic layer verifies — and the verification is the existing spec comparator, so a bad extraction fails a check instead of silently entering the graph.”

If the posting's knowledge-graph line comes up

Lead with that vocabulary rather than “product matching.” Canonical entities resolved from heterogeneous sources, typed attributes, and a weighted relation graph between entities — including graph-data-structure backing the rank graphs — is a product knowledge graph. That is an accurate description of what is in the repository, not a stretch.

Before you claim any of it

Confirm which parts were your own work. The repository has several contributors — it carries per-developer configs for BEN, ELI and JAMES — and the older Services/Parser/Pricing/ pipeline carries another author's name and a 2019 date. Check ownership of Matcher, Transformer and Scorer specifically.

Bring numbers you can source. Listing volume, group count, match rate. “We used bitsets so comparison was cheap” invites “how many comparisons?” — and you want a real figure there, not an estimate improvised in the room.

10 · 45-minute strategy

Budget the clock for two problems, not for a conversation

Assumes two problems

If they open with only one problem, expect it to go deeper and to absorb the whole middle of the session—stretch the loop rather than rushing to finish early. If a diagram or design question replaces the second problem, section 06 is your material.

  1. 0–3 min · Set the terms

    Short greeting, then ask the three opening questions from section 02: think aloud or not, what tooling is permitted, brute force first or straight to optimal. Confirm your language is available.

  2. 3–6 min · Restate before you type

    Say the problem back in your own words, name one edge case and one assumption, and state the approach you intend plus its complexity. Get a nod before writing.

  3. 6–20 min · First problem

    Write it, run small cases in the REPL as you go rather than at the end, and keep narrating. If you see the optimization, say so out loud even if you implement the simple version first.

  4. 20–23 min · Close it properly

    State final time and space complexity, name the edge cases you handled, and say what you would test next. This is the part candidates skip and interviewers score.

  5. 23–40 min · Second problem

    Same loop, faster. Expect the conceptual follow-ups here—hash table internals and downsides, BFS vs DFS—and answer them in a sentence each rather than lecturing.

  6. 40–45 min · Your two questions

    Pick from section 08. One about the actual system, one about the role. If time collapsed, ask one good question rather than two rushed ones, and thank them by name.

When you are stuck

Say so in structure, not in silence: name what you have, name what is blocking, state the smallest thing that would unblock you. “I have the O(n²) version and I can see the repeated work—I think a hashmap on the prefix sums removes it, let me try that” keeps the round moving. A long quiet pause is the only genuinely bad outcome.

When they interrupt or nudge

Treat it as data, not criticism—interviewers nudge when they can see where you are heading. Stop, restate what you now understand the constraint to be, say which part of your approach it changes, and adjust in public. Defending the first idea past a hint is the expensive mistake.

11 · Last-minute checklist

Ten minutes before the call

  • Confirm the actual interview date in the calendar; this page intentionally does not guess it.
  • Test camera, microphone, headphones, power, network, and the supplied Zoom URL.
  • Open the CodePair link early if you have one—check the language list and that the editor and run button work before the interviewer joins.
  • Warm up on one easy problem in the half hour before. Cold-starting a shared editor in front of someone is the avoidable version of freezing.
  • Close notifications and every AI assistant, autocomplete overlay, and live transcription not explicitly authorized. Ask once at the start; abide by the answer.
  • Have paper for the problem statement, constraints, and edge cases—not a second screen of scripts.
  • Rehearse the first ninety seconds aloud: restate, name an edge case, state the approach and its complexity.
  • Put the short “Why ServiceNow?” answer in your own voice—do not memorize punctuation. It may get sixty seconds.
  • Keep one Answer Bank story and the Harness/MCP boundary loaded in case a design or diagram question appears.
  • Pick two questions for the close. The role is confirmed; the team is not—do not present CPQ AI as settled.
  • Join two or three minutes early, then close this page unless notes are explicitly allowed.

05 · Three stories

Problem → decision → evidence → lesson

1. Agents sharing a codebase

Problem: parallel agents need clear ownership, durable state, and recovery when a session disappears.

Your decisions: persist work records, express dependencies, arbitrate conflicting edits, and tie completion to evidence.

Outcome to explain: who owns the task after interruption, how duplicate work is prevented, and what proves the resumed task actually finished.

Steampunk connection: workflows may span models, APIs, approvals, and external systems; recovery is part of the product.

2. Predictive pricing across a process boundary

Existing prep evidence: Node sends JSON commands to a long-running Python sidecar. The model is an XGBoost regressor; pandas prepares features, and scikit-learn supplies an imputer and a split.

The engineering decision: preserve feature names and ordering between training and prediction. A matching shape alone doesn't prove matching meaning.

Lesson: define preprocessing as part of the model artifact; evaluate with splits that represent the actual deployment, and don't present a random split's score as production impact.

3. Operational software with a measurable result

Your résumé describes a fulfillment optimizer over 100K+ SKUs using bitmap indexing to evaluate millions of paths in about a minute, reducing fulfillment cost per order by 15%. Explain the constraints, why the representation made search practical, and how the result was measured. If the measurement period or denominator is not at hand, say so.

Steampunk connection: a mission need may call for an optimizer, a predictive model, or deterministic logic. Choosing the appropriate method is part of senior AI engineering.

06 · Hypothetical system design

“Build an assistant for a federal caseworker.”

This is a practice scenario, not a disclosed Steampunk project. Start by asking what decision the caseworker makes, which sources they can access, and which actions require human authorization.

  1. Define the workflow and baseline

    Observe how a caseworker answers a policy question today. Measure time, accuracy, and rework. Begin with a narrow read-only task and agree on acceptance examples with users.

  2. Ingest approved documents

    Parse text and tables, preserve version and source references, attach access-control metadata, and test extraction quality. Handle deletions and superseded policies as explicit updates.

  3. Retrieve authorized evidence

    Filter by the caller's permissions before selecting context. Combine keyword and vector retrieval when useful, rerank candidates, preserve citations, and return insufficient evidence when coverage is weak.

  4. Generate a bounded answer

    Keep retrieved text as data, not instructions. Ask for cited answers tied to current sources. Validate structured outputs, limit context, and make uncertainty visible to the user.

  5. Add actions only with enforceable checks

    Use typed tools, server-side authorization, scoped credentials, idempotency keys, and persisted workflow state. Require approval for consequential actions; a model-generated plan cannot grant itself permissions.

  6. Evaluate and operate with LLMOps

    Measure retrieval coverage, supported-answer rate, task success, unauthorized-action attempts, p95 latency, and cost per successful task. Version models, prompts, retrieval settings, and data; release gradually with rollback and a known owner.

Close with the tradeoff: “I'd start with one well-evaluated workflow. I would introduce multiple agents only when specialization or independently checkable parallel work improves the result enough to justify coordination cost.”

07 · Technical practice

Short answers with a useful follow-up

RAG, fine-tuning, or a predictive model?

Use retrieval when the answer depends on changing or permissioned knowledge. Consider fine-tuning for a repeatable behavior or format problem with suitable examples, after measuring a baseline. Use a supervised model for a stable, bounded prediction task with reliable labels. These can coexist in one application.

Follow-up: Fine-tuning does not replace access controls or guarantee factual recall. What specific measured failure would justify its cost?
How do you improve a weak RAG answer?

Separate retrieval failures from generation failures. Check document extraction, freshness, chunk boundaries, query coverage, metadata filters, reranking, and whether the answer-bearing passage was in context. Maintain a small labeled set of questions with expected evidence and negative cases.

Measures: retrieval recall at k, evidence correctness, citation support, task success, abstention behavior, and latency. A fluent answer is not a retrieval metric.
How do you prevent prompt injection and unsafe tool use?

Treat documents and tool results as untrusted data. Enforce permissions and argument validation outside the model. Minimize credential scope and data returned, constrain network destinations where needed, and require explicit approval for high-impact operations. Test malicious documents and tool outputs as part of evaluation.

Follow-up: Input sanitization and content filtering help with particular threats; neither substitutes for authorization. Explain the remaining exposure honestly.
What state belongs outside the context window?

Workflow status, approved actions, ownership, tool receipts, retry counts, durable identifiers, and recovery checkpoints belong in persistent storage. The prompt contains the bounded context needed for the next step. After a timeout, read authoritative state before retrying an external side effect.

Example: A service accepts a request, then the worker crashes before recording success. Recover using the idempotency key or receipt, not a blind second request.
How would you evaluate predictive ML?

Define the decision, label, loss, and baseline. Split by time or entity when that matches deployment, keep preprocessing fitted only on training data, and check leakage. Pick metrics based on error costs: regression error in business units; precision/recall and calibration for classification; relevant subgroup performance where justified.

Follow-up: Compare offline gains with real workflow impact. Monitor input and outcome changes; retraining is a decision backed by evidence, not a timer alone.
How do you make inference faster and cheaper?

Measure where time goes: retrieval, queues, model calls, and tools. Reduce unnecessary context and serial calls, cache safely with permission-aware keys, route simpler tasks to smaller models, and limit concurrency and retries. Use streaming when it improves the user's experience, while measuring total completion time separately.

Boundary: GPU batching, quantization, and serving engines are design options to discuss with LLMOps. Don't imply that provider-routing experience proves hands-on GPU optimization.
How would you work with design, product, and mission stakeholders?

Observe the current workflow, agree on the costly failure cases, and build a small prototype users can react to. Include citations, error states, escalation, and approval paths in the design. Translate feedback into measurable acceptance criteria and a versioned evaluation set.

Concrete question: “What does the user do when the assistant is unsure, and can they finish the task without it?”
What would your first month look like?

Proposed approach: learn the mission, data restrictions, delivery process, and existing architecture; reproduce the current baseline; pair with users and LLMOps; ship one narrow improvement with evaluation, monitoring, and a rollback path. Document a reusable component only after proving it in the workflow.

Ask what is already built before proposing a replacement. The actual client, cloud, framework, and first assignment remain unknown.

05 · MCP and A2A, current as of 16 Sep 2026

Know what changed this year, then say how the two compose

Your FAQ describes last year’s MCP session model

The FAQ’s D8 and D9 describe the initialize handshake, Mcp-Session-Id and resumable SSE streams. That was correct through revision 2025-11-25. The 2026-07-28 revision removed all three. Use D8 and D9 as history, and use the list below for “how does MCP work today”. Fact

MCP 2026-07-28 — the changes worth saying Fact

  • Stateless core. No initialize handshake and no protocol sessions. Every request carries its protocol version and client capabilities in _meta. server/discover is required on servers and optional for clients to call. State a server needs across calls becomes an explicit handle passed as a tool argument.
  • Multi Round-Trip Requests. Servers no longer send their own requests for elicitation, sampling or roots. They return resultType: "input_required", and the client retries with the answers.
  • Routing headers. Streamable HTTP POSTs carry Mcp-Method and Mcp-Name, so gateways, rate limiters and WAFs can route and meter without parsing JSON.
  • Cacheable lists. tools/list and friends return ttlMs and cacheScope. Servers should list tools in deterministic order, which the changelog ties to prompt-cache hit rates.
  • Authorization hardening. Issuer validation per RFC 9207, credentials bound to the issuer that minted them, Client ID Metadata Documents preferred, Dynamic Client Registration deprecated. Audience validation of access tokens is a MUST.
  • Lifecycle. Tasks moved into an extension with polling. Roots, Sampling and Logging are deprecated with at least twelve months’ notice. Resumable SSE streams are gone: a broken stream means re-issuing the request.
  • Governance. Anthropic donated MCP to the Linux Foundation’s Agentic AI Foundation on 9 December 2025.

A2A 1.0 — the concepts to name Fact

  • Origin and governance. Google announced A2A on 9 April 2025 and donated it to the Linux Foundation on 23 June 2025. Version 1.0, the first stable release, shipped in March 2026. The Linux Foundation reported more than 150 supporting organizations on 9 April 2026, with support in Azure AI Foundry, Copilot Studio and Amazon Bedrock AgentCore.
  • Agent Card. JSON at /.well-known/agent-card.json: identity, skills, capabilities, supported interfaces, security schemes, an optional signature, and an authenticated extended card for callers who sign in.
  • Task. The unit of delegated work, with a contextId grouping related tasks and messages. States: submitted, working, input-required, auth-required, completed, failed, canceled, rejected.
  • Message, Part, Artifact. Messages carry parts (text, files, structured data). Outputs come back as artifacts made of parts.
  • Transport. Three bindings: JSON-RPC 2.0, gRPC, and HTTP+JSON. Streaming delivers status and artifact update events. Push notifications post to a client-registered webhook for long tasks.
  • Security. Schemes declared on the card: API key, HTTP auth, OAuth 2.0 flows, OpenID Connect and mutual TLS. An optional tenant field routes multi-tenant requests.

Probe: “When would you use A2A instead of MCP — and would you ever use both?”

Answer spine

  • MCP when the caller should orchestrate and your capability is a tool: a search, a citation check, a document fetch.
  • A2A when the work needs your own planning, verification and human checkpoints, and the caller should only see a task, its state and the result.
  • Both, layered: an external agent delegates a research task to CoCounsel over A2A; inside, CoCounsel’s agent uses tools — possibly over MCP — against Westlaw, KeyCite and the firm’s documents. The A2A spec’s own appendix describes this composition.
  • The CoCounsel-specific point: the unit you expose decides where verification lives. A coarse, task-level surface keeps the citation ledger on Thomson Reuters’ side; a fine-grained tool surface is more flexible but lets an outside model assemble legal work product nobody verified.

Follow-up: “Then why does the Claude connection use MCP?” Because MCP is how assistants integrate today, and an MCP tool can still be task-shaped: “research this question” returning a cited artifact, with long work handled through the tasks extension. Protocol choice and granularity are separate decisions.

06 · Design exercise

Expose CoCounsel Legal to Claude, Amazon Quick, or a firm’s own agent

How to run it

Say the frame in one breath, then take the seven concerns in order, one or two sentences each, and stop for questions. Everything here is a proposed design built from the public specs and Thomson Reuters’ public statements Inference. Where your own system did something similar, the link says so; do not claim more than it shows.

The frame, first

The model on the other side isn’t ours, and the data is privileged. So I’d treat the MCP server as a product boundary: authenticate the person, authorize every call against their firm and matter, return the smallest verified result that does the job, and keep a record that would satisfy the firm’s general counsel.

1 · Identity and authorization
  • The MCP server is an OAuth resource server. It publishes protected resource metadata (RFC 9728), and clients request tokens with a resource indicator naming it (RFC 8707). The 2026-07-28 spec says servers must validate that tokens were issued for them as the audience. Fact
  • Clients register with Client ID Metadata Documents; Dynamic Client Registration is deprecated. Clients must validate the issuer (RFC 9207). Fact
  • For firms: let the firm’s identity provider and administrators decide which AI clients may connect, rather than each lawyer consenting alone. Partners quoted in the 2026-07-28 release blog mention an Enterprise-Managed Authorization extension for this; check its current status before naming it as settled. Inference
  • Never forward the user’s MCP token to internal Westlaw or document APIs. Exchange it for a narrowly scoped internal credential, so a token minted for the MCP server cannot be replayed elsewhere. Inference

Your evidence: the dispatcher chain — default-deny, role allowlist, capability check, envelope — in G1 and the precise limits in the native-execution breakdown.

2 · Tenancy and confidentiality of legal data
  • Authorize at firm, matter and document level, including ethical walls: a lawyer screened from a matter must not reach it through an assistant any more than through the UI. HighQ MCP’s public model — same permissions, read-only, audit logged — is the house precedent. Fact for HighQ; Inference for walls.
  • Anything returned enters another vendor’s model context. Return only what this user may see and what the task needs; prefer citations and excerpts over bulk documents.
  • Keep the public commitment true end to end: customer data not used to train third-party models, not shared beyond the customer’s environment. That constrains logging, caching and any evaluation data. Fact for the commitment.
  • Residency: rollouts to Canada, the UK and Australia imply region-pinned storage and processing for data and logs. Inference
  • Why lawyers care: ABA Formal Opinion 512 (29 July 2024) ties generative AI use to confidentiality under Model Rule 1.6 and warns about inadvertent disclosure through shared tools. Fact

Your evidence: the tenant-isolation design and cross-tenant test plan in G3. That card is explicitly a design answer, not an audited deployment — say it the same way.

3 · Tool design for model callers
  • Prefer task-shaped tools — “research this question in this jurisdiction”, “review these clauses” — that return a cited artifact, over raw search primitives. Verification stays inside CoCounsel.
  • Structured results: each claim carries source identifiers, KeyCite status and a link the lawyer can open. The model should not have to parse prose to find the citation.
  • Bound results at the source, page with handles, and make “no results” distinguishable from “did not run”.
  • Long research runs use the tasks extension; clarifications use input_required instead of guessing jurisdiction or date ranges.
  • Refusals name the fix: “this matter is walled for your account — ask the matter owner”, not a bare 403 the model will retry.

Your evidence: description budgets of 1,500 characters with a 1,600 hard cap, results capped around 1,500 tokens, projections, teaching refusals, boundedness markers (N6).

4 · Rate limits and cost
  • Quotas per firm, per user and per client application, with separate concurrency limits for expensive agentic runs versus cheap lookups.
  • Meter at the gateway using the Mcp-Method and Mcp-Name headers, before any JSON parsing. Fact for the headers.
  • Reserve an estimated budget before a costly run and reconcile actual usage afterward; show partial results with the reason when a run stops.
  • Cache list results with the spec’s ttlMs, keep tool order deterministic, and cache per-tenant where content permissions allow.

Your evidence: the gateway, AIMD admission and the two-stores bug in N8; the run-budget design in G5.

5 · Audit
  • A receipt per call: firm, user, client application, tool and version, policy decision, sources returned, and outcome. Denied attempts too.
  • Write the durable record before executing anything with a side effect; an unknown outcome stays unknown until reconciled.
  • Audit logs hold privileged material by reference, with retention and access agreed with the firm. They are sensitive data themselves.

Your evidence: G7 (design) and the recorded-decision mechanism in Q9.

6 · Prompt-injection boundaries — both directions
  • Inbound: documents a firm uploads, or pulls through a connector, can carry instructions. They are data. CoCounsel’s agent must not gain new permissions or destinations because a document says so.
  • Outbound: CoCounsel’s answer becomes untrusted input inside Claude or Quick. Return structured fields, mark quoted source text as quoted, and never return anything that would be dangerous if the outside model obeyed it.
  • No write, send or export tools without an explicit, version-bound human approval. Tool descriptions are part of the attack surface; version and review them like code.
  • Test the outcome, not the text: the export did not happen, whatever the model said.

Your evidence: G2 and G4 (designs); the layered-guardrails model in the FAQ’s guardrails part.

7 · Versioning
  • Protocol: support the current dated revision and one prior during migrations. The streamable HTTP spec describes clients probing modern servers first and falling back to the legacy handshake. Fact
  • Tools: additive changes in place; a breaking change gets a new tool name; old names deprecate with usage telemetry and a date. MCP itself uses at least twelve months for deprecations. Fact for the spec window.
  • Behavior: pin model, prompt and tool versions to evaluation results, so “the tool changed” and “the model changed” are separate, testable events.

Your evidence: debt policy that flips once users depend on you (Q12). Say the flip out loud: an alpha can break freely; a million-user product with external clients cannot.

What you would build first

One read-only, task-shaped tool behind real OAuth, one pilot firm, full audit, called from one client. Measure citation accuracy and latency on that slice before adding breadth. That is the canary-first habit from N13 applied to an integration.

07 · Agentic workflow reliability

Completion you can prove, not steps that ran

Answer spine Inference

  • Define done per task, with evidence. A research memo is complete when every cited authority resolves and passes a validity check, not when the model stops.
  • Evaluate end to end. Thomson Reuters already moved its metric from skill-level scores to whether the system completes a natural task end to end Fact. Extend that to tasks started from Claude or Quick.
  • Durable steps. Checkpoint long runs, make side effects idempotent, and resume rather than restart after a crash or timeout.
  • Human checkpoints where judgment lives. Thomson Reuters describes Brief Builder as agentic with a human in the loop Fact. Map those pauses to input_required or A2A’s input-required state at the boundary.
  • Honest partial results. Stopped, partial and unknown are first-class outcomes with what completed and what did not.
  • Observe per step. Tool latency, retries, token spend and verification failures by step, so a regression points at a stage.

Your evidence

  • “Done” requires evidence; the grader cannot be the implementer, enforced structurally; 141 scenario tests across ten roles (Q8).
  • Telling a dead worker from a slow one, and not reassigning under a possibly-live write (N3).
  • A silent six-hour stall and the watchdog that no longer depends on what it watches (N9).
  • Containment and reconciliation after an agent acts wrongly (G8, design) and the eval-before-ship plan (G6, design).

08 · Python, React, cost + latency

The full-stack half of the job

Python API design — “How would you build the service behind an MCP or A2A endpoint?”

Answer spine Inference

  • Async I/O end to end, because the service mostly waits on models and content APIs. Put a timeout on every outbound call and propagate cancellation when the client disconnects.
  • Validate at the edge with typed models, and generate the OpenAPI or JSON Schema contract from them so the TypeScript client and MCP tool schemas share one source.
  • Stream long work (SSE); hand anything longer than a request to a durable job with an id the client can poll or subscribe to.
  • Idempotency keys on anything with a side effect; one error model with retryable versus permanent codes.
  • Structured logs keyed by request, firm and task ids; per-step latency and token metrics.
  • Tests: contract tests on the public schema, and authorization tests with a negative control for every allowed path.

Be candid here

Your verified Python is the Storewolf scoring sidecar: a long-lived process reading JSON lines on stdin, not an HTTP service (Storewolf). Papercusp’s server is TypeScript. Say that plainly, then show the design judgment above. Do not name a Python web framework as something you have run in production unless your résumé says so.

The transferable story: the feature-schema contract across a process boundary — training writes the exact column list, inference re-adds missing columns and reindexes to the booster’s feature names. Two guards on one failure mode is an API-contract story in disguise.

React and TypeScript — “What does the frontend for agentic work need that a normal CRUD app does not?”

Answer spine Inference

  • Render a task as a state machine the user can read: queued, working, needs your input, done, failed, cancelled. The A2A task states are a good vocabulary even inside one product.
  • Stream progress and partial artifacts; never show a success toast because a request was accepted.
  • Citations are UI, not decoration: every claim links to its source, and verification status is visible.
  • Keep server state in a query cache and meaningful view state in the URL, so a result is shareable and testable.
  • Budget connections: several streaming panels can starve the browser’s per-host connection limit.
  • Accessibility is part of the standard: live regions for streaming text, focus management when a task asks for input, keyboard-reachable citations.

Your evidence: the polling-to-streaming fix for ~40 queries against ~6 connections, and the anti-pattern list that includes duplicate React keys (Q11). URL-held UI state and headless UI verification (N11).

Gap to name: that UI is an internal operator desktop app. Accessibility work is not in your verified material.

Performance and LLM cost/latency — “A CoCounsel workflow called from Claude feels slow. Where do you look?”

Answer spine Inference

  • Split the latency: client and network, authorization, planning, each tool call, each model call, verification, and serialization back. Report p50 and p95 per step, not one number.
  • Time to first useful output matters more than total time for long research: stream the plan and early findings.
  • Cost levers: stable prompt prefixes and deterministic tool order for cache hits, routing easy steps to smaller models, parallel independent tool calls, and bounded results so nothing is paid for twice.
  • Thomson Reuters is multi-model with a proprietary legal LLM Fact. Ask where routing decisions live.
  • Set a quality floor before optimizing: a faster answer with a broken citation is a regression, not a win.

Your evidence: admission versus compute — a test run waited fourteen minutes without starting in a shared queue under load, versus 1.5 seconds on a direct path (Q11); result caps and projections, prompt-cache-aware routing (N8).

09 · Leadership and behavioural

Drafted answers, each tied to a verified card

Pick three to rehearse aloud. Each draft uses only what the linked card supports; where your record is thin, the draft says so first.

“How do you set technical standards for a team?”

The standard I’m proudest of is a rule rather than a component. We kept hitting the same bug in different costumes: config or documentation restating something the code already owns, and drifting. So we made a ladder — derive the value from the source; if you can’t, pin it with a test that fails when the prose and code disagree; if static analysis can’t see it, attest it at runtime; only then maintain it by hand, and say why. There are forty-seven of those pin tests now. The part that made it a standard, not a project, is that “a new config field restating the code” became a review smell people name. I apply the same idea to tests: exactly four frameworks, and a lint fails a new ad-hoc script.

Source: Q5 and Q2.

Add for a lead role: “With a team, enforcement catches the regression, but the review is where people learn why. I’d want both.” That is a stated approach, not a past result.

“How do you do code review?” / “What makes you push back on a change?”

The most useful thing I can give a reviewer is evidence, not a conclusion: what I ran, what it returned, what I couldn’t determine. “This works” asks them to trust me; “here’s the failing case before and after” lets them check me. I review the same way. What makes me push back is a new config field that restates something the code already knows — a second copy of a truth with no owner. And I ask whether the new test has ever failed, because a guard that has never failed hasn’t been tested.

Source: Q13, rapid-fire “review taste”, Q2.

“Tell me about mentoring an engineer.” Gap

I’ll be straight: my recent work hasn’t included formally mentoring engineers; the contributors I’ve directed have mostly been automated agents. What transfers is how I teach through the system. Every refusal names its own repair, so someone blocked learns the rule at the moment they hit it, and each rule carries the incident that produced it. With people I’d mentor the same way: pair on the first change in an unfamiliar area, review by asking what would make the test fail rather than rewriting their code, and write the reason next to the rule.

Source: the Answer Bank’s advice to say so and pivot (Q13); teaching refusals (N6).

“How do you break down a large initiative and estimate it?”

I break down by risk, not by component. First the thinnest slice that crosses the riskiest boundary end to end — for an external MCP integration that’s one read-only tool, real authentication, one pilot customer, and audit — then breadth. When I drained a large backlog, the pattern was triage and rank before anyone starts, feed work by a written filter rather than hand-assignment, launch one canary and confirm it completes, then scale, and finish with a residue table of what didn’t get done and why. For estimates I’d give ranges and re-estimate at each checkpoint, because the first slice is where the real unknowns show up.

Source: N13. The estimation sentence is an approach, not a track record; do not attach numbers to it.

“Tell me about influencing a decision without authority.”

What I learned is that most disagreements I thought were resolved came back, because the resolution lived in a chat message nobody re-reads. So rulings other people must follow get recorded as numbered decisions attached to the plan they govern, with the reasoning, and the tool that hands out the next piece of work shows the governing decisions inline. The payoff surprised me: someone re-read a recorded decision, realized their own earlier work had been wrong in most of the places they’d touched, fixed it, and then found more instances of the same mistake. Written decisions persuade after you’ve left the room.

Source: Q9.

“How do you decide when to pay down technical debt?”

It depends on whether anyone depends on you. My current system is alpha with no external users, so the expensive mistake there is caution — a compatibility shim protecting nobody — and I bias toward making the breaking fix now. CoCounsel is the opposite case: a million users and external AI clients calling it, so the default flips to versioned tools and real deprecation windows. What I’d keep either way is the line between a fix and a mitigation. Restarting or widening a timeout is fine if you say it’s a mitigation and the real fix has an owner.

Source: Q12; the million-user figure is Thomson Reuters’ public February 2026 number.

“Tell me about a mistake.” / “A hard bug.” / “An incident.”
  • Mistake: reporting a metric as a regression when one column stored two scales; the rule “find the code that writes a number before reporting it”; retracting in the written record (Q6).
  • Hard bug: an instrument that lied — a liveness check calling a running process “gone” — and the positive-control rule (Q3).
  • Incident: auto-commit silently stalled for about six hours; watchdogs must not depend on what they watch (N9).

Pick one per question. For this role, the incident story lands best if they ask about operating integrations: it is about detecting silent failure at a boundary.

“Why Thomson Reuters?” / “Why this team?”

Two reasons. The hard part of legal AI isn’t generating text, it’s being able to show where every claim came from — and Thomson Reuters owns the content and the validity signals to do that. And CoCounsel is now reached from outside: inside Claude over MCP, with Amazon Quick announced. That makes the integration boundary part of the product, which is exactly where I’ve spent my time — deciding what a model caller is allowed to do, what it gets back, and how you prove what happened. I’d rather do that work where the stakes are privileged client data than where nobody would notice a mistake.

Check before saying: “Amazon Quick announced” and “inside Claude” are from the 12 May and 20 August 2026 releases in section 12.

“What is your biggest weakness?”

Two honest options, both sourced:

  • Recent human-team leadership. Much of your recent work coordinated automated agents, not a room of engineers (Q13). Say what you are doing about it and what transfers.
  • Process weight. Forty-seven hooks and a long playbook is a tax on every action; a prompt lagged a removed tool by a month (N14). This one shows lead-level self-criticism about standards.

Avoid a disguised strength. The Answer Bank’s rule applies: a real weakness with a number beats any polished non-answer.

05 · Likely questions

Spoken drafts, each under ninety seconds

Read each draft aloud once tonight, then close it and say it from the summary line. Where a draft is a proposed design rather than something you built, it says so. Keep it labelled that way when you speak.

“What does an AI control plane mean to you?”

Definition, then your mapping

I think of it as four jobs between the people building agents and the things agents touch. First, an inventory: every agent and model registered with an owner, a version and a risk tier. Second, identity and policy at the point of use: a gateway that decides what an agent may call, under whose identity, and routes it. Third, guardrails in the lifecycle, so nothing reaches production without passing checks that are code rather than a form. Fourth, telemetry and an audit record, so you can explain afterwards what an agent did and why it was allowed. The agents doing work are the data plane. The control plane decides what’s allowed and proves what happened. In my own platform the pieces map fairly directly: the tool catalog is the inventory, default-deny dispatch and capability checks are the policy point, the release gate is the lifecycle guardrail, and live state cells plus task identity are the telemetry.

“Where does it usually fail?” Drift. A registry maintained by hand stops describing what is actually running. You have hit exactly that. Tell the event-catalog story from Q5.

“Gateway versus control plane?” The gateway is the enforcement point on the request path. The control plane adds inventory, policy authoring, observability and audit around it.

Definition: vendor literature, Inference. Mapping: N1, G1, Q1, Q7.

“How would you inject Security and Responsible AI guardrails into CI/CD for agents?”

Proposed design, anchored in your gate

I’d make the pipeline refuse to promote anything it can’t positively verify. Stage one is registration: the agent has to exist in the registry with an owner, a risk tier and the data it touches, or the build stops. Stage two is static policy: requested tool scopes checked against what the tier allows, a secrets scan, and the prompt, model and tool versions pinned so every result is attributable. Stage three is behavioral: scenario and red-team runs that assert a forbidden side effect did not happen, each paired with an authorized positive control, so an always-deny policy or a broken connector can’t look green. Stage four, for higher tiers, is the Responsible AI evidence as an attached review record, not a checkbox. Then a staged rollout: shadow, a limited pilot, and stop criteria. The principle carries straight over from my own release gate. Anything we can’t positively verify falls back to the stricter path, because a silently narrowed check hands you a false green.

“Won’t that slow teams down?” Tier it. Low-risk internal agents get the automated stages, and human review is reserved for the tiers that need it. Reuse verdicts against pinned versions, the way your gate inherits passes for untouched tests instead of re-running them.

“How do you know a guardrail works?” A guard that has never failed hasn’t been tested. Your mutation probe deliberately breaks the thing under test and asserts the guard catches it.

Design: G6, Proposed. Built: Q1, Q2.

“How do you handle identity and access for autonomous agents?”

Built, with the honest status

I separate three questions: which operation the agent can request, what the server authorizes, and what the resulting process can actually touch. In my platform the dispatcher runs a default-deny step, so a tool that declares no gate at all is refused rather than allowed by omission. Above that there’s a per-role tool allowlist, a per-principal capability check, and a capability envelope with a protected floor no autonomous role can exercise. The generic dispatch route goes through the same stack, because a tool ban that a generic dispatcher can route around is theatre. I’d be straight about the state of it: the enforcement point is live, but the authored policy is thin. When I checked on 9 September, only three roles carried deny entries. For an enterprise gateway I’d add that the model never chooses its own scope. The server derives it from authenticated identity, credentials stay server-side, and a resumed job is re-authorized instead of trusted from when it was queued.

“What would prove the policy is real?” Run an allowed command through the managed route. Verify its native counterpart is unavailable on launch and on resume. Then test unauthorized writes, secret reads, egress and child-process cleanup.

“Can privilege bypass it?” Your session confinement is shaped so it can’t: the decision function receives no role or superuser flag, and it has only a deny list. Say plainly that it is implemented and wired, but zero confinements have been declared.

G1 · native execution · G3 for the scope-derivation design.

“How do you observe agents and LLMs in production?”

Three properties, then the LLM layer

Three properties matter more than the tool name. Provenance: our process list says who launched something, for which piece of work, and what it costs, not just that something is using CPU. Outside observation: a health signal emitted by the thing being judged can’t detect that thing being saturated, so anything that matters is observed from outside the process. Explicit unknowns: a value we can’t measure says “not measured” in-band, so unknown never reads as zero or fine. We alert on transitions, not levels. For LLM calls specifically, I’d make every call carry the model, prompt and tool versions, tokens, latency, cost, and the policy decision that allowed it, all correlated to the agent and the run. Then the telemetry doubles as the audit trail.

“Alert fatigue?” Anything that fires and self-recovers is still a bug. A false alarm is a defect in the alarm.

“Dead agent or slow one?” A heartbeat proves the process is scheduled, not that it is working. Use one liveness function with an evidence ladder, and φ-accrual suspicion for eviction across machines.

Built: Q7, N3. Per-call LLM telemetry: G7, Proposed.

“How do you test or simulate agents before production?”

Two layers, and who may judge

Two layers, kept separate. Hard safety properties get deterministic tests: authorization, approval binding, duplicate-write protection. Model behavior gets scenario runs. In my platform there are 141 behavioral scenario tests across ten agent roles that run the actual prompts against a model. For capability, there’s a pre-registered random subset of SWE-bench Pro, 50 and 150 tasks at seed 42, so we can’t move the goalposts after the run. The part I’d emphasize is who is allowed to judge. A grader can’t be in the implementer’s lineage, enforced structurally, and “done” requires cited evidence. For a safety test, the assertion is that the side effect didn’t happen, not that the model wrote a refusal.

“A good red-team case?” Change an approved payload after review. Resume after permission is revoked. Replay the same send twice. Put an export instruction inside retrieved content. Observe the backend, not the final text.

“What pass rate would you ship at?” Not a bare percentage. It needs the denominator and the severity. Zero cross-tenant leaks in a finite suite is a release condition, not proof the risk is zero.

Q8 · G6 for the red-team design.

“Tell me about a hard problem you solved.”

The registry story, because this is a registry role

The most relevant one here is registry drift. Our event catalog listed which events had emitters, and it was maintained by hand. The single most-fired event in the whole system was recorded as unregistered, and fourteen subscribers were parked waiting on an event with no emitter anywhere. Fixing that entry wasn’t the point. The category was: a second copy of a truth the code already owns always drifts. So we wrote a ladder. Derive the value from the source if you can. If you can’t, keep the prose but pin it with a test that fails when it diverges; there are 47 of those now. If static analysis can’t see it, attest it against the runtime on a schedule. Hand-maintain it only as a last resort, with a stated reason. An Agent Registry needs the same rule: registration should be derived from what is actually deployed, or checked against it, not filled in by hand.

“An example of attestation?” The tool-description budget check runs against the runtime catalog at registration and on every hot reload, because a static read under-counts tools that build their text from constants.

“Another one?” The silent stall: the background commit routine kept firing, but no commit landed and nothing alarmed for about six hours. A watchdog must not depend on what it watches, and the robust signal was that the head stopped advancing.

“How do you handle rate limits, routing and cost across model providers?”

A pool, a gateway, and two stores that disagreed

Every agent’s calls bill to a credentialed account, and there’s a pool of them behind an inference gateway. There are three routing modes. Pin gives predictable billing and no failover. Auto picks at session start, prefers the same account each turn so the prompt cache stays warm, and fails over on a rate limit. Bypass uses the system credential. Admission is an AIMD controller over the pool’s measured headroom. The operating rule is to preflight before launch: one canary, confirm it completes a real turn, then the rest. The bug that taught me most was two stores. A probe updated the database view of capacity, but the gateway kept its own in-memory exclusion map, and nothing reconciled them. Admission sat at four while the controller allowed twenty-four. The fix was one action that converges both, and a status read that names which ceiling is binding.

“When do you re-route automatically?” On a measured failure, never on a predicted one.

“Cost per agent?” Result caps and projections on every tool, and pacing around a one-hour prompt-cache window instead of waking agents just to keep it warm.

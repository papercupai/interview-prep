06 · If he goes technical

Short answers for the likely probes

It's a 30-minute intro, so expect one or two of these, not a design round. Give the answer in about 60 seconds, then stop.

Design

“Expose a C++ solver to customers as a service”

  • gRPC: SubmitJob (unary, with an idempotency key), GetJob, StreamProgress (server-streaming), CancelJob
  • Validate the request and the geometry up front, then persist the job row in Postgres. Workers claim with FOR UPDATE SKIP LOCKED or read from a task queue.
  • Workers call C++ through pybind11 and release the GIL around the solve. Results go to object storage and the client gets a URL, not a huge gRPC message.
  • Backpressure: admission control on queue depth and GPU quota per tenant. Autoscale GPU nodes on queue depth, not CPU.
  • One trace across Python and C++ (OpenTelemetry), plus job-state metrics
Concurrency

“Concurrency across the Python/C++ boundary?”

  • The GIL: long C++ calls release it (py::gil_scoped_release). A C++ thread that calls back into Python must acquire it first, or you get crashes or deadlock.
  • Ownership: who frees the buffer? Use zero-copy views (buffer protocol, numpy) only while the owner is alive.
  • Cancellation: C++ won't see a Python exception. Pass a cancel flag or token that the solver loop checks.
  • Signals only reach the main thread, so a stuck native call needs its own timeout. For isolation or crash safety, run it in a separate process.
Retries

“How do you make retries safe?”

At-least-once delivery plus idempotent handlers. The idempotency key has a unique constraint, and a replayed request returns the original result. Only retry what can be retried: gRPC UNAVAILABLE or DEADLINE_EXCEEDED, never INVALID_ARGUMENT. Use exponential backoff with jitter and a retry budget. A worker's lease carries a fencing token so a zombie can't write a result after it has been replaced.

Postgres

“Walk me through a safe migration on a big table”

Expand, then contract. Add a nullable column (no table rewrite), backfill in batches, then add the constraint as NOT VALID and VALIDATE it separately. Build indexes with CREATE INDEX CONCURRENTLY. Set a lock_timeout so a DDL statement waiting on a lock doesn't block every query behind it. Deploy code that works with both schemas before you drop anything.

gRPC

“gRPC gotchas?”

Always set deadlines and propagate them. Evolving protos: never reuse or renumber fields, add new ones as optional, and reserve the numbers of removed ones. Large payloads should be streamed in chunks or handed off as a presigned URL. Know unary vs server-streaming vs bidirectional. Async Python uses grpc.aio.

Debugging

“A job got 3× slower. Where do you look?”

Start by measuring, not guessing. Is it queue wait or run time? Check the trace spans. For Python, py-spy. For native code, perf and flame graphs. Check GPU utilization. Compare input size, since geometry may have grown. Rule out contention: another tenant on the same node, or memory pressure. Don't blame “load” until you can show the mechanism, a rule you apply in Papercusp every day.

04 · Role-informed practice · not reported questions

The questions worth rehearsing out loud

These are plausible prompts inferred from the role and product. Ranking is a preparation priority, not an estimated probability. Answer outlines are adaptable drafts: use only experiences and outcomes that are true for you.

1 · Walk me through a production system you built. What did you personally own?
Strong answer structure

Problem and users → a small architecture diagram → your contribution → one correctness invariant → one real failure or tradeoff → evidence the fix worked. For Papercusp, lead with orchestration and production ownership, not the agent count.

Follow-ups to prepare
  • Why PostgreSQL rather than an in-memory queue? Where are the transaction boundaries?
  • Which component can fail independently? What survives a process restart?
  • What did you measure, and what would you change if requirements changed?
Avoid

A feature tour, unverified metrics, or taking credit for code you did not own.

2 · Design a service that runs expensive simulations and returns results reliably.
Answer outline

Clarify job size, latency, tenant isolation, result size and compute limits. Validate a request, persist a job, return an ID, claim work atomically, run compute outside the transaction, then conditionally publish the result. Add bounded admission, per-tenant quotas, versioned inputs and observable states. Keep large artifacts in object storage, with authorized references rather than database blobs.

Important tradeoff

A synchronous RPC can submit work; it need not stay open for the entire simulation. Polling or a stream can report status. A lost client connection must not silently decide the job's lifecycle.

Rehearse the whole design below.

3 · A worker crashes—or a paused worker returns after its job has been reassigned. What happens?
Answer outline

Persist attempts and leases. Reclaim expired attempts according to policy. Issue a monotonically changing attempt/fencing token. Completion updates must match the current token and expected state; an old worker must not overwrite the new attempt's result.

The subtle part

A lease is a liveness mechanism, not proof that the old process stopped. Database fencing does not automatically fence external effects. Use attempt-scoped artifacts, idempotent engine calls where possible, and conditional publication. A heartbeat alone does not prove useful progress.

Test you should describe

Pause worker A, reclaim with B, then resume A. Show that A cannot publish a stale result. Also crash between compute completion and result acknowledgement.

4 · How do you make submission idempotent under concurrent retries?
Answer outline

Scope the request key to the tenant and operation. Record the key, validated input fingerprint and resulting job ID under a database uniqueness constraint. Repeating the same request returns the existing job; reusing the key with different inputs is rejected. Don't rely on “check then insert” without atomic enforcement.

Follow-up

If a database write and queue publish cross systems, explain the crash gap and a transactional outbox or a database-backed claim path. Distinguish at-least-once delivery from effectively-once visible results; don't promise global exactly-once execution.

5 · When would you use async Python, threads, processes or a native C++ call?
Answer outline

Async works for cooperative I/O; declaring a function async does not make a blocking call non-blocking. On a conventional GIL-enabled Python build, threads don't generally parallelize Python CPU work. A native extension can run concurrently if it releases the GIL and is thread-safe; processes provide a different isolation boundary with serialization and lifecycle costs.

Native boundary

pybind11 does not automatically release the GIL. Discuss explicit release around safe native work, reacquisition before Python-object access, memory ownership and cancellation. A thread-safe interpreter boundary does not imply a thread-safe engine.

Python's thread guidance · pybind11 GIL guidance

6 · The gRPC deadline expires, but the native simulation keeps running. How do you handle that?
Answer outline

Give RPCs realistic deadlines and carry the remaining budget downstream; don't restart a full timeout at each hop. A cancelled RPC does not automatically stop application-created work. Separate “the caller stopped waiting” from “cancel this durable job.” For actual cancellation, track it, ask the engine cooperatively, release resources and fence late results. If hard termination is necessary, choose an isolatable worker process rather than pretending a Python task can kill an arbitrary native thread.

Retry trap

A deadline error may occur after submission succeeded. Retry with the same idempotency key or query the job; don't automatically submit another expensive simulation.

Official gRPC deadline and server-cleanup guidance

7 · A user switches simulations, but an old response overwrites the new result. What's wrong?
Answer outline

Reproduce the out-of-order response. Associate responses with the current job/request identity and ignore stale completions. Cancel unnecessary fetches where supported; clean up effects and subscriptions. A component being mounted is not enough—the selected job may have changed while it stayed mounted.

Test

Start slow request A, switch to B, resolve B, then A. The UI must still display B. Include loading, error, cancelled and retrying states, and keyboard-accessible controls.

React's effect cleanup and race-condition example

8 · A PostgreSQL queue or status query gets slow. How do you investigate?
Answer outline

First separate pool wait, lock wait, execution time and network time. Inspect a representative query plan, actual row counts and access pattern before adding an index. Check whether filtering and ordering fit the index, whether a huge offset is the issue, and whether long transactions retain locks. Tune from evidence, then verify the relevant workload.

Queue-specific detail

FOR UPDATE SKIP LOCKED can let consumers skip locked candidate rows. PostgreSQL warns that it gives an inconsistent view: useful for a queue-like table, not a general correctness shortcut. Keep claim transactions short; never hold a row lock for a simulation's whole runtime.

PostgreSQL locking-clause documentation

9 · How would you ship and test a change spanning React, Python and native compute?
Answer outline

Define the public contract and failure behavior first. Use fast unit checks for validation/state transitions; integration tests with real database transactions and service contracts; a small real native-engine smoke path; and e2e tests for submission → status → authorized result access. Simulate duplicate delivery, cancellation, stale completion and partial failures—not just happy-path mocks.

Deployment and debugging

Plan compatible schema/API evolution, observable rollout and a rollback boundary. Correlate a request and job across frontend, service and native worker. Measure queue delay separately from compute time. Only claim solver correctness against a trusted reference owned with the domain team; UI tests can't establish physical accuracy.

05 · Ten-minute whiteboard rehearsal

Upload → simulation → trustworthy result

Original practice scenario, not a claim about Vinci's internal architecture. Start simple; earn complexity from explicit failure cases.

Clarify

What is the promise?

Interactive or batch? Maximum payload/result size? Tenant isolation? Cancellation semantics? Does repeating the same input mean reuse a result or deliberately recompute? What engine/model version defines reproducibility?

Submit

Validate and durably record intent

Authenticate the tenant, validate the input, authorize referenced assets, record the request key and input/version fingerprint, create one job, and return its ID. Reject key reuse with a different request. Don't expose another tenant's results through a guessed ID.

Claim

A short transaction—not a long lock

Atomically select available work and create an attempt/lease. Commit before compute. Bound admission by actual worker/GPU capacity and enforce tenant fairness; increasing concurrency is not automatically increasing throughput.

Compute

Make the native boundary explicit

Define input-buffer lifetime, GIL/thread behavior, engine thread safety, progress signals and cooperative cancellation. Persist outputs under an attempt-specific name so stale execution cannot corrupt the current result.

Complete

Publish only the current attempt

Conditionally advance state using the attempt token. Report durable status and authorized artifacts. Version events or status snapshots so a stale client update cannot move the UI backwards.

Observe

Locate the actual bottleneck

Separate admission wait, queue wait, input transfer, engine runtime and result transfer. Tie logs/traces to job and attempt IDs. Alert on stuck jobs with a recovery policy, not just on dead processes.

Failure timeline to draw: submit succeeds → response is lost → client retries → A claims → A pauses → lease expires → B claims → A resumes. Show why neither the retry nor A's late completion creates a second visible result.

06 · If there is a coding exercise

Two focused drills, not a guessed LeetCode list

SQL · concurrency

Claim one queued job

Sketch an atomic claim in PostgreSQL. State the schema assumptions and explain why two workers cannot claim the same queued row.

BEGIN;
WITH picked AS (
  SELECT id FROM jobs
  WHERE state = 'queued'
    AND available_at <= now()
  ORDER BY created_at, id
  LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE jobs AS j
SET state = 'running',
    attempt = j.attempt + 1
FROM picked
WHERE j.id = picked.id
RETURNING j.id, j.attempt;
COMMIT;

Whiteboard sketch, fictional schema: production needs lease expiry, ownership, admission/fairness and state-transition rules. An empty return is valid when no job is available. Commit before native compute; guard completion with the returned attempt token. Test two concurrent claimers and a stale finisher.

Python · diagnose before rewriting

Why isn't this non-blocking?

async def run_job(job):
    return engine.simulate(job)

Explain that a synchronous call still blocks its executing thread. Ask whether the native engine releases the GIL, is thread-safe and supports cancellation before choosing a thread or process boundary.

  • For async I/O, use a bounded semaphore around awaited work, not unbounded task creation.
  • If one task fails, explicitly choose fail-fast versus partial results. A TaskGroup and gather have different failure semantics.
  • A timeout is not proof that a thread/native operation stopped. Account for late completion and resource ownership.

Review Python task-group and gather semantics. Be ready to write a small test with delayed tasks, one failure and cancellation.
